# 部署指南总览

OmniPG 采用「宿主基础设施 + 容器网关」两层部署形态：

- **宿主层（Pigsty v4.4.0）**：PostgreSQL 18（5432）、pgBouncer（6432）、Redis（6379）、etcd（2379）、Grafana/VictoriaMetrics 等，配置见 `infra/`。
- **容器层（gateway/docker-compose.yml）**：etcd（APISIX 配置中心）、APISIX（9080 对外 / 9180 仅内网管理 / 7085 仅本机回环；9443 预留未映射）、PostgREST（3100）、Swagger UI（8082）、Logto（3001/3002）。PostgreSQL/pgBouncer/Redis 不放入容器，统一由 Pigsty 管理（22 号审查文档决策）。

本文档给出两套部署方案的对比、环境区分与部署前置检查；具体步骤见 [脚本部署.md](脚本部署.md) 与 [手动部署.md](手动部署.md)。

## 方案 A：一键脚本（scripts/deploy-all.sh）

适用场景（来自 `scripts/deploy-all.sh` 头注）：

- ⚠️ 仅适用于 **Phase 1 单机环境**（DB + 网关在同一台服务器）；
- WSL2 开发环境初始化；
- 测试服务器重建；
- 灾难恢复。

特点：

| 项 | 说明 |
| --- | --- |
| 入口 | `bash scripts/deploy-all.sh <environment>`，默认 development |
| 编排顺序 | deploy-infra（all）→ deploy-db → deploy-gateway → init-apisix-routes → e2e-test |
| 环境参数 | 第一参数传给所有子脚本（加载 `.env.$ENV`） |
| 失败行为 | `set -euo pipefail`，任一步失败立即退出并提示排查方向 |
| 优点 | 快、可重复，适合标准单机环境与 CI（`.github/workflows/deploy-all.yml`） |
| 缺点 | 可控性低；非标准拓扑（DB/网关分离）或历史遗留问题时不适用 |

## 方案 B：手动逐步部署

适用场景：

- 定制化部署：Phase 2 DB 服务器与网关服务器分离（`deploy-infra.sh db|gateway` 分模式）；
- 排查问题：定位「是哪一步失败」时按步骤重放；
- 理解每一步做什么（数据库 bootstrap、迁移、网关、Logto、辅助数据）；
- 在脚本不可用的环境（无 sudo、无 Docker Desktop 等）手工执行。

特点：每步对应一个 `scripts/` 脚本或配置目录，可逐段验证后再继续；详见 [手动部署.md](手动部署.md)。

## 两套方案差异对比

| 维度 | 一键脚本（方案 A） | 手动逐步（方案 B） |
| --- | --- | --- |
| 入口 | `scripts/deploy-all.sh` | 按 [手动部署.md](手动部署.md) 9 步执行 |
| 适用 | 标准单机 / 快速验证 / 重建 / 灾难恢复 | 定制拓扑 / 排障 / 学习理解 / CI 分步 |
| 速度 | 快（全自动） | 慢（逐步确认） |
| 可控性 | 低（顺序固定） | 高（可跳过/重试单步） |
| 幂等性 | 各子脚本幂等设计（见 [脚本部署.md](脚本部署.md)） | 同左，但依赖人工执行顺序 |
| 失败定位 | 脚本打印 ❌ 与排查提示 | 每步可独立验证，定位更直接 |
| 对应 CI | `deploy-all.yml` | `deploy-infra.yml` / `deploy-db.yml` / `deploy-gateway.yml` |

## 环境区分：development / staging / production

环境由根目录 `.env.<environment>` 区分（详见 [环境配置.md](环境配置.md)）：

| 维度 | development | staging | production |
| --- | --- | --- | --- |
| 配置文件 | `.env.development` | `.env.staging` | `.env.production` |
| APP_ENV | development | staging | production |
| APP_DEBUG | true | false | false |
| 敏感值 | 仓库内开发默认值（仅限本地） | `${VAR}` 占位符，由 CI/服务器环境注入 | `${VAR}` 占位符，由 CI/密钥服务注入 |
| 部署入口 | `bash scripts/deploy-all.sh development` | workflow_dispatch 选 staging | workflow_dispatch 选 production |
| 典型用途 | WSL2 本地开发 | 预发布验证 | 生产 |

> ⚠️ staging/production 的 `.env.*` 文件内容是 `${DB_PASSWORD}` 等占位符；`cp` / `export` 不会自动展开，必须由 CI Secrets 注入或先预展开（见 [环境配置.md](环境配置.md)）。

| 依赖 | 用途 | 检查 |

| WSL2 Ubuntu（systemd 启用） | Pigsty 宿主 | `cat /etc/wsl.conf` 含 `[boot] systemd=true` |
| Pigsty v4.4.0 | 集群部署（脚本会自动下载到 `~/pigsty`） | `ls ~/pigsty/deploy.yml` |
| Docker + Docker Compose | 网关栈 | `docker compose version` |
| psql / curl / python3 | 验证与脚本运行 | `command -v psql curl python3` |

| jq（e2e 使用） | JSON 解析 | `command -v jq` |
| MaxMind License Key（仅 geolite2 导入） | 辅助数据 | `MAXMIND_LICENSE_KEY` 环境变量 |

> `scripts/verify-stack.sh` 的【0/10】依赖预检会逐一检查 docker / curl / psql / python3。

组件版本（与 [01-项目简介/技术栈](../01-项目简介/技术栈.md) 口径一致）：Pigsty v4.4.0 · PostgreSQL 18 · PostgREST v14.15（容器 3100:3000）· APISIX 3.17.0 · etcd 3.5.11 · Logto OSS v1.42 · Swagger UI v5.2.0 · dbmate · pgTAP · GitHub Actions。

容器 → 宿主链路检查（Windows + WSL2 场景）：

```bash
# Windows 11 22H2+：启用 mirrored 网络（%USERPROFILE%\.wslconfig → networkingMode=mirrored）
# Windows 10：运行 scripts/wsl-portproxy.ps1 转发 5432/6432
docker run --rm --network app-net --add-host host.docker.internal:host-gateway \
  alpine sh -c 'nc -z -w3 host.docker.internal 6432 && echo OK || echo FAIL'
```

### 数据库前置

- Pigsty 已创建角色 `app_owner`（LOGIN/CREATEDB）、`authenticator`（LOGIN）、`web_anon`（NOLOGIN）与库 `app_db`（`infra/pigsty.yml` 的 `pg_users` / `pg_databases`）。
- 若使用 Logto：宿主 PG 需要 `logto` 库与用户（compose 中 `DB_URL` 引用 `postgres://logto:${LOGTO_DB_PASSWORD}@host.docker.internal:5433/logto`，运行态走宿主 5433；当前 `infra/*.yml` 未包含该库定义，首次部署前需预创建，见 [环境配置.md](环境配置.md)）。
- `gateway/.env` 已就绪（`cp .env.development gateway/.env`），其中 `APISIX_ADMIN_KEY`、`JWKS_JSON` 与 compose/APISIX 一致。

### 数据核查脚本：scripts/055-t1-precheck.sql

`scripts/055-t1-precheck.sql` 是仓库内唯一的「前置核查」SQL（只读，无任何写操作）：

```bash
psql -U app_owner -d app_db -f scripts/055-t1-precheck.sql
```

它面向 **055 菜单权限单表化迁移**，输出 iam_api / iam_menu / iam_role_api 的存量数据清单（总览、无码行、死端点、button 挂接、孤儿行、绑定分布、一码多行、转换映射预期等 §0–§11）。在升级涉及权限体系变更前，先跑它确认数据现状；普通部署不强制。

## 部署顺序总览

```
1. deploy-infra.sh all <env>   # Pigsty：PG 集群 / pgBouncer / Redis / etcd / 监控
2. deploy-db.sh <env>          # bootstrap（init + src types）→ dbmate up → apply-src → dbmate status
3. deploy-gateway.sh <env>     # gateway/.env → compose pull/build/up → 健康检查
4. APISIX 路由初始化           # init-apisix-routes.sh（Logto 路由集，2026-08-19 起唯一部署链入口）
5. e2e-test.sh                 # Logto OIDC code flow 端到端验收（deploy-all 第 5 步）
```

> 注：Logto 初始化（管理员、应用、角色、组织、webhook、claims 脚本）由 `scripts/phase2/init-logto.py` 完成，不在 deploy-all 自动链中，首次部署需手动执行（见 [手动部署.md](手动部署.md) Step 7）。

## CI/CD 简述

GitHub Actions（`.github/workflows/`）：

| Workflow | 触发 | 职责 |
| --- | --- | --- |
| ci.yml | PR（dev/main） | 路径过滤（db/gateway/infra/extensions）→ sqlfluff 静态检查、dbmate dry-run、compose 校验/构建、yamllint、扩展一致性检查 |
| deploy-all.yml | workflow_dispatch（staging/production） | SSH 到服务器 → git pull → `bash scripts/deploy-all.sh <env>` → e2e |
| deploy-db.yml | workflow_dispatch | SSH → git pull → `deploy-db.sh` → `dbmate status` + 函数存在性验证 |
| deploy-gateway.yml | workflow_dispatch | SSH → git pull → `deploy-gateway.sh` → `init-apisix-routes.sh` → e2e |
| deploy-infra.yml | workflow_dispatch（mode: all/db/gateway） | SSH → git pull → `deploy-infra.sh <mode> <env>` |

所需 Secrets：`SSH_PRIVATE_KEY`、`DB_SERVER_HOST`、`GATEWAY_SERVER_HOST`、`SERVER_USER`、`DBMATE_DATABASE_URL`、`DB_URI`、`APISIX_ADMIN_KEY`。

> ✅ 2026-08-19：ci.yml 的 `syncer-changed` 过滤与 `syncer-check` 任务已移除；`infra-check` 只检查唯一 `infra/pigsty.yml`。✅ deploy-db.yml 验证查询已改为 `api_v1_platform`（2026-08-19）。
