# 常见问题排查

> 本文档面向本地开发环境（WSL2 + Docker Desktop + Pigsty）的高频问题。定位顺序：容器 → 数据库 → 网关 → Logto。

## 快速定位建议

1. `docker compose ps` 确认容器状态（app-etcd / app-apisix / app-postgrest / app-swagger / app-logto）
2. `docker compose logs <svc> --tail 50` 看具体报错
3. 数据库问题查宿主 Pigsty（pg_hba / pgbouncer / userlist）
4. 网关问题查 `gateway/apisix/config.yaml` 与路由初始化脚本 `init-apisix-routes.sh`
5. Logto 问题查 `docker logs app-logto`（db seed / CSP patch / 启动）

## 1. 端口被占用 / 容器起不来

端口占用表（本栈与常见冲突源）：

| 端口 | 本栈占用 | 常见冲突 |
| --- | --- | --- |
| 3000 | Grafana（Pigsty） | 旧版 PostgREST 映射（现映射 3100） |
| 3001 / 3002 | Logto core / console | 其他 Node 服务 |
| 3100 | PostgREST（compose 硬编码） | — |
| 9080 | APISIX 数据面（唯一对外端口） | 其他网关 |
| 9180 | APISIX Admin + Dashboard（仅内网管理） | 其他管理面板 |
| 7085 | APISIX Status API（仅本机回环 127.0.0.1） | — |
| ~~9443~~ | ~~APISIX HTTPS（预留，2026-08-20 起不再映射宿主）~~ | 其他 HTTPS 服务 |
| 8082 | Swagger UI | 其他 Web 服务 |
| 2379 | Pigsty etcd | ⚠️ compose 内 app-etcd **不映射** 2379，避免冲突 |
| 5432 / 6432 | 宿主 PG / pgbouncer | Windows 侧服务（需 portproxy 时） |

排查：

```bash
# Windows
netstat -ano | findstr :3001
taskkill /PID <pid> /F        # 确认占用者后

# WSL2
ss -tlnp | grep -E '3001|3100|9080|6432'
```

容器起不来：

- `docker compose ps` 看 Exit 状态；`docker compose logs app-apisix --tail 50` 看报错。
- APISIX 依赖 etcd：etcd 未就绪时 APISIX 反复重启。查 `docker logs app-etcd`，确认 compose 内 `app-etcd:2379` 可达。
- Logto 起不来：`db seed` 失败通常是 `DB_URL`（host.docker.internal:5433）连不上 `logto` 库或密码错（compose 默认 `logto_dev_pass_2026`）。
- 改了 `LOGTO_EXTRA_FRAME_ANCESTOR` 或端口后需 `docker compose up -d --force-recreate logto`（CSP 补丁幂等，不会自动更新）。
- 镜像拉取失败：检查网络/镜像源（见 [前置条件](前置条件.md)）。

## 2. 数据库连接失败（密码 / pg_hba / pgbouncer）

三层密码必须一致：

| 位置 | 配置 |
| --- | --- |
| Pigsty `pg_users` | app_owner / authenticator / logto 的登录密码 |
| pgBouncer `userlist.txt` | 同密码（明文或 SCRAM 形式） |
| `gateway/.env` | `DB_PASSWORD`、`AUTHENTICATOR_PASSWORD`、`LOGTO_DB_PASSWORD` |

验证与修复：

```bash
# 直连 PG（5432）
PGPASSWORD=dev_password_change_me psql -h 127.0.0.1 -U app_owner -d app_db -c "SELECT 1"
# 经 pgbouncer（6432，PostgREST 路径）
PGPASSWORD=authenticator_dev_pass psql -h 127.0.0.1 -p 6432 -U authenticator -d app_db -c "SELECT 1"

# 检查 pg_hba（需允许 127.0.0.1/32、172.17.0.0/16、172.20.0.0/16，scram-sha-256）
grep -vE '^[[:space:]]*(#|$)' /etc/postgresql/18/main/pg_hba.conf
sudo -u postgres psql -c "SELECT pg_reload_conf();"

# 重启 pgbouncer
pkill pgbouncer
sudo -u postgres /usr/sbin/pgbouncer /etc/pgbouncer/pgbouncer.ini &
```

- 密码含特殊字符时用 `PGPASSWORD='...'` 环境变量，不要拼进 URL（历史踩坑记录，已归档）。
- PostgREST 连接串走 pgbouncer **6432**（`PGRST_DB_URI`）；Logto 走宿主 PG **5433**（compose `DB_URL`）。
- 容器→宿主不通：`docker run --rm --network gateway_app-net --add-host host.docker.internal:host-gateway alpine sh -c 'nc -z -w3 host.docker.internal 6432'`；不通则检查 Docker Desktop WSL2 网络 / `scripts/wsl-portproxy.ps1`（§6）。
- 直连 PostgREST 报 `PGRST101`（连不上库）/ `PGRST115`（authenticator/web_anon 角色缺失）时，检查 Pigsty 角色与 GRANT 链（`db/init/02-schemas.sql`、`db/api_v1/platform/privileges/zz_grant_all.sql`）。

## 3. 迁移失败与回滚

`make migrate` 的行为（代码事实）：

- 连接 `postgres://app_owner:<DB_PASSWORD>@127.0.0.1:5432/app_db`（**直连 5432**），`DB_PASSWORD` 取自 `gateway/.env`——文件缺失或密码错都会失败。
- 迁移目录 `db/migrations/platform`（当前为 squash 基线 064/065/066）；`make migrate-status` 查看状态。

失败处理：

```bash
make migrate-status      # 看哪些已应用/待应用
make migrate-rollback    # 回滚最近一次（dbmate rollback）
```

- 注意：`065_v010_baseline.sql` / `066_v010_seed_data.sql` 是 squash 基线，**没有 down 语义**（历史 62 个迁移在 git tag `v0.1.0`）；对这类文件执行 rollback 会报错或无事发生。
- 迁移只建表结构与种子；函数/视图/触发器/RLS 在 `db/src`、`db/api_v1`，全量幂等重放用 `bash scripts/apply-src.sh <database_url>`（完整部署链见 `scripts/deploy-db.sh`）。
- schema 变化后 PostgREST 需要重载：`docker restart app-postgrest`（或等其自动 reload）。

## 4. APISIX 路由未生效

现象：所有请求 404 / 受保护 API 全 401 / 新增路由不生效 / Dashboard 路由列表为空。

解法：

```bash
# ① 确认 APISIX 就绪
curl -s http://localhost:7085/status        # {"status":"ok"}

# ② 检查 Admin API 中实际生效的路由（Dashboard: http://localhost:9180/ui）
curl -s http://localhost:9180/apisix/admin/routes -H "X-API-KEY: $APISIX_ADMIN_KEY" | python3 -m json.tool

# ③ 路由缺失/异常时，重跑路由初始化脚本
#    预期脚本（Logto 路由）：
bash scripts/init-apisix-routes.sh          # 需要 gateway/.env 含 LOGTO_WEBHOOK_SIGNING_KEY
#    部署链现状（make dev 自动运行的是旧脚本，见下方警告）：
# bash scripts/init-apisix-routes.sh
```

- 路由存 etcd（traditional 模式，`gateway/apisix/config.yaml`：`config_provider: etcd`）。etcd 未启动/配置不对 → Admin API 报错、路由为空。
- `gateway/apisix/apisix.yaml`（standalone 遗留）已于 2026-08-19 删除，改它无效。
- 401 全挂通常是 jwt-auth 元数据问题：`gateway/.env` 的 `JWKS_JSON` 不是 Logto JWKS（默认 HS256 dev key 验不了 Logto 签发的 token），或 `APISIX_ADMIN_KEY` 与 compose 不一致。staging/production 的 JWKS 应为 Logto RS256 公钥（compose 与 .env.staging/.production 注释写 ES384，口径不一致——需以 Logto 实际配置核实）。

> ✅ 2026-08-19：部署链（`make dev` 等）已统一为 Logto 版 `scripts/init-apisix-routes.sh`（7 条路由：logto_jwks / logto_proxy / webhook_logto / ensure_user / api_v1_platform / rpc_all / catch_all）；Casdoor 时代 `setup_apisix.sh` 已删除。排查路由问题以「检查 APISIX Admin API 中实际路由（http://localhost:9180/ui 或 GET /apisix/admin/routes）→ 重跑 `scripts/init-apisix-routes.sh`」为准。

## 5. Logto 登录回调 / CORS

- 回调报 `invalid redirect_uri`：`redirect_uri` 必须与 Logto Console 应用配置一致（e2e 默认 `http://localhost:5173/auth/callback`）。
- token 换不出来 / 拿到的是不透明串：token 交换请求必须带 `resource`（RFC 8707），否则 Logto 发 opaque token，APISIX 无法验签。
- CORS 被拦：APISIX 全局 CORS 已放行 `*`（`global_rules/1`，允许头含 `logto-signature-sha-256`）；开发期另有 `/logto/*` 同源代理；PostgREST 直连时 `PGRST_CORS_ORIGINS=*`。
- iframe 嵌入登录页被 CSP 拦截：compose entrypoint 用 `logto-csp-patch.js` 给 Logto 注入 `LOGTO_EXTRA_FRAME_ANCESTOR`（默认放行 localhost:3006/3007）。改了前端端口后必须 `docker compose up -d --force-recreate logto`（幂等补丁不会自动更新）。
- 改了 `JWKS_JSON` / `AUTHENTICATOR_PASSWORD` 等 env 后：`docker compose up -d --force-recreate postgrest apisix`（环境变量变化需要重建容器）。

## 6. WSL2 下 Windows 访问端口的 portproxy

背景：Windows 10 无 WSL2 mirrored 网络模式时，Docker 容器里的 `host.docker.internal` 无法直达 WSL2 内 Pigsty 服务（PG 5432 / pgbouncer 6432）。`scripts/wsl-portproxy.ps1` 在 Windows 侧把端口转发到 WSL2 IP：

```powershell
# PowerShell（管理员）
powershell -ExecutionPolicy Bypass -File scripts/wsl-portproxy.ps1
```

脚本行为（代码事实）：

- 取 `wsl hostname -I` 的 WSL2 IP；删除旧规则后 `netsh interface portproxy add v4tov4 listenport=5432/6432 ... connectaddress=<WSL2_IP>`（IP 漂移后重跑即更新）。
- 自动创建防火墙规则「OmniPG WSL2 PortProxy」（TCP 5432, 6432）。
- 结尾用 `Test-NetConnection 127.0.0.1 -Port 5432/6432` 自检。

注意：需要管理员权限；WSL2 IP 每次重启会变，需重跑；Windows 11 22H2+ 启用 mirrored 模式后可不用。验证：

```bash
# WSL2 内确认服务监听
ss -tlnp | grep -E ':5432|:6432'
# Windows 侧
Test-NetConnection 127.0.0.1 -Port 6432
```
