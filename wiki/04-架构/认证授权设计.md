# 认证与授权设计

> 本章是 wiki 的核心章节：认证（AuthN）由 Logto 承担，授权（AuthZ）判定在 PostgreSQL 内完成（RLS + has_permission）。"从 casbin 吸收了什么、放弃了什么" 见 §7。所有函数名/表名以 db/ 下实际 SQL 为准。

## 1. 认证：Logto OIDC 流程

```text
1. 前端未登录 → Logto SDK 重定向到 Logto 登录页（authorization code + PKCE，scope 含 offline_access）
2. 用户完成认证（密码 / 验证码 / 微信网页 / 微信原生 App 等连接器）
3. 回调 → SDK 用 authorization code 换 access token + refresh token
4. SDK getAccessToken(resource, organizationId) 用 refresh token flow 换组织 token
   （组织 token 不能从 code flow 直接获取——Logto 官方限制，见 05 号文档 F7）
5. 前端以组织 token 调业务 API；过期 → SDK 自动 refresh（角色变更在刷新时生效）
```

签发时执行 **Custom Token Claims 脚本**（scripts/phase2/init-logto.py 中的 CLAIMS_SCRIPT，v2.0 定稿：零 fetch，直接从 Logto context 提取）：

```javascript
const getCustomJwtClaims = async ({ token, context }) => {
  // ① 全局角色：context.user.roles（Logto roles 表，type=User）
  const globalRoles = (context.user?.roles ?? []).map((r) => r.name);
  // ② 组织角色：仅组织 token 存在 context.organization
  const orgId = context.organization?.id;
  const orgRoles = orgId
    ? (context.user?.organizationRoles ?? [])
        .filter((r) => r.organizationId === orgId)
        .map((r) => r.roleName)
    : [];
  // ③ 并集注入（网关 / current_user_roles 判定用）
  const roles = [...new Set([...globalRoles, ...orgRoles])];
  // ④ global_roles / org_roles 拆分注入——user_role 镜像 JIT 精确对齐用
  // ⑤ pg_role 映射（最高优先级 → PostgREST DB 角色）
  const priority = ['role_super_admin', 'role_admin', 'role_editor'];
  const pgRoleMap = {
    role_super_admin: 'super_admin',
    role_admin: 'role_admin',
    role_editor: 'role_editor',
    role_guest: 'role_guest'
  };
  const pgRole = priority.find((r) => roles.includes(r)) ?? 'role_guest';
  return { roles, global_roles: globalRoles, org_roles: orgRoles, pg_role: pgRoleMap[pgRole] };
};
```

JWT payload 样例（组织 token）：内置 claim `sub`（Logto 用户 id，21 位 nanoid）、`aud`（API 资源）、`organization_id`（组织 id，Logto 内置 F19）；自定义注入 `roles`（角色名数组）、`global_roles` / `org_roles`（镜像对齐）、`pg_role`（PostgREST 切换角色）。

## 2. Token 校验（网关层 / PostgREST）

| 层 | 组件 | 校验内容 | 配置 |
| --- | --- | --- | --- |
| 网关 | APISIX jwt-auth 插件 | 签名验签（开发：HS256 对称密钥，.env.example 占位；staging/production：Logto JWKS 公钥 **RS256**——05 文档与 init-apisix-routes.sh 口径；compose/.env 注释写 ES384，口径不一致，需以 Logto 实际配置核实） | jwt-auth 插件元数据：scripts/init-apisix-routes.sh（RS256 + 从 Logto /.well-known/openid-configuration 拉取 JWKS，2026-08-19 起唯一入口）；开发环境 gateway/.env 的 JWKS_JSON（HS256） |
| API 层 | PostgREST | 再次验签（PGRST_JWT_SECRET = JWKS_JSON）并把 claims 注入 request.jwt.claims | gateway/docker-compose.yml（env 优先） |
| 角色切换 | PostgREST | 按 JWT claim 切换 PG 角色：.pg_role（JSPath），postgrest.conf 参考文件已对齐（2026-08-19） | PGRST_JWT_ROLE_CLAIM_KEY |

说明：

- **运行态以 gateway/docker-compose.yml 为权威**：`PGRST_DB_SCHEMAS=api_v1_public`（单 schema）、`PGRST_JWT_ROLE_CLAIM_KEY=".pg_role"`、`PGRST_DB_PRE_REQUEST=""`（黑名单预请求已退役）、extra search path = api_v1_public,public、max-rows 1000、宿主 3100。gateway/postgrest/postgrest.conf 为**参考文件**（2026-08-19 已与运行态对齐：单 schema api_v1_public、jwt-role-claim-key=.pg_role、无 pre-request）；db-anon-role = "web_anon"、jwt-secret = "$(JWKS_JSON)"。
- `db/src/public/functions/logto_ts.sql` 的 `logto_ts(text)` 是 **webhook 时间戳解析器**（13 位毫秒 / 10 位秒 / ISO 字符串 → timestamptz），与 token 校验无关。
- 已知审查项（历史审查 33 号 N8/N9b，已归档）：claims 脚本的 pg_role 映射表只覆盖 role_super_admin / role_admin / role_editor / role_guest，组织角色 tenant_admin / editor / viewer 不在映射内会落到 role_guest——如需 PostgREST 侧按租户角色提权，需扩展映射（当前以代码为准，未修）。

## 3. 授权模型（角色 / 菜单 / 权限 / 数据范围）

### 3.1 数据三类（05 号文档 v2.0 定稿）

| 类别 | 数据 | 权威方 | 业务侧对象 |
| --- | --- | --- | --- |
| ① Logto 权威 | 用户、组织（租户）、组织成员、角色目录、用户↔角色分配、成员↔组织角色分配 | Logto | — |
| ② PG 镜像（只读投影） | users、tenants、user_tenants、role、organization_role、user_role | Logto（webhook / JIT / 对账） | 表在 public，写通道仅 sync_* / ensure_user / 对账 |
| ③ PG 自主 | iam_menu（菜单 + 权限点 + 端点）、iam_role_menu（绑定）、iam_role_data_scope（数据范围） | 业务 PG | 管理端经 RPC 写（带 has_permission） |

### 3.2 角色

- `role`（Logto 全局角色镜像，db/migrations/public/064_v010_mirror_tables.sql）：`role_code` 为**生成列 = name**（F20：Logto 角色名单实例全局唯一），是绑定表 join key。
- `organization_role`（Logto 组织角色镜像）：组织模板角色（如 tenant_admin / editor / viewer），与全局角色分离。
- `user_role`（分配镜像）：`organization_id = ''` 表示全局角色段，非空 = 组织角色段。

### 3.3 菜单与权限点（055 单表化，SharpFort 模型）

`iam_menu` 单表承载导航 + 权限点 + 端点信息：

| 维度 | 说明 |
| --- | --- |
| menu_type | ENUM：directory / menu / button / link（button = 权限点行；link = 外链/iframe） |
| 权限点 | button 行 `api_code` 必填（CHECK），命名空间统一 `public:*`；非 button 行 api_code 强制 NULL |
| 端点 | button 行可选 `api_url` + `api_method`（成对 CHECK；method 值域 GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS/*；api_url 非空行部分唯一索引） |
| 绑定 | 仅 `iam_role_menu`（role_code, menu_id）唯一；iam_api / iam_role_api 已随 055 删除 |
| UI 隔离 | button 行 router/component 强制 NULL（CHECK iam_menu_button_nav_null_check），不生成前端路由 |

> 一码多端点 = 多行同 api_code 的 button 行（每行一个端点）。has_permission 判定走单通道：claims roles ∩ iam_role_menu → iam_menu.api_code。

### 3.4 数据范围（DataScope）

- `scope_type` 原生 ENUM（db/src/public/types/scope_type.sql）：`all`（全部）/ `dept_and_child`（本部门及以下）/ `self`（仅本人）/ `custom`（自定义部门）。
- `iam_role_data_scope`（role_code, scope_type, dept_id, created_by）：custom 时一个角色可多行（每行一个 dept_id），非 custom 时 dept_id 必须 NULL（CHECK 保证）。
- 判定函数（读 claims + 小表，db/src/public/functions/）：
  - `current_data_scope()`：超管短路返回 all；多角色取最宽（all > dept_and_child > custom > self，RuoYi 同语义）；返回 {scope_type, dept_ids}。
  - `current_visible_dept_ids()`：把 scope 展开为可见部门 id 集合（all = 全部；custom = 指定；dept_and_child = 递归子树）。
  - `current_user_dept_id()`：查 user_profile.dept_id（SECURITY DEFINER 防 RLS 递归）。

### 3.5 会话 helper 一览

| 函数 | 数据源 | 语义 |
| --- | --- | --- |
| current_user_id() | claims sub | 当前用户 id（text，Logto nanoid） |
| current_user_roles() | claims roles | 当前角色名数组（零查询） |
| current_tenant_id() | claims organization_id | 当前租户 id（组织 token） |
| is_super_admin() | current_user_roles() @> {role_super_admin} | 超管判定 |
| require_permission(p_code) | has_permission | 无权限即 42501 |
| require_super_admin() | is_super_admin | 非超管即 42501 |

## 4. RLS 行级安全

PostgREST 把 JWT claims 注入 `request.jwt.claims`（GUC），策略直接消费（零查询）。集中清单 db/src/public/privileges/rls_policies.sql（20 个策略）：

| 表 | 策略 | 语义 |
| --- | --- | --- |
| users | users_tenant_policy | 超管 / 本人 / 同租户（经 user_profile.tenant_id） |
| tenants | tenants_read_policy | 超管 / 当前租户 / 成员可见本组织 |
| user_tenants | user_tenants_policy | 超管 / 本人 / 当前组织 |
| role | role_read_policy | 全局只读（authenticated 仅 SELECT） |
| user_profile | profile_tenant_policy | 读 = 超管/本人/同租户；写 = 超管/本人（WITH CHECK） |
| department | dept_tenant_isolation_policy | RESTRICTIVE 租户隔离 |
| iam_menu | menu_read_policy | 仅 is_active 可读 |
| iam_role_menu | role_menu_read_policy | 全局共享读 |
| audit_log | audit_log_read_policy | 超管 / 本租户 |
| dict_data / dict_type | dict_data_read_policy / dict_type_read_policy | 超管 / 全局（tenant_id IS NULL）/ 本租户 |
| ip_geolite2_city / ip_region_v4 | geolite2_read_policy / ip_region_read_policy | 全局只读 |
| login_log | login_log_read_policy | 超管 / 本租户 / 本人 |
| organization_role | org_role_select_policy | 全局只读 |
| position | position_tenant_isolation_policy | RESTRICTIVE 租户隔离 |
| iam_role_data_scope | role_data_scope_read_policy | 全局只读 |
| user_position | user_position_tenant_isolation_policy | RESTRICTIVE 租户隔离 |
| user_role | user_role_read_policy | 超管 / 本人 |
| webhook_event_log | webhook_event_log_select_policy | 仅超管（payload 含 PII） |

## 5. has_permission 与 RPC 内判定

`has_permission(p_code)`（db/src/public/functions/has_permission.sql）判定顺序：

1. 超管短路：is_super_admin() → true；
2. 从 claims roles 提取角色数组（零查询）；
3. 单通道 EXISTS：`iam_role_menu rm JOIN iam_menu m WHERE rm.role_code = ANY(roles) AND m.api_code = p_code AND m.is_active`。

三档门槛模型（05.4 定稿，035 落地）：

| 档位 | 函数形态 | 代表 RPC | 说明 |
| --- | --- | --- | --- |
| 无门槛 | SECURITY INVOKER + RLS | search_audit_log、get_dept_tree、get_audit_log_timeline | 查询类由 RLS 行级兜底 |
| 权限点 | SECURITY DEFINER + require_permission('public:xxx') | rpc_create_menu、rpc_update_config、rpc_set_role_menus 等 21+ CRUD | 写/管理操作 |
| 超管 | SECURITY DEFINER + require_super_admin() | rpc_list_cron_jobs、rpc_replay_webhook_event、rpc_list_webhook_events | 平台级运维 |

权限点前缀统一 `public:*`（055 D11 收敛，如 public:menu:create / public:data-scope:bind / public:config:write / public:import / public:login-log:list）。完整映射见 db/api_v1/public/rpc/ 下各文件与 iam_menu seed。

> 已知遗留：db/api_v1/public/rpc/rpc_set_role_data_scope.sql 的 role 存在性检查仍引用已删除的 iam_role_api 表（055 单表化后该表不存在），运行时可能报 42P01——以 055 迁移与 db/tests/public/05_rls_test.sql 为准，属待修项（TODO）。

## 6. webhook 同步（Logto → PG 单向）

接收端 `api_v1_public.webhook_logto(payload jsonb)`（db/api_v1/public/rpc/rpc_webhook_logto.sql，GRANT EXECUTE TO web_anon），按 event 分发。入口路由为 `POST /rpc/webhook_logto`（scripts/init-apisix-routes.sh：无 jwt-auth，serverless-pre-function 做 HMAC-SHA256(rawBody) 验签，缺 LOGTO_WEBHOOK_SIGNING_KEY 时 fail-closed；2026-08-19 起为唯一部署链入口）：

| Logto 事件 | 调用的同步函数 | 镜像表 |
| --- | --- | --- |
| User.Created / User.Data.Updated | sync_user_upsert | users |
| User.Deleted | sync_user_delete（硬删，FK CASCADE 清理档案/分配） | users |
| User.SuspensionStatus.Updated | sync_user_suspension | users.is_suspended |
| Organization.Created / Organization.Data.Updated | sync_tenant_upsert | tenants |
| Organization.Deleted | sync_tenant_delete（先解绑 user_profile.tenant_id） | tenants |
| Organization.Membership.Updated | sync_membership_delta（addedUserIds / removedUserIds 增量） | user_tenants |
| OrganizationRole.Created / Data.Updated / Deleted | sync_organization_role_upsert / _delete | organization_role |
| Role.Created / Data.Updated / Deleted | sync_role_upsert / sync_role_delete | role |
| PostSignIn | sync_login_log_write | login_log |

可靠性设计：

- 每个事件先落 `webhook_event_log`（received），处理后置 success / error / ignored（未知事件）；写入失败不阻断（N6）。
- sync_* 均幂等（ON CONFLICT），镜像表以 `logto_updated_at` 做乱序守护（N18：仅当新值 ≥ 现值才覆盖）。
- 用户↔角色分配在 Logto 无 webhook 事件（F13/F21）→ 由登录 JWT 携带的 claims 经 `api_v1_public.ensure_user()` JIT 覆盖（global_roles / org_roles 分段精确对齐）。
- 每日对账：scripts/phase2/reconcile-logto.py（部署机 crontab `0 3 * * *`），Management API 拉全量 → sync_*（幂等），兜底丢事件/存量污染。
- 重放：rpc_list_webhook_events（超管分页查询）+ rpc_replay_webhook_event（超管按 id 重放 payload，并记 log_operate）。

## 7. 从 casbin 吸收了什么、放弃了什么

**吸收（保留为数据模型/思路，非运行时引擎）：**

| 吸收点 | 现状落点 |
| --- | --- |
| RBAC 数据模型（角色 → 资源绑定） | iam_role_menu（单表化后）+ iam_menu.api_code |
| casbin_rule 扁平策略视图思想 | 已随 2026-08-20 兼容视图清理移除（不再借鉴 Casbin 模型）；授权数据以 iam_role_menu → iam_menu 为准 |
| Role-in-JWT 优化（用户数退出授权路径） | roles claim 注入，授权判定零用户查询 |
| role_code 作为策略主体（v0） | role.role_code 生成列 = Logto 角色名，绑定表 join key |

**放弃（退役组件/表）：**

| 放弃项 | 说明 |
| --- | --- |
| Casdoor / casbin 网关引擎（authz-casbin） | 网关只做 jwt-auth 验签 + 路由；授权判定下沉 PG（05 号文档 §10） |
| Go PolicySyncer / syncer | webhook 同步全部在数据库内完成（sync_* 函数）；无 Go 服务、无 pg_notify→etcd 管道 |
| iam_api / iam_role_api 双表 + 双通道 | 055 单表化：权限点与端点内嵌 iam_menu button 行，has_permission 单通道 |
| sys_token_blacklist / sys_user_session / check_token_blacklist | D12：会话与吊销交 Logto（refresh token revocation）；PGRST_DB_PRE_REQUEST 清空 |
| user_login_sso / refresh_token_rtr（password grant 遗留） | Logto 无 password grant 路径，RPC 已删除 |
| 应用自签 JWT（generate_rs256_jwt 等） | JWT 由 Logto 签发（RS256 + JWKS / 开发 HS256） |

## 8. 用户-角色-组织 membership 同步

```text
Logto（权威）                        PostgreSQL 镜像
  │ 角色目录 Role.* 事件 ─────────────▶ role（sync_role_upsert/delete）
  │ 组织 Organization.* 事件 ─────────▶ tenants（sync_tenant_upsert/delete）
  │ 成员 Membership.Updated 增量 ─────▶ user_tenants（sync_membership_delta）
  │ 组织角色 OrganizationRole.* ──────▶ organization_role
  │ 用户↔角色分配（无事件） ────────────▶ user_role（登录 JIT：ensure_user 按 claims
  │                                      global_roles/org_roles 分段精确对齐）
  │ 登录 PostSignIn ──────────────────▶ login_log（sync_login_log_write）
  └ 每日对账 reconcile-logto.py ──────▶ 全量 diff → sync_*（兜底）
```

要点：

- **user_role 镜像不进授权路径**：授权判定读 claims；镜像只服务管理端展示，允许分钟级延迟。
- user_role 删除随 users / role 镜像 FK ON DELETE CASCADE 清理（064 迁移）。
- sync_tenant_delete 先把该租户下 user_profile.tenant_id 置 NULL（RESTRICT FK 前置），再删 tenants。
