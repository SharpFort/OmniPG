## 2. §2 模板选择决策树——业界最佳实践评估

### 2.1 总体评价

决策树框架（按表性质分类 → 审计模板）本身符合 ABP/EF Core 审计惯例，分类维度（系统级/审计日志/配置/关联/日志/视图/核心业务/只读缓存）覆盖了多数场景。**主要不足**：① 与现库架构脱节（本次已随表名更新修复）；② 缺「IdP 镜像表」「静态参考数据」两个现库真实存在的表类分支；③ 若干业界惯例（软删部分唯一索引、append-only 防护、配置审计强化）未写入树中，新表建表时容易漏。

### 2.2 发现清单（B1-B8，未应用，待裁决）

**B1（建议新增分支）缺「IdP 镜像表」分支** ⭐
- **现状**：users / tenants / role / organization_role / user_tenants 由 Logto webhook 同步写入，树中无对应分支——按现树会被归入「核心业务表 → 模板 10」，但现库 role/organization_role 只有 created_at/updated_at + logto_updated_at（模板 4）。
- **业界依据**：外部系统同步的镜像表，写入者是系统而非用户，`_by` 无用户语义；审计重点是**同步时间戳**（synced_at/logto_updated_at）与**事件来源**（webhook event）。users/tenants 带全套 _by 是历史产物，不必在新镜像表照搬。
- **建议**：新增分支「镜像/同步表 → 模板 4（created/updated）+ logto_updated_at 同步元数据；_by 按需由同步函数填充」。

**B2（建议升级）配置/字典表：可选 → 推荐模板 6** ⭐
- **现状**：树写「⚠️ 可选：模板 1 或模板 6」；现库 app_config 实际只有 created_at/updated_at（模板 4，无 _by）。
- **业界依据**：配置变更属安全敏感操作（配置篡改是常见攻击面，等保/SOC2 要求配置变更可追溯）。ABP 自身对 Setting/配置类也支持 audited entity。
- **建议**：树中升级为「推荐模板 6」；同时考虑给 app_config 补 created_by/updated_by（需前端/触发器配合）。

**B3（建议独立分支）静态参考数据表**
- **现状**：ip_geolite2_blocks/city/locations、ip_region_v4 存在但树中无分支（本次暂并入「只读/缓存」分支）。
- **建议**：独立分支「静态参考数据（外部导入）→ ❌ 无审计，审计在数据源/导入流程」。

**B4（建议补注释）软删 + 唯一约束 → 部分唯一索引** ⭐
- **现状**：模板 7-10 与决策树均未提；现库 department.dept_name、position.pos_code 等将来加唯一约束时必然踩坑（删除后无法重建同名/同码）。
- **业界依据**：deleted_at 软删模式下的标准做法：`CREATE UNIQUE INDEX uq_xxx ON t(col) WHERE deleted_at IS NULL;`
- **建议**：在模板 7-10 或 §7 查询辅助中加此注释/示例。

**B5（建议补注释）日志/事件表 append-only 防护**
- **现状**：树只说「无需审计字段」；现库 audit_log / login_log / webhook_event_log 已实现「仅 SELECT 策略 + SECURITY DEFINER 写入」，但树未写明，新表容易漏掉。
- **建议**：该分支补一句「业务角色 REVOKE UPDATE/DELETE，写入走 SECURITY DEFINER 函数」。

**B6（建议补注释）关联表实现细节**
- **业界惯例**：复合主键（避免无意义代理键）、硬删不软删、无 updated_at 触发器、按需加 tenant_id。现库 user_role / user_tenants / user_position 均符合。
- **建议**：分支下补一行实现约定。

**B7（建议补注释）审计日志表自身治理**
- **现状**：audit_log 是全库增长最快的表；已有 idx_audit_logtype/tenant/user/operation/created 查询索引，无分区/归档策略说明。
- **业界依据**：审计日志需保留策略（保留 N 月）+ 按时间分区/归档，防止单表膨胀拖垮查询。
- **建议**：该分支补「追加保护 + 分区/归档策略」一句（治理方案另文）。

**B8（可选提示）created_at 默认值语义**
- `now()` = 事务开始时间（审计字段行业惯例，OK）；日志表如需行级精确时间可用 `clock_timestamp()`。仅作提示，无需改动。

### 2.3 决策树优化建议版（若批准 B1-B8，v4.5 候选）

```
新建数据库对象需要审计字段吗？
│
├── 系统级表（cron_job_log）
│   └── ❌ 无（系统任务写入，无用户上下文）
├── 审计日志表（audit_log）
│   └── ❌ 无（自身即审计）；追加保护 + 分区/归档策略
├── 静态参考数据表（ip_geolite2_* / ip_region_v4）
│   └── ❌ 无（外部导入，审计在数据源）
├── IdP 镜像/同步表（users / tenants / role / organization_role / user_tenants）
│   └── ⚠️ 模板 4 + logto_updated_at 同步元数据（_by 由同步函数按需填）
├── 配置/字典表（app_config / dict_type / dict_data）
│   └── ✅ 推荐模板 6（配置变更安全敏感，须可追溯修改者）
├── 关联表（user_role / iam_role_menu / user_position / iam_role_data_scope）
│   └── ⚠️ 模板 1；复合主键、硬删、无 updated_at 触发器
├── 日志/事件表（login_log / webhook_event_log）
│   └── ⚠️ 模板 1；REVOKE UPDATE/DELETE，写入走 SECURITY DEFINER
├── 视图（VIEW）
│   └── ❌ 无（审计字段在基表）
├── 核心业务表（department / position / user_profile）
│   └── ✅ 模板 10 ⭐⭐；软删 + 唯一约束用部分唯一索引（WHERE deleted_at IS NULL）
└── 只读/缓存表（物化视图、缓存表）
    └── ❌ 无（审计在源表）
```

## 3. 顺带发现（本次未改动，待裁决）

**D1（P1）文档头代码路径漂移**：文档头称 `db/src/public/templates/audit_fields.sql`——该目录实际为空；5 个函数实际在 `db/src/public/functions/audit_*.sql`（存在 ✓）。建议修正文档头指向。

**D2（P1）§0.1 函数 2/3/4 与现库脱节（文档与实现的实质矛盾）**：
- 现库**无任何表**绑定 audit_user_fields() / audit_deletion_user() / audit_created_at()（全库触发器实测：生产审计链是 `audit_trigger_func('tenant_aware')` + `write_audit_log` → audit_log，§6 触发器章节同样未提这条真实链路）。
- 这三个函数写入 `current_user_id()`（现返回 **text**，Logto id），而模板字段定义为 `created_by UUID` → **按 §4 模板建新表并绑这些触发器会类型不匹配**。
- 现库 `_by` 类型本身分裂：department/audit_log 为 uuid，其余（dict_data/dict_type/iam_menu/position/users/tenants/user_profile 等）为 text。
- **需用户裁决方向**：A) 模板整体改 TEXT（对齐 Logto id 现实，推荐）；B) 保留 UUID 模板 + 函数改写入 uuid 转换；C) 模板双轨（uuid 系表 vs 镜像系表）。

**D3（P2）§5 字段类型对照表漂移**：`CreatorId/LastModifierId/DeleterId → UUID` 与现库主流 text 不符（同 D2，随 D2 裁决联动）。

**D4（P2）§7.4 数据质量检查 SQL 结构错误**：`SELECT table_name, column_name, ... FROM department GROUP BY table_name, column_name` 不可执行（department 无这两列）；本次仅按任务要求改表名，结构问题未动。正确写法应为基于 information_schema.columns 的目录查询或对指定表逐列检查。
