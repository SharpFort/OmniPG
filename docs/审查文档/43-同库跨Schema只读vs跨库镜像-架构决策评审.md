# 43 架构决策评审：同库跨 Schema 只读（认证数据与 Admin 绑定）vs 跨库 Webhook 镜像

> **状态**：✅ 评审完成（2026-08-21）。与认证选型（Logto/Zitadel/better-auth）无关，回答纯架构问题
> **评审问题**：
> ① 业务数据与"用户认证与授权数据"同库、跨 schema 只读，且认证数据与 OmniPG Admin 永久捆绑，其他模块未来迁服务器——这是不是未来严谨的最佳方案？
> ② 是否比目前"跨库 webhook 镜像用户/角色/租户"的方案更好？
> ③ "Admin 只读认证数据、认证保持唯一来源"是不是最好的方案？
> **一句话结论**：**是。同库跨 schema 只读在一致性、运维、维护面上全面优于 webhook 镜像；"Admin 只读 + 认证唯一权威"是正确原则，且应把它提升为架构铁律。唯一要修正的措辞是"永久捆绑"——应理解为"Admin 模块与认证库同生命周期（强内聚）"，而其他模块的迁移自由恰恰由"只读走 API、不授直读"来保证，同库方案不会锁死它们。** 但"严谨"成立需要满足 §6 的 7 个条件（不是无条件的）。

---

## 1. 三个问题的直接回答

| 问题 | 回答 |
|---|---|
| ① 同库跨 schema 只读 + Admin 捆绑认证库，是未来严谨的最佳方案吗？ | ✅ **是严谨方案，且优于镜像**。前提 = §6 的 7 个条件（唯一权威、只读走安全视图、其他模块走 API、故障域治理等）。注意"捆绑"只发生在 Admin 模块——它与认证数据本就强内聚（它就是管用户/角色/租户的模块） |
| ② 比跨库 webhook 镜像更好？ | ✅ **明显更好**。镜像方案在本仓库已有实锤缺陷：33 号记录 3 条 P0 失效链路（用户/角色/组织删除 webhook 全部失效）、"用户-角色分配无事件可订阅"的**唯一权威通道缺口**、5000 截断错误、对账缺失导致的漂移；同库只读把这些机制全部删除（§4/§5） |
| ③ Admin 只读、认证保持唯一来源，是最好的方案吧？ | ✅ **对，这是核心原则**（单一事实来源，Single Source of Truth）。同库只读是这一原则的最佳物理实现：读 = 跨 schema 安全视图（强一致、零延迟）；写 = 仍走认证服务的 API/Console（Admin 不直接写认证表），唯一权威完整保留 |

---

## 2. 评判框架：一条好的认证-业务数据关系长什么样

1. **唯一权威**：认证数据只有认证服务一个写入者；其他方零写路径；
2. **一致性**：读到的用户/角色/租户与认证实际状态零延迟、零漂移；
3. **故障域**：认证异常不放大成业务库数据面故障（或放大面可控）；
4. **演进自由度**：未来其他模块迁服务器时，不被物理存储锁死；
5. **维护面**：同步链路、对账、重放、乱序守护等机制越少越好；
6. **安全**：敏感列（密码散列等）绝不越过只读边界。

---

## 3. 两方案对比

| 维度 | 现状：跨库 webhook 镜像 + 对账 | 提议：同库跨 schema 只读 |
|---|---|---|
| 一致性 | 最终一致，靠 webhook/JIT/对账三层补救 | **强一致**（同库事务可见性） |
| 数据源 | 镜像表是"复制品"，与权威可能漂移 | 安全视图直读权威表，**无第二副本** |
| 同步链路 | 15 事件订阅 + sync_* 15 函数 + 重放 RPC + reconcile 对账 + JIT ensure_user 双写 | **全部退役**（37 号 D2 对拍后可删） |
| 已知缺陷面 | 33 号：3 条 P0 失效链路、分配无事件（唯一权威通道缺口）、截断 bug、写路径残留 | 无此机制，无此缺陷面 |
| 延迟 | 用户-角色分配仅登录 JIT，admin 展示有延迟（37 号 D5） | 零延迟 |
| 备份/PITR | 两库两个备份，时间点难对齐（对账不一致风险） | **单库一份 PITR，认证+业务天然同点恢复** |
| 故障域 | 认证库故障不影响镜像读（唯一优势） | 认证库=业务库，实例级故障同挂；但业务本就需要认证服务（JWT 验签），**服务面依赖早已存在**，新增的只是存储面共享 |
| 资源 | 两库 + 同步流量 + 对账全量拉取 | 单库，省资源；需治理锁/连接竞争（§7） |
| 迁移自由度 | 镜像表随业务库，认证库独立可迁 | 认证 schema 随 admin 库；**其他模块迁出不受影响（走 API）** |

## 4. 镜像方案的固有代价（本仓库实证，不是理论风险）

33 号审查（2026-08-10）已记录：`User.Deleted / Organization.Deleted / Role.Deleted` 三条删除同步链路**全部失效（P0）**；组织角色事件未订阅；封禁事件未订阅；**用户-角色分配在 Logto 无事件可订阅**——镜像只能靠"登录 JIT 兜底"，这正是 37 号 D5 承认的"admin 展示延迟"根因；另有 5000 截断处理错误、镜像表被 PostgREST 自动暴露写方法等"侥幸安全"问题。结论是：**镜像方案的复杂度是买来的、且买来的不是一致性，只是物理隔离**。当物理隔离不是硬需求时，这套机制是纯负债。

---

## 5. 同库只读方案的收益清单

1. 退役 `sync_*` 15 个函数、`rpc_webhook_logto` 数据分支、`reconcile-logto.py` 主体、`ensure_user` 镜像写入段、webhook 15 事件订阅（保留 PostSignIn 登录日志按 D6/D7 决策）；
2. 退役乱序守护（N18 `logto_updated_at`）、对账全量拉取、重放 RPC——**维护面下降一个数量级**；
3. 业务 FK 可跨 schema 直挂认证表（PG 支持），删除/改名即级联一致；
4. 单库备份 + PITR = 认证与业务**同一时间点恢复**（镜像方案做不到）；
5. 前端 admin 页面零延迟展示角色/租户变更。

---

## 6. "严谨成立"的 7 个条件（缺一则退回镜像或补设计）

1. **唯一权威铁律**：认证 schema 仅认证服务可写；Admin 的写操作一律转发认证 API（不直接 INSERT/UPDATE 认证表）；DB 层用 `REVOKE` 兜底（仅认证用户持有 DML，其余角色零写权限）。
2. **只读走安全视图**：跨 schema 直读只允许 `SECURITY DEFINER` 视图（owner = app_owner），列级授权，**排除密码散列/token 类敏感列**；禁止向任何业务角色授认证表裸 SELECT（38 号 §2.6 敏感列清单）。
3. **其他模块走 API**：只有 Admin 模块持有直读视图权限；其他模块（未来迁服务器的）一律走 PostgREST API 读用户/角色——**这一条同时保住了迁移自由度**。
4. **故障域治理**：业务连接与认证连接分离（pgBouncer 池隔离、statement_timeout），认证升级 DDL 走低峰窗口 + 回归门（38/40 号）；监控同库锁等待。
5. **容量治理**：认证日志/会话类表分区 + 清理策略，避免拖垮共用实例。
6. **审计**：直读视图调用路径全部可审计；升级后跑 38 号 §3.7 断言门。
7. **明确定义"捆绑边界"**：捆绑 = Admin 模块与认证库同生命周期；**其他模块不在捆绑范围内**，架构文档显式声明。

---

## 7. 残余风险与治理（诚实清单）

| 风险 | 等级 | 治理 |
|---|---|---|
| 同实例故障域耦合（认证存储故障 = 业务存储故障） | P1 | 单实例高可用（Pigsty/Patroni）+ 备份演练；服务面耦合本就存在，新增仅为存储面 |
| 认证高频写/大表与业务抢锁抢 IO | P2 | 连接池隔离、statement_timeout、日志表分区清理、监控 |
| 认证软件升级 DDL 锁影响业务 | P1 | 低峰窗口 + 升级回归门（38/40 号）+ 演练 |
| 直读视图误授/敏感列泄漏 | P0 | §6 条件 2/6 + 38 号 §3.7 断言门（has_table_privilege 检查） |
| 未来 admin 模块本身要拆出迁移 | P3 | 届时 admin 与认证库同迁（本就要一起），或退回 API 读取 |

---

## 8. 结论

- **同库跨 schema 只读 > 跨库 webhook 镜像**：一致性、维护面、备份一致性全面胜出；镜像方案的唯一优势（物理隔离）在"业务已依赖认证服务"的前提下价值有限。
- **"Admin 与认证库绑定"是正确架构**：Admin 就是认证数据的管理面，强内聚；**"永久捆绑"的担忧应转化为 §6 条件 3**——用"只读仅限 Admin 视图、其他模块走 API"来保证未来迁移自由，而不是靠镜像表解耦。
- **"Admin 只读 + 认证唯一来源"是应写入项目总纲的架构铁律**：同库只是它的物理实现；无论未来认证选型如何变（Logto/Zitadel/better-auth），这条铁律不变——认证服务独占写、Admin 经安全视图只读、其他模块经 API 读取。
