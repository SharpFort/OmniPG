## 2. 需求合理性分析

用户设想：每版本若干迁移 → 发布时合并移除中间态 → 新版本继续新增 → 再发布再合并。

**判定：合理，且与业界主流实践一致。** 逐点对照：

| 用户的设想 | 业界对应实践 | 一致性 |
|:---|:---|:---|
| 发布时合并、移除中间态 | Flyway 官方 "Resetting the baseline"；Prisma 官方 "Creating a clean history in a production environment" | ✅ 一致 |
| 合并对象 = 全库终态单文件 | Flyway Baseline Migrations（`B` 前缀累积迁移，官方：*"a single, cumulative migration that represents the state of your database"*）；Prisma `migrate diff --from-empty` | ✅ 一致 |
| 新版本继续追加迁移 | 所有工具的通用版本化模型 | ✅ 一致 |
| "移除中间态"的时机 | Django 官方建议**两阶段**：squash 保留旧文件 → 发布 → 等全部环境升级 → 删旧文件 → 二次发布 | ⚠️ 本项目仅单开发库，可一步到位，但建议 git tag 兜底（见 D2） |

两处修正建议：
1. **"合并" ≠ "手工拼接 62 个文件"**。62 个文件含大量互相覆盖/撤销的中间态（014/016 RENAME、027 schema pivot、055 单表化、035/037/051 的 CREATE OR REPLACE 覆盖链……），且有历史 bug 文件（024/035 含 NUL 字节、021 jsonb 列访问、003 引用已删表、040 用已改名旧列）。手工拼接等于"模拟执行 62 轮 DDL"，工作量巨大且大概率产出跑不通的脚本。业界（Prisma/Flyway/dbmate）一律**工具生成**。
2. **版本账本修复是 squash 的一部分**，不只是删文件。`schema_migrations` 的脱节状态（只记 001–005）正好在这次一并收敛。

## 3. 业界最佳实践核实（一手来源）

### 3.1 dbmate（本项目所用工具）
来源：https://github.com/amacneil/dbmate （README main 分支）+ 源码 `pkg/dbmate/db.go`

- **`dbmate dump`**：官方 —— *"write the database schema.sql file … The schema.sql file will contain a complete schema for your database, even if some tables or columns were created outside of dbmate migrations."*
- **schema.sql 用途**：官方 —— *"You can use the schema file to quickly restore your database without needing to run all migrations."*
- **schema_migrations 只存版本号**：官方 —— *"When you apply a migration dbmate only stores the version number, not the contents"*。
- **源码实证（对方案 B 最关键）**：`FindMigrations()` 只扫描迁移文件目录，把"文件版本 ∈ schema_migrations"标记为 Applied；**schema_migrations 中多余的记录（对应文件已删）被完全忽略，不报错不告警** → **删除 001–063 旧文件对存量库安全**。`Migrate()` 不自动 load schema.sql（需 `dbmate load` 手动）。
- **对本项目的含义**：dbmate 没有 baseline 命令，squash = "新 baseline 迁移文件（幂等）+ 存量库账本收敛"，删除旧文件无任何副作用。

### 3.2 Flyway
来源：https://flywaydb.org/documentation/command/baseline （现重定向至 red-gate 文档站；源码仓库 flyway/flywaydb.org）

- **baseline 命令**：官方 —— *"Baselines an existing database, excluding all migrations up to and including baselineVersion."*
- **Reset baseline 官方定位**：官方 —— *"When you have many migrations, it might be desirable to reset your baseline migration. This will allow you to reduce the overhead of dealing with lots of scripts, many of which might be old and irrelevant."*
- **Baseline Migrations（累积迁移，Teams 版）**：官方 —— *"you might wish to add a single, cumulative migration that represents the state of your database after all of those migrations have been applied without disrupting existing environments … New environments will choose the latest baseline migration as the starting point."*（`B` 前缀，如 `B5__my_database.sql`；与 `baseline` 命令是两个不同机制）
- **对本项目的含义**：用户设想 = Flyway 官方两条路线的合集（baseline 标记存量库 + 累积迁移引导新库）。dbmate 无 `B` 前缀机制，用"幂等 baseline 迁移"等价实现。

### 3.3 Django
来源：https://docs.djangoproject.com/en/5.2/topics/migrations/#migration-squashing

- 官方 squash 定义：*"Squashing is the act of reducing an existing set of many migrations down to one (or sometimes a few) migrations which still represent the same changes."*
- 官方推荐流程（**两阶段发布**）：*"squash, keeping the old files, commit and release, wait until all systems are upgraded with the new release … and then remove the old files, commit and do a second release."*
- **对本项目的含义**：单开发库可一步到位；若未来有 staging/prod 多环境，改用两阶段。

### 3.4 Prisma
来源：https://www.prisma.io/docs/orm/prisma-migrate/workflows/squashing-migrations

- 官方场景 2 "Creating a clean history in a production environment"：*"the decision is made to squash the whole history into a single migration … the team is not deriving value from the migration steps (and could get them back from version control history in a pinch)"*——与本项目现状逐字吻合。
- 官方做法：`migrate diff --from-empty --to-schema prisma/schema.prisma` 生成单文件 SQL → 清空旧迁移目录放入新文件 → 存量库 `migrate resolve --applied <新迁移名>` 标记已应用（不执行）。
- **对本项目的含义**：反写 baseline 的等价物是 pg_dump/PGlite 导出终态；存量库用"INSERT schema_migrations 版本号"等价于 `migrate resolve`。

### 3.5 Pigsty
来源：https://pigsty.io/docs/pgsql/migration/ （官方文档，Vonng/pigsty.io 仓库）

- 官方 Migration 文档主题是 **"How to migrate existing postgres into Pigsty-managed cluster with minimal downtime"**——逻辑复制/蓝绿**数据迁移** playbook（`pgsql-migration.yml`）。
- **核实结论：Pigsty 不提供、也不建议任何 schema 版本迁移方案**（它管集群生命周期与自身 CMDB schema，后者用 pigsty.yml 声明式幂等管理）。应用 schema 演进完全交给应用侧工具（dbmate 等）——本项目现状正是如此，无冲突。

### 3.6 其他佐证
- Atlas（ariga）提供 `atlas migrate squash` 命令（一次性 squash 版本化目录），同一趋势的又一实例。
- golang-migrate/Rails（squasher gem）等生态均有社区标准 squash 工作流。

## 4. 方案对比：A 手工合并 vs B 反写 baseline

| 维度 | A：手工合并 62 个文件 | B：从库反写（**推荐**） |
|:---|:---|:---|
| 语义正确性 | 低。62 文件含大量互相覆盖/撤销的中间态（RENAME、DROP、pivot、CREATE OR REPLACE 覆盖链），拼接≈模拟执行 | 高。库 = 2026-08-15 审计追平终态（含 062/063 最新变更），导出的就是已验证可用状态 |
| 已知文件缺陷 | 需逐一带入（024/035 NUL 字节、003 引用已删表、040 旧列名、down 段干扰） | 天然绕过（不读旧文件） |
| 工作量 | 巨大（手工追踪 62 轮 DDL 的净效果） | 小（导出 + 修剪白名单，半自动化） |
| 业界对标 | 无工具采用此路线 | Prisma `migrate diff --from-empty`、Flyway 累积迁移、dbmate dump 的官方路线 |
| 17 号铁律合规 | 需从每个文件手工剔除代码对象段 | 导出时白名单只取表结构+数据即可 |
| 可验证性 | 拼完才知道对不对 | 可在临时库/PGlite 先重建验证再落库 |

**判定：B。** 用户直觉（"反写"）与官方工具路线一致。

## 5. 推荐方案 B 执行骨架（2026-08-16 用户拍板 D1–D5 后修订版，未执行）

**最终交付 = 3 个独立迁移文件**（用户拍板：表结构/种子数据分离 + 镜像表单独成文件）：

| 文件 | 内容 | 顺序依据 |
|:---|:---|:---|
| `064_v010_mirror_tables.sql` | IdP 镜像/绑定表结构：users、tenants、role、organization_role、user_tenants、user_role（共 6 张） | FK 依赖：user_profile/user_position/user_role 等业务表 FK → users/tenants/role，镜像必须先建 |
| `065_v010_baseline.sql` | 业务表结构：department、position、user_profile、user_position、iam_menu、iam_role_menu、iam_role_data_scope、dict_type、dict_data、app_config、audit_log、login_log、cron_job_log、webhook_event_log、ip_geolite2_city/blocks/locations、ip_region_v4（共 18 张；不含 schema_migrations——由 dbmate 自建） | 依赖 064 的镜像表 |
| `066_v010_seed_data.sql` | 种子数据（data-only）：app_config(14)、dict_type(2)、dict_data(9)、iam_menu(55) | 依赖 064/065 的表；**排除**镜像表数据（IdP webhook 同步）、业务运行时数据（audit_log 417/login_log 72/webhook_event_log 20/department 1/user_profile 3/iam_role_menu 98 等均不入库） |

dbmate 按文件名排序应用 064→065→066，FK 依赖天然满足。

执行步骤：
1. **导出镜像表结构**：`pg_dump --schema-only --no-owner --no-privileges -t users -t tenants -t role -t organization_role -t user_tenants -t user_role` → 修剪（去 COMMENT/GRANT 噪音、DDL 改幂等形态 `IF NOT EXISTS`）→ 064。
2. **导出业务表结构**：`pg_dump --schema-only` 白名单 18 张业务表 → 同法修剪 → 065。
3. **导出种子数据**：`pg_dump --data-only --column-inserts`（或 COPY 形态）app_config/dict_type/dict_data/iam_menu → 幂等化（ON CONFLICT DO NOTHING 或按项目 042/046 惯例）→ 066。
4. **合规审查（17 号铁律）**：三文件只含表结构+数据；函数/视图/触发器/枚举/RLS/GRANT 一律不出现（归 src/api_v1/init，由 apply-src 部署）；枚举由 bootstrap 的 src types 前置创建。
5. **删旧文件**：`git rm` 001–063（62 个文件）——dbmate 源码证实存量库零副作用。
6. **账本收敛（D5 拍板）**：存量库 `DELETE FROM schema_migrations; INSERT INTO schema_migrations VALUES ('064'),('065'),('066');`；新库走 `bootstrap → dbmate up → apply-src` 自然登记。
7. **打 tag（D2 拍板）**：`git tag v0.1.0`（tag 内含 62 个历史迁移，随时可取回）。D4 分支改名**暂缓**，等用户指令。
8. **验证**：临时库跑完整部署链（bootstrap → dbmate up → apply-src）→ 幂等双跑 → `make test`（WSL + PGPASSWORD）+ e2e → 存量库 `dbmate status` 干净 + `NOTIFY pgrst, 'reload schema'`。另将 db/schema.sql 占位文件替换为真实 `dbmate dump` 产物。

## 6. 风险与注意

1. **apply-src 会重放新 baseline**（§1.4）→ 064/065/066 必须幂等，且双跑验证（技能 Phase 7 惯例）。
2. **17 号铁律**：三个文件只含表结构 + 数据；代码对象继续归 src/api_v1。若 pg_dump 混入函数/视图/触发器，修剪时必须剔除（用扩展排除查询 + schema 白名单）。
3. **062/063 终态必须包含**：department `_by` uuid→text、audit_log.created_by 删除、inventory/sales schema 退役（DROP 不进入 baseline——反写的是"退役后"终态，天然正确）。
4. **种子 vs 运行时数据**：镜像表（users/tenants/role…）现库有 webhook 同步数据，**不能**进 baseline；只取权限目录/字典/配置类种子。
5. **060 教训**：`CREATE TABLE IF NOT EXISTS` 型迁移在存量库静默跳过——若未来某表结构再漂移，手工追平仍需手工 ALTER；baseline 重建路径可缓解此问题（新库永远从 064/065/066 起）。
6. **编号历史**：045/046 双文件、缺 007/008/054 的编号不连续——squash 后消失，不影响 dbmate（按文件名排序，版本号仅用于账本比对）。
