# OmniPG 部署配置问题诊断与解决方案

> **日期**: 2026-07-31  
> **环境**: WSL2 Ubuntu 26.04 + Docker Desktop + Pigsty v4.4.0  
> **项目路径**: `D:\WeChat Files\OmniPG`

---

## 问题 #1: APISIX 配置意见 — 仅安装网关，移除 APISIX API 等服务

### 现象

APISIX 应仅作为网关（data plane）运行，不安装 Admin API 等服务。当前配置中：
- `setup_apisix.sh` 尝试通过 Admin API (端口 9180) 配置插件
- `syncer` 服务尝试通过 Admin API 动态更新 Casbin 策略

### 根因分析

APISIX standalone 模式（`config_provider: yaml`）下：
- **Admin API 不可用**（官方设计如此，见 [APISIX 部署模式文档](https://apisix.apache.org/docs/apisix/deployment-modes/#standalone)）
- 路由配置通过 `apisix.yaml` 静态加载
- 插件元数据（如 Casbin model/policy）通过文件挂载，不通过 Admin API

当前代码中的问题：

1. **`scripts/setup_apisix.sh`** 使用 Admin API：
   ```bash
   APISIX_ADMIN_URL="${APISIX_ADMIN_URL:-http://localhost:9180}"
   curl -s -X PUT "${APISIX_ADMIN_URL}/apisix/admin/plugin_metadata/authz-casbin" ...
   ```

2. **`gateway/docker-compose.yml` 中 syncer 服务** 使用 Admin API：
   ```yaml
   syncer:
     environment:
       APISIX_ADMIN_URL: http://apisix:9080/apisix/admin/plugin_metadata/authz-casbin
   ```

### 解决方案

#### 方案 A：保持 Standalone 模式（推荐）

**优点**：无 etcd 依赖，配置简单，适合单机部署  
**缺点**：路由变更需重启 APISIX

修改如下：

1. **删除 `setup_apisix.sh` 中的 Admin API 调用**，改为验证文件挂载：
   ```bash
   #!/bin/bash
   echo "=== APISIX Standalone 模式配置验证 ==="
   echo "路由由 apisix.yaml 静态加载，无需 Admin API"
   echo ""
   echo "[1/2] 验证 Casbin 配置文件..."
   if [ -f "../gateway/apisix/casbin_rule" ]; then
       echo "  ✅ casbin_rule 文件存在"
   else
       echo "  ❌ casbin_rule 文件不存在"
   fi
   echo ""
   echo "[2/2] 验证 JWKS 路由..."
   echo "  JWKS 由 apisix.yaml 中的 /well-known/jwks 路由提供"
   echo ""
   echo "=== 配置验证完成 ==="
   ```

2. **修改 syncer 服务**，改为写入 `casbin_rule` 文件而非调用 Admin API：
   ```yaml
   syncer:
     build:
       context: ../db/syncer
       dockerfile: Dockerfile
     container_name: policy-syncer
     restart: unless-stopped
     networks:
       app-net:
         ipv4_address: 172.20.0.7
     environment:
       DB_HOST: pgbouncer
       DB_PORT: "6432"
       DB_USER: app_owner
       DB_PASSWORD: dev_password_change_me
       SSL_MODE: disable
       # 改为写入文件模式
       CASBIN_RULE_FILE: /shared/casbin_rule
     volumes:
       - casbin_rule:/shared
     depends_on:
       - pgbouncer
   
   volumes:
     casbin_rule:
       driver: local
   ```

3. **APISIX 挂载 casbin_rule 卷**：
   ```yaml
   apisix:
     volumes:
       - casbin_rule:/usr/local/apisix/conf/casbin_rule:ro
   ```

#### 方案 B：切换为 Traditional 模式（需要 etcd）

**优点**：Admin API 可用，动态配置  
**缺点**：需要运行 etcd，增加复杂度

```yaml
# docker-compose.yml
apisix:
  image: apache/apisix:3.17.0-debian
  environment:
    APISIX_STAND_ALONE: "false"  # 关闭 standalone
  depends_on:
    - etcd

etcd:
  image: bitnami/etcd:3.5
  environment:
    ALLOW_NONE_AUTHENTICATION: "yes"
  ports:
    - "2379:2379"
```

**建议**：Phase 1 单机环境推荐方案 A，保持简单；Phase 2 生产环境可考虑方案 B。

## 问题 #2: Swagger UI 访问 :8082/ 提示错误

### 现象

浏览器访问 `http://<WSL2-IP>:8082/` 显示错误，无法加载 API 文档。

### 根因分析

`gateway/docker-compose.yml` 中 Swagger UI 容器的 `API_URL` 使用了 Docker 网桥 IP：

```yaml
swagger-ui:
  environment:
    API_URL: "http://172.17.126.161:3001/"
```

**问题**：
1. `172.17.126.161` 是 Docker bridge 网络 IP，每次 WSL2 重启后变化
2. Swagger UI 在容器内尝试访问此 IP，但 Windows 浏览器无法解析容器内部网络
3. 正确做法是使用 `host.docker.internal` 或 WSL2 主机 IP

### 解决方案

#### 修改 `gateway/docker-compose.yml`

```yaml
swagger-ui:
  image: swaggerapi/swagger-ui:v5.2.0
  container_name: app-swagger
  restart: unless-stopped
  networks:
    app-net:
      ipv4_address: 172.20.0.4
  environment:
    # 使用 host.docker.internal 访问宿主机服务
    API_URL: "http://host.docker.internal:3001/"
    # 或者使用相对路径（推荐）
    # API_URL: "/"
  ports:
    - "8082:8080"
  extra_hosts:
    - "host.docker.internal:host-gateway"
```

#### 备选方案：使用动态 IP

如果 `host.docker.internal` 不可用，可在启动脚本中动态获取 IP：

```bash
# scripts/deploy-gateway.sh 或 start.sh
WSL_IP=$(hostname -I | awk '{print $1}')
sed -i "s|API_URL:.*|API_URL: \"http://${WSL_IP}:3001/\"|" gateway/docker-compose.yml
```

#### 验证

```bash
# 重启 Swagger UI
docker compose up -d swagger-ui

# 验证
curl -s http://localhost:8082/ | head -c 200
```

## 问题 #3: Pigsty Web UI 节点清单 404（IP 变化问题）

### 现象

1. 通过 Nginx 端口 8080 访问 Pigsty Web 管理界面 ✅
2. 首页正常显示 ✅
3. 点击 PGSQL、INFRA、ETCD 节点链接提示 404 ❌

### 根因分析

`infra/pigsty.yml` 中 `infra_portal` 使用 `${admin_ip}` 作为代理端点：

```yaml
infra_portal:
  home         : { domain: i.pigsty }
  grafana      : { domain: g.pigsty, endpoint: "${admin_ip}:3000", websocket: true }
  vmetrics     : { domain: p.pigsty, endpoint: "${admin_ip}:8428" }
  pgadmin      : { domain: adm.pigsty, endpoint: "${admin_ip}:8885" }
  code         : { domain: code.pigsty, endpoint: "${admin_ip}:8080" }
  jupyter      : { domain: jupyter.pigsty, endpoint: "${admin_ip}:8889" }
```

**问题**：
1. `admin_ip: 192.168.0.128` 是 WSL2 动态分配的 IP
2. 每次重启电脑后 WSL2 IP 会变化
3. Pigsty 部署时将 `${admin_ip}` 解析为旧 IP 写入 Nginx 配置
4. Nginx 代理到旧 IP 导致 404

### 解决方案

#### 方案 A：使用 127.0.0.1 替代 ${admin_ip}（推荐）

由于所有服务都在同一台机器上，Nginx 代理到本地服务应使用 `127.0.0.1`：

```yaml
# infra/pigsty.yml
infra_portal:
  home         : { domain: i.pigsty }
  grafana      : { domain: g.pigsty, endpoint: "127.0.0.1:3000", websocket: true }
  vmetrics     : { domain: p.pigsty, endpoint: "127.0.0.1:8428" }
  pgadmin      : { domain: adm.pigsty, endpoint: "127.0.0.1:8885" }
  code         : { domain: code.pigsty, endpoint: "127.0.0.1:8080" }
  jupyter      : { domain: jupyter.pigsty, endpoint: "127.0.0.1:8889" }
```

#### 方案 B：配置 WSL2 静态 IP（高级）

在 `%USERPROFILE%\.wslconfig` 中配置：

```ini
[wsl2]
memory=8GB
processors=4
swap=2GB
# 静态 IP（需要 Windows 11 22H2+）
localhostForwarding=true
```

然后在 WSL2 中配置静态 IP：

```bash
# /etc/wsl.conf
[network]
generateResolvConf = false
```

#### 方案 C：每次重启后重新部署 Pigsty

```bash
# 更新 admin_ip
sed -i "s/admin_ip:.*/admin_ip: $(hostname -I | awk '{print $1}')/" infra/pigsty.yml

# 重新部署
cd ~/pigsty && ./infra.yml -t nginx_config,nginx_reload
```

#### 验证

```bash
# 检查 Nginx 配置中的代理地址
grep -r "proxy_pass" /etc/nginx/conf.d/ | head -20

# 应显示 127.0.0.1 而非旧 IP
```

## 问题 #4: PostgREST 端口 3001 只显示一行信息

### 现象

访问 `http://<WSL2-IP>:3001/` 只返回一行信息，而非完整的 OpenAPI JSON。

### 根因分析

PostgREST 返回单行信息通常是**错误消息**，可能原因：

#### 原因 1：数据库连接失败

`gateway/docker-compose.yml` 中 PostgREST 连接 pgbouncer：

```yaml
postgrest:
  environment:
    PGRST_DB_URI: "postgres://authenticator:***@pgbouncer:6432/app_db?sslmode=disable"
```

**潜在问题**：
- pgbouncer 容器未启动或启动缓慢
- 密码不匹配（PostgREST 使用 `authenticator`，但 `userlist.txt` 中是 `authenticator_dev_pass`）

#### 原因 2：Schema 不存在或无权限

```yaml
PGRST_DB_SCHEMAS: "api_v1_sys,api_v1_sales,api_v1_inventory"
```

如果这些 Schema 不存在，或 `authenticator` 角色没有 USAGE 权限，PostgREST 会返回错误。

#### 原因 3：`db-pre-request` 函数缺失

```yaml
PGRST_DB_PRE_REQUEST: "api_v1_sys.check_token_blacklist"
```

如果 `check_token_blacklist` 函数不存在，所有请求都会失败。

### 解决方案

#### 步骤 1：诊断 PostgREST 日志

```bash
docker logs app-postgrest --tail 50
```

常见错误：
- `permission denied for schema api_v1_sys` → 权限问题
- `function api_v1_sys.check_token_blacklist() does not exist` → 函数未刷入
- `could not connect to server` → 数据库连接问题

#### 步骤 2：修复数据库权限

```bash
# 连接到 PostgreSQL
PGPASSWORD=dev_password_change_me psql -h 127.0.0.1 -U app_owner -d app_db

-- 执行以下 SQL
GRANT USAGE ON SCHEMA api_v1_sys TO authenticator;
GRANT USAGE ON SCHEMA api_v1_sales TO authenticator;
GRANT USAGE ON SCHEMA api_v1_inventory TO authenticator;
GRANT ALL ON ALL TABLES IN SCHEMA api_v1_sys TO authenticator;
GRANT ALL ON ALL TABLES IN SCHEMA api_v1_sales TO authenticator;
GRANT ALL ON ALL TABLES IN SCHEMA api_v1_inventory TO authenticator;
GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA api_v1_sys TO authenticator;
GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA api_v1_sales TO authenticator;
GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA api_v1_inventory TO authenticator;
GRANT web_anon TO authenticator;
```

#### 步骤 3：刷入幂等源码

```bash
cd /mnt/d/WeChat\ Files/OmniPG
export PGPASSWORD=dev_password_change_me
for f in $(find db/src -name '*.sql' -not -name '_*' | sort); do
  psql -h 127.0.0.1 -U app_owner -d app_db -v ON_ERROR_STOP=0 -f "$f"
done
```

#### 步骤 4：修复 pgbouncer 认证（如需要）

检查 `edoburu/pgbouncer` 容器的认证配置：

```bash
# 进入 pgbouncer 容器
docker exec -it pgbouncer cat /etc/pgbouncer/userlist.txt
```

如果密码不匹配，需要同步：
- PostgREST 连接密码：`authenticator`（来自 `PGRST_DB_URI`）
- pgbouncer `AUTH_PASSWORD`：`authenticator`（来自 docker-compose）
- PostgreSQL `authenticator` 角色密码：`authenticator_dev_pass`（来自 `pigsty.yml`）

**注意**：`edoburu/pgbouncer` 容器的 `AUTH_PASSWORD` 是客户端连接 pgbouncer 的密码，不是 PostgreSQL 密码。

#### 步骤 5：重启 PostgREST

```bash
docker restart app-postgrest
sleep 3
curl -s http://localhost:3001/ | jq .
```

#### 验证

```bash
# 应返回完整的 OpenAPI JSON
curl -s http://localhost:3001/ | jq '.definitions | keys'

# 测试 RPC 调用
curl -s http://localhost:3001/rpc/user_login_sso \
  -H "Content-Type: application/json" \
  -d '{"p_username":"admin","p_password":"admin123"}' | jq .
```

## 其他发现的问题

### 问题 5：Docker Compose 卷路径不一致

`gateway/docker-compose.yml` 中使用绝对路径：

```yaml
volumes:
  - /root/OmniPG/gateway/apisix/config.yaml:/usr/local/apisix/conf/config.yaml:ro
```

但项目实际路径可能是 `/mnt/d/WeChat Files/OmniPG` 或 `/opt/omnipg`。

**建议**：改用相对路径：

```yaml
volumes:
  - ./apisix/config.yaml:/usr/local/apisix/conf/config.yaml:ro
  - ./apisix/apisix.yaml:/usr/local/apisix/conf/apisix.yaml:ro
  - ./apisix/debug.yaml:/usr/local/apisix/conf/debug.yaml:ro
```

### 问题 6：Syncer 8080 端口冲突

`docker-compose.yml` 中 syncer 服务映射了 8080 端口，与 WSL2 Nginx/Pigsty 冲突。

```yaml
syncer:
  # 移除 ports 映射，或改为其他端口
  # ports:
  #   - "8080:8080"
```

## 修复优先级

| 优先级 | 问题 | 影响 |
|:---:|:---|:---|
| P0 | PostgREST 数据库权限 | API 完全不可用 |
| P0 | Swagger UI API_URL | API 文档无法访问 |
| P1 | Pigsty 节点 404 | 管理界面不可用 |
| P1 | APISIX Admin API 调用 | 路由配置失败 |
| P2 | Docker 卷路径 | 可能导致容器启动失败 |
| P2 | Syncer 端口冲突 | 服务无法启动 |

## 一键修复脚本

```bash
#!/bin/bash
# scripts/fix-deployment-issues.sh
set -euo pipefail

PROJECT_DIR="$(cd "$(dirname "$0")/.." && pwd)"
cd "$PROJECT_DIR"

echo "========================================"
echo "  OmniPG 部署问题一键修复"
echo "========================================"

# 1. 修复 Swagger UI API_URL
echo ""
echo "[1/4] 修复 Swagger UI API_URL..."
cd gateway
sed -i 's|API_URL:.*|API_URL: "http://host.docker.internal:3001/"|' docker-compose.yml
echo "  ✅ 已修复"

# 2. 修复 Pigsty admin_ip
echo ""
echo "[2/4] 修复 Pigsty admin_ip..."
cd "$PROJECT_DIR/infra"
WSL_IP=$(hostname -I | awk '{print $1}')
sed -i "s/admin_ip:.*/admin_ip: ${WSL_IP}/" pigsty.yml
sed -i 's/endpoint: "\${admin_ip}:/endpoint: "127.0.0.1:/g' pigsty.yml
echo "  ✅ 已修复 (使用 127.0.0.1)"

# 3. 修复 Docker 卷路径
echo ""
echo "[3/4] 修复 Docker 卷路径..."
cd "$PROJECT_DIR/gateway"
sed -i 's|/root/OmniPG/gateway/|./|g' docker-compose.yml
echo "  ✅ 已修复"

# 4. 重启服务
echo ""
echo "[4/4] 重启服务..."
docker compose down
docker compose up -d
sleep 10

echo ""
echo "========================================"
echo "  修复完成！请验证以下服务："
echo "========================================"
echo ""
echo "  Swagger UI:  http://localhost:8082"
echo "  PostgREST:   http://localhost:3001"
echo "  APISIX:      http://localhost:9080"
echo "  Pigsty:      http://localhost:8080"
echo ""
```
