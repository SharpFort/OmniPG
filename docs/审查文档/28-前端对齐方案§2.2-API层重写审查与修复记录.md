## 三、cleanup_expired_tokens 死链复核（拍板 4 的关键查证）

用户拍板"后端定时任务自动清除，不用前端处理"——查证后发现**没有可清理的东西**：

1. `public.cleanup_expired_tokens()` **全库无定义**——029 的 wrapper（`api_v1_public.cleanup_expired_tokens()`）内部 `PERFORM public.cleanup_expired_tokens()` 目标不存在，调用必报 undefined function；
2. 清理对象 `sys_token_blacklist` / `sys_user_session` 表 **014 已 DROP**（D12 决策：会话/吊销交 Logto 管理）；
3. 034 重调度的 cron 任务 `cleanup-expired-tokens`（每小时）自创建起**每次执行都失败**（先 42501 门槛——cron 无 JWT claims；后 undefined function）；
4. 连带：`v_system_stats_realtime.last_cleanup_time` 恒 NULL（任务从未成功写入 cron_job_log）。

**处置（比"后端定时跑"更彻底）**：wrapper + 权限点 `sys:session:cleanup` + cron 任务**整链删除**；`v_system_stats_realtime.last_cleanup_time` 改指 `cleanup-old-audit-logs`（真实在跑的审计日志 90 天清理任务）。前端 monitor 页**不需要**任何会话清理封装。

**教训**：029 补门槛时假设 `public.cleanup_expired_tokens` 存在（未核实）；034 重调度时只看了"函数名存在"（029 wrapper）没看底层。**包装函数链必须逐层核实到底层实现**（本审查第 3 层核实才暴露）。

## 四、Q1 替代分析（get_user_permissions 使用场景）

| 输出 | 历史用途（Casdoor 时代） | 现状替代 | 说明 |
|:--|:--|:--|:--|
| user_id | 前端确认身份 | `get_current_user().id` | 登录态由 userStore 持有 |
| roles | 角色判断 | `get_current_user().roles`（string[]） | claims 直出，零查询 |
| permissions（path/method） | 按钮/接口级权限 | **v_role_api_detail 视图**（api_code 集合，§2.6 usePermission） | ⚠️ 旧输出是 casbin 语义（path/method），与后端授权判定键 **api_code 不一致**——即使函数不炸，前端拿它判断按钮权限也会与 has_permission 对不上 |

**结论：使用场景不存在**。casbin_rule 视图（009 重建为 iam_role_api/iam_role_menu 投影）保留——pgTAP 测试（test_casbin_view.sql / 01_schema_test.sql）引用，只读兼容视图无害；如需删除需连带改测试，另行决策。
