## 一、问题 1：APISIX 仅网关模式（Standalone）下的残留配置

### 1.1 现状核查

按 CI/CD 方案决策（§一.10："基础组件：Pigsty 统一管理…Docker"），APISIX 应**仅作为网关（data plane，standalone 模式）运行**，不安装 Admin API、Dashboard、etcd 等控制面组件。

**已正确移除的部分** ✅：
- `docker-compose.yml` 中 APISIX 服务**未**映射 9180（Admin API）端口，未运行 etcd 容器；
- `gateway/apisix/config.yaml` 为纯 data plane 配置（`role: data_plane` + `config_provider: yaml`）；
- `gateway/apisix/apisix.yaml` 已静态声明路由（含 `#END` 结尾标记 ✅）。

**未移除/仍错误的残留** ❌：

| # | 位置 | 问题 | 后果 |
|:--|:--|:--|:--|
| A1 | `scripts/setup_apisix.sh` L4/L15/L31 | 仍通过 `curl PUT http://localhost:9180/apisix/admin/plugin_metadata/...` 配置插件 | Standalone 模式下 **Admin API 不可用**（官方文档："This makes it possible to disable the Admin API"），脚本必然失败 |
| A2 | `scripts/setup_apisix.sh` L16/L32 | 请求头变量损坏：`-H "X-API-KEY: ${APIS...EY}"` | bash 将 `${APIS...EY}` 解析为 `${APIS}`（未定义→空）+ 字面量 `...EY`，实际发送 `X-API-KEY: ...EY`，即使 Admin API 可用也认证失败 |
| A3 | `db/syncer/internal/apisix/client.go` | Syncer 全部逻辑基于 HTTP Admin API（GET/PUT `/plugin_metadata/authz-casbin`） | Standalone 模式无 Admin API → 策略同步永远失败（日志报 404） |
| A4 | `gateway/docker-compose.yml` L184 | `APISIX_ADMIN_URL: http://apisix:9080/apisix/admin/plugin_metadata/authz-casbin` | 双重错误：端口 9080 是数据面（Admin API 应为 9180），且 standalone 下 Admin API 不存在 |
| A5 | `gateway/apisix/apisix.yaml` | **缺少 `plugin_metadata` 段**（官方 standalone YAML 支持顶层 `plugin_metadata:` 配置） | jwt-auth 插件无共享密钥 → 所有挂 `jwt-auth` 的路由（`/api/v1/sys/*`、`/rpc/*`、`/*`）**一律 401** |
| A6 | `.github/workflows/deploy-gateway.yml` L36/L56 | 仍传 `APISIX_ADMIN_KEY` secret 并执行 `setup_apisix.sh` 步骤 | 控制面密钥在"仅网关"架构下已无意义，CI 步骤会失败 |
| A7 | `scripts/fix-apisix-etcd.sh` | 遗留"APISIX 使用 etcd 模式"修复脚本 | 与"仅网关/standalone"方向直接冲突，属应归档的死代码 |
| A8 | `gateway/apisix/casbin_rule` | 空文件（0 行），`casbin_model.conf` 存在但**未挂载进容器、未在任何路由启用 authz-casbin 插件** | Casbin 鉴权链路当前完全未生效 |
| A9 | `gateway/apisix/debug.yaml` | 调试模式（`X-APISIX-Dynamic-Debug` 头）处于启用状态 | 安全风险（P2），正常部署应关闭 |

> 另注：`测试验证清单-Phase4.md` L358 的故障排查仍建议 `curl http://localhost:9180/apisix/admin/plugin_metadata/jwt-auth`，与 standalone 模式矛盾，文档需同步修正。

### 1.2 官方依据

1. **Standalone 模式定义**（[deployment-modes](https://apisix.apache.org/zh/docs/apisix/deployment-modes/)）：`deployment.role: data_plane` + `role_data_plane.config_provider: yaml`，"This makes it possible to **disable the Admin API** and discover configuration changes and reloads based on the local file system"。文件模式每 1 秒检测 `apisix.yaml` 变化并热加载（须以 `#END` 结尾）。
2. **Standalone YAML 支持 `plugin_metadata`**（同文档 "How to configure plugin metadata" 章节，id 即插件名）——jwt-auth 密钥应写在这里，而不是通过 Admin API。
3. **Status API 独立端口**（[status-api](https://apisix.apache.org/zh/docs/apisix/status-api/)）：默认 `127.0.0.1:7085`，需在 `config.yaml` 的 `apisix.status` 段配置；**`/apisix/status` 不在 9080 上**——`deploy-gateway.sh`、`e2e-test.sh`、测试清单中 `curl http://localhost:9080/apisix/status` 的健康检查写法全部错误（必然 404）。

### 1.3 修复方案（推荐：保持 Standalone + 文件模式）

#### ① `gateway/apisix/apisix.yaml`：补 `plugin_metadata`（jwt-auth 共享密钥）

系统 JWT 由后端 `rpc/user_login_sso` 以 **HS256** 签发（密钥即 `PGRST_JWT_SECRET` 中的 `k` 字段，与 `JWKS_JSON` 同源）。jwt-auth 插件的元数据应使用同一密钥：

```yaml
plugin_metadata:
  - id: jwt-auth
    algorithm: HS256
    key: c2VjcmV0X2RldmVsb3BtZW50X2tleV9hdF9sZWFzdF9zZXZlbl9jaGFyYWN0ZXJzIQ==   # = JWKS_JSON 中 k 字段（base64）
    base64_secret: true
#END
```

> ⚠️ 若后续切换为 Casdoor 签发 RS256 令牌，则将 `algorithm` 改为 `RS256`、`key` 改为 Casdoor 的 JWKS JSON（这正是旧脚本的意图，但旧脚本用 Admin API 且算法/密钥源与现状不符，不可用）。

#### ② `scripts/setup_apisix.sh`：重写为"静态配置校验"（删除 Admin API 调用）

```bash
#!/bin/bash
# APISIX Standalone 模式配置校验（路由/插件由 apisix.yaml 静态加载，无需 Admin API）
set -euo pipefail
SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
APISIX_YAML="$SCRIPT_DIR/../gateway/apisix/apisix.yaml"

echo "=== APISIX Standalone 配置校验 ==="
[ -f "$APISIX_YAML" ] && grep -q '#END' "$APISIX_YAML" \
  && echo "  ✅ apisix.yaml 存在且含 #END 标记" \
  || { echo "  ❌ apisix.yaml 缺失或缺少 #END"; exit 1; }

grep -q 'id: jwt-auth' "$APISIX_YAML" && echo "  ✅ plugin_metadata.jwt-auth 已配置" \
  || { echo "  ❌ 缺少 plugin_metadata.jwt-auth（受保护路由将全部 401）"; exit 1; }

echo "  ✅ 校验通过 — 路由由 apisix.yaml 静态加载（热更新：修改文件后 1 秒内生效）"
```

#### ③ Syncer：改为"写文件"模式（需小量 Go 开发）

`db/syncer` 当前 `APISIXClient` 接口（GetPolicy/PutPolicy）基于 Admin API。在 standalone 模式下改为**写 `casbin_rule` 文件 + 通知 APISIX 重载**：

- 方案：syncer 增加 `CASBIN_RULE_FILE` 环境变量；`PutPolicy` 实现改为原子写文件（`write temp → rename`），`GetPolicy` 改为读文件；
- compose 中 APISIX 与 syncer 共享卷（syncer 读写、APISIX 只读挂载）；
- `apisix.yaml` 中需要鉴权的路由挂 `authz-casbin` 插件，其 `policy` 通过 `_meta`/文件引用（详见 §7.10 说明，当前 Casbin 链路整体未生效，建议单独立项）。

**过渡期**：若暂不改造 syncer，可先将 `docker-compose.yml` 中 syncer 的 `APISIX_ADMIN_URL` 环境变量移除，并接受"策略同步暂不生效"的降级状态（Casbin 鉴权当前本就没有生效）。

#### ④ 清理其他残留

- `.github/workflows/deploy-gateway.yml`：删除 `APISIX_ADMIN_KEY` 环境变量与 "Initialize APISIX Routes" 步骤（或改为执行上述校验脚本）；
- `scripts/fix-apisix-etcd.sh`、`scripts/phase4-*.sh`、`scripts/casdoor_integration.sh`：归档到 `scripts/legacy/`（或删除），避免误导；
- `gateway/apisix/debug.yaml`：移除挂载并删除文件（或按需开启）；
- `config.yaml` 补充 Status API（同时修复健康检查，见 §7.3）。

## 二、问题 2：Swagger UI :8082 报错

### 2.1 现状核查

```yaml
# gateway/docker-compose.yml L139-142
swagger-ui:
  environment:
    API_URL: "http://172.17.126.161:3001/"   # ← 硬编码 WSL2 旧 IP（commit c81a044 引入）
```

`172.17.126.161` 是某次开机时 WSL2 动态分配的 eth0 IP。**WSL2 每次重启 IP 都会变化**，IP 失效后 Swagger UI 无法拉取 OpenAPI 文档 → 页面报错。这与问题 3 同源（IP 漂移）。

### 2.2 根因补充：CORS 被错误归因

Swagger UI 在**浏览器端**向 `API_URL` 发起请求拉取 OpenAPI spec。该请求**直接打 PostgREST（:3001），不经过 APISIX**，因此 APISIX 的全局 `cors` 插件管不到它。而 `postgrest.conf` L98 写着 `cors-origins = ""`（注释："CORS 配置（由 APISIX 网关处理）"）——**这个注释是错的**：spec 拉取请求跨源（8082 → 3001），PostgREST 必须自己返回 CORS 头，否则浏览器拦截。当初改成 WSL2 IP 并不能解决 CORS，只是凑巧掩盖了问题。

### 2.3 修复方案

```yaml
swagger-ui:
  image: swaggerapi/swagger-ui:v5.2.0
  container_name: app-swagger
  restart: unless-stopped
  networks:
    app-net:
      ipv4_address: 172.20.0.4
  environment:
    # ✅ 参数化：浏览器与 Docker 同机时 localhost 即宿主机映射端口，永不漂移
    # （Swagger 由浏览器端拉取 spec，因此不能用容器网络域名 app-postgrest）
    API_URL: "http://localhost:${PGRST_PORT:-3001}/"
  ports:
    - "8082:8080"
```

同时给 PostgREST 开启 CORS（compose 环境变量或 postgrest.conf）——**这是必须的**：Swagger 在浏览器端从 8082 跨源拉取 3001 的 spec，不经过 APISIX，PostgREST 必须自己返回 CORS 头：

```yaml
postgrest:
  environment:
    PGRST_CORS_ORIGINS: "*"        # 开发环境放开；生产建议收窄为前端域名
```

```ini
# gateway/postgrest/postgrest.conf
cors-origins = "*"
```

> 备选：若需要从局域网其他设备访问 Swagger（此时浏览器不在宿主机上，localhost 失效），可在 APISIX 增加一条公开路由 `/openapi` → PostgREST `/`（不挂 jwt-auth），`API_URL` 改为 `http://localhost:9080/openapi`，CORS 由 APISIX 全局 cors 插件处理。

## 三、问题 3：Pigsty WebUI 节点清单 404（IP 漂移）

### 3.1 现状核查

三份配置全部硬编码局域网 IP：

| 文件 | hosts | admin_ip | infra_portal endpoint |
|:--|:--|:--|:--|
| `infra/pigsty.yml` | `192.168.0.128` | `192.168.0.128` | `${admin_ip}:3000 / 8428 / 8885 / 8080 / 8889` |
| `infra/pigsty.db.yml` | `192.168.0.128` | `192.168.0.128` | `${admin_ip}:3000 / 8428 / 8885` |
| `infra/pigsty.gateway.yml` | `192.168.0.129` | `192.168.0.129` | `${admin_ip}:8080 / 8889` |

`node_etc_hosts` 同样引用 `${admin_ip}`（写入 `/etc/hosts`）。**Pigsty 部署时把 `${admin_ip}` 渲染进 nginx 反代配置与首页拓扑表**，WSL2 重启后 IP 变化 → 全部指向过期地址。

### 3.2 404 的具体机制（官方文档核实）

- Pigsty WebUI 由 INFRA 模块的 **Nginx（默认 80/443）** 提供服务（[webui](https://pigsty.cc/docs/setup/webui/)）；
- 首页"节点清单"卡片（官方 demo 站实测 HTML）链接结构为 **Grafana 路径**：
  - 表头：NODE → `/ui/d/node-overview`、PGSQL → `/ui/d/pgsql-overview`、INFRA → `/ui/d/infra-overview`、ETCD → `/ui/d/etcd-overview`
  - 实例行：`/ui/d/node-instance?var-id=<ip>`、`/ui/d/pgsql-instance?var-ins=pg_omnipg-1`
- nginx 的 `/ui/` location 反代到 `${admin_ip}:3000`（部署时渲染）。**IP 过期后**：
  - 若反代目标写死为旧 IP → 点击节点卡片 = 请求发往 `http://192.168.0.128:3000/...`（可能是局域网内其他设备或无响应）→ 表现为 404/502/超时；
  - 首页本身是 nginx 静态页（不依赖 IP）→ 所以"首页正常、点节点 404"。
- 另外，用户通过 **8080 端口**访问 WebUI（非 Pigsty 默认 80），说明 nginx 监听被自定义过；若自定义 server 块未正确代理 `/ui/`、`/vmetrics/` 等 location（或缺失 SSI 支持），也会直接 404。该自定义配置不在仓库内，需在机器上核查（见 3.4 验证命令）。

### 3.3 官方依据（重要）

Pigsty 官方安装文档（[setup/install](https://pigsty.cc/docs/setup/install/)）明确：

> "通常您只需要关注本机 IP 地址 —— **作为特例，单机部署时，如果没有静态 IP 地址，可使用 `127.0.0.1` 作为逃生窗口**。"

WSL2 正是"没有静态 IP"的典型场景 → **官方推荐路径就是用 `127.0.0.1`**。

### 3.4 修复方案

#### 方案 A（推荐）：单机配置全面改用 `127.0.0.1`，一劳永逸

修改 `infra/pigsty.yml`（`pigsty.db.yml` 同理）：

```yaml
all:
  children:
    pg_omnipg:
      hosts:
        127.0.0.1: { pg_seq: 1, pg_role: primary }      # ← 替换 192.168.0.128
    infra:
      hosts:
        127.0.0.1: { infra_seq: 1 }
    etcd:
      hosts:
        127.0.0.1: { etcd_seq: 1 }
    redis:
      hosts:
        127.0.0.1: { redis_node: 1, redis_instances: { 6379: {} } }
    docker:
      hosts:
        127.0.0.1: { docker_seq: 1 }
    vibe:
      hosts:
        127.0.0.1: { vibe_seq: 1 }
  vars:
    version: v4.4.0
    admin_ip: 127.0.0.1                                    # ← 关键
    infra_portal:
      home         : { domain: i.pigsty }
      grafana      : { domain: g.pigsty, endpoint: "127.0.0.1:3000", websocket: true }
      vmetrics     : { domain: p.pigsty, endpoint: "127.0.0.1:8428" }
      pgadmin      : { domain: adm.pigsty, endpoint: "127.0.0.1:8885" }
      code         : { domain: code.pigsty, endpoint: "127.0.0.1:8080" }
      jupyter      : { domain: jupyter.pigsty, endpoint: "127.0.0.1:8889" }
    node_etc_hosts: ['127.0.0.1 i.pigsty sss.pigsty']
```

**重新生成 nginx 配置并生效**（在 WSL2 内执行，幂等）：

```bash
cd ~/pigsty
cp /mnt/d/WeChat\ Files/OmniPG/infra/pigsty.yml ./pigsty.yml   # 先同步新配置
./infra.yml          # 重新渲染 nginx 配置 / 首页拓扑表 / /etc/hosts，并 reload
```

> 注：不要用 `./configure` 重新生成，它会基于模板**覆盖**你的定制配置；直接用修改后的 `pigsty.yml` 跑 `./infra.yml` 即可。若仅验证 nginx 反代目标，执行：
> ```bash
> grep -r "proxy_pass" /etc/nginx/conf.d/pigsty/ | head -20   # 应全部是 127.0.0.1
> ```

#### 方案 B：动态 IP 检测（若必须使用真实 IP，如跨设备访问）

在 `scripts/deploy-infra.sh` 中增加 IP 漂移检测与配置重写（在复制配置到 `~/pigsty` 之前）：

```bash
# ===== deploy-infra.sh 新增段 =====
CURRENT_IP=$(hostname -I 2>/dev/null | awk '{print $1}')
if [ -z "$CURRENT_IP" ]; then CURRENT_IP="127.0.0.1"; fi
echo "  当前节点 IP: ${CURRENT_IP}"

# 用占位符模板生成运行时配置（仓库中 infra/pigsty.yml 固定写 10.10.10.10 占位符）
sed -e "s/10\.10\.10\.10/${CURRENT_IP}/g" \
    -e "s/admin_ip: .*/admin_ip: ${CURRENT_IP}/" \
    "$CONFIG_FILE" > "$HOME/pigsty/pigsty.yml"

# 若 IP 与上次不同，需重渲染 nginx/首页：
cd "$HOME/pigsty"
if [ -f .ip_last ] && [ "$(cat .ip_last)" != "$CURRENT_IP" ]; then
    ./infra.yml 2>&1 | tail -5
fi
echo "$CURRENT_IP" > "$HOME/pigsty/.ip_last"
```

配套建议：仓库内的 `infra/pigsty.yml` 统一使用 `10.10.10.10` 占位符（官方模板默认占位符），部署时替换——避免把机器 IP 提交进 git。

#### 方案 C：根治 WSL2 IP 漂移（系统层）

- **Windows 11 22H2+**：`%USERPROFILE%\.wslconfig` 加 `networkingMode=mirrored`，WSL2 与 Windows 共享 IP，`127.0.0.1` 双向直达（同时解决 Docker 容器 ↔ WSL2 宿主互访问题，见问题 4）；
- **Windows 10**（当前宿主）：无 mirrored 模式，只能方案 A/B；或每次开机后执行 `wsl --shutdown` 前记录 IP，部署脚本自动检测。

### 3.5 自定义 8080 端口核查

在机器上执行以下命令确认 8080 的 server 块配置正确（不在仓库内，需现场核查）：

## 四、问题 4：PostgREST :3001 只见一行信息

### 4.1 现状核查（多层故障叠加）

```
gateway/docker-compose.yml:
  L50   pgbouncer:  DATABASE_URL=postgres://app_owner:***@pgsql:5432/app_db   ← 密码字面 ***
  L52               AUTH_PASSWORD=authenticator                              ← 与真实密码不一致
  L111  postgrest:  PGRST_DB_URI: "postgres://authenticator:***@pgbouncer:6432/app_db?sslmode=disable"  ← 密码字面 ***
gateway/postgrest/postgrest.conf:
  L9    db-uri = "postgres://authenticator:***@host.docker.internal:6432/app_db?sslmode=disable"  ← 密码字面 ***
```

三层故障：

1. **凭据占位符**：连接串密码是字面 `***`（`grep` 实测文件原文如此）。PostgREST 用 `***` 认证 pgbouncer → 必然失败；
2. **角色缺失**：compose 自建的 `pgsql` 容器（`postgres:17-alpine`）只有 `POSTGRES_USER=app_owner` 一个角色，**不存在 `authenticator`、`web_anon` 角色**（这两个角色只在 Pigsty 管理的宿主 PG 里由 `pigsty.yml` 创建）→ 即使密码正确，pgbouncer 的 `auth_query`（`AUTH_USER=authenticator`）也查不到用户；
3. **空库**：docker `pgsql` 的 `app_db` 是全新空库，**没有 `api_v1_sys/api_v1_sales/api_v1_inventory` schema，没有跑过 dbmate 迁移与 apply-src** → PostgREST 即使连上，schema cache 也会加载失败。

**"一行信息"判别方法**（在机器上直接看响应体即可定位是哪一层）：

```bash
curl -s http://localhost:3001/ | head -c 500
# {"code":"PGRST101",...,"message":"Could not connect to the database"}   → 连接/认证失败（当前 *** 即此层）
# {"code":"PGRST115",...,"message":"role \"web_anon\" not found"}          → 角色缺失
# {"code":"PGRST104",...,"message":"schema \"api_v1_sys\" not found"}      → schema 未建/未授权
# 正常: 大段 OpenAPI JSON（几千字符以上）
```

### 4.2 架构根因：compose 自建 PG 与"Pigsty 统一管理 PG"决策冲突

`ci-cd-方案.v2.1修复版.md` 决策 #4/#10：**PostgreSQL/pgBouncer/Redis 由 Pigsty 统一管理，Docker Compose 不单独部署**；测试清单也明确"**Docker Compose 服务启动（无 Redis）**"且验收项为"PostgREST 多 Schema 配置正确"。但 commit `f181e97` 为"解决 Docker↔WSL2 网络隔离"引入了 `pgsql` + `pgbouncer` + `casdoor-db` 三个容器，把数据库搬进 Docker——于是出现了**两套数据库**（宿主 Pigsty PG18 管迁移/源码，docker PG17 管运行时），角色/schema/迁移全部断链。

### 4.3 修复方案

#### 方案 A（推荐，架构对齐）：移除 compose 中的数据库容器，统一连 Pigsty 数据库

适用条件：Windows 11 22H2+（WSL2 mirrored 网络）或能接受容器→宿主用动态 IP。

```yaml
# gateway/docker-compose.yml（精简后）
services:
  postgrest:
    image: postgrest/postgrest:v14.15
    container_name: app-postgrest
    restart: unless-stopped
    networks: [app-net]
    environment:
      PGRST_DB_URI: "postgres://authenticator:${AUTHENTICATOR_PASSWORD}@host.docker.internal:6432/app_db?sslmode=disable"
      PGRST_DB_SCHEMAS: "api_v1_sys,api_v1_sales,api_v1_inventory"
      PGRST_DB_ANON_ROLE: web_anon
      PGRST_DB_EXTRA_SEARCH_PATH: "api_v1_sys,api_v1_sales,api_v1_inventory,public,sales,inventory"
      PGRST_JWT_SECRET: '${JWKS_JSON}'
      PGRST_DB_PRE_REQUEST: "api_v1_sys.check_token_blacklist"
      PGRST_OPENAPI_SERVER_PROXY_URI: "http://localhost:3001"
      PGRST_SERVER_HOST: "0.0.0.0"
      PGRST_SERVER_PORT: "3000"
      PGRST_CORS_ORIGINS: "*"
      PGRST_DB_AGGREGATES_ENABLED: "true"
      PGRST_MAX_ROWS: "1000"
    ports: ["3001:3000"]
    extra_hosts:
      - "host.docker.internal:host-gateway"
  casdoor:
    image: casbin/casdoor:v1.680.0
    container_name: app-casdoor
    restart: unless-stopped
    networks: [app-net]
    ports: ["8000:8000"]
    environment:
      driverName: postgres
      dataSourceName: "user=casdoor password=${CASDOOR_DB_PASSWORD} host=host.docker.internal port=5432 sslmode=disable dbname=casdoor"
      runMode: dev
      httpPort: 8000
    extra_hosts:
      - "host.docker.internal:host-gateway"
  # apisix / swagger-ui / syncer 保持不变（见 §1.3 / §2.3）
```

配套：`scripts/start.sh` 已启动宿主 pgbouncer（6432），`deploy-infra.sh` 保证 Pigsty PG/角色/库齐备；`deploy-db.sh` 继续对宿主 PG 执行迁移与 apply-src（无需改动）。

#### 方案 B（Windows 10 现状下的务实方案）：保留 docker PG，但补齐角色/Schema/迁移

若无法使用 mirrored 网络，保留 `pgsql`/`pgbouncer`/`casdoor-db` 容器，但必须补齐三层：

**① 初始化角色**（`gateway/postgres/init/01-roles.sql`，挂载到 `docker-entrypoint-initdb.d`）：

```sql
-- docker pgsql 首次启动时自动执行
CREATE ROLE authenticator LOGIN PASSWORD 'authenticator_dev_pass' INHERIT;
CREATE ROLE web_anon NOLOGIN;
GRANT web_anon TO authenticator;
```

```yaml
pgsql:
  image: postgres:17-alpine
  container_name: pgsql
  restart: unless-stopped
  networks:
    app-net:
      ipv4_address: 172.20.0.10
  environment:
    POSTGRES_DB: app_db
    POSTGRES_USER: app_owner
    POSTGRES_PASSWORD: ${DB_PASSWORD}
  ports:
    - "5433:5432"              # 暴露给宿主跑迁移（避免与宿主 5432 冲突）
  volumes:
    - pgsql_data:/var/lib/postgresql/data
    - ./postgres/init:/docker-entrypoint-initdb.d:ro
```

**② 数据库迁移指向 docker PG**：

```bash
# deploy-db.sh 支持 DB_PORT 覆盖（方案 B 时 DB_PORT=5433）
export DBMATE_DATABASE_URL="postgres://app_owner:${DB_PASSWORD}@127.0.0.1:${DB_PORT:-5433}/app_db?sslmode=disable"
cd db && dbmate up && bash ../scripts/apply-src.sh "$DBMATE_DATABASE_URL"
```

**③ 修正全部密码为 .env 参数化**（关键！）：

```yaml
pgbouncer:
  image: edoburu/pgbouncer:latest
  container_name: pgbouncer
  restart: unless-stopped
  networks:
    app-net:
      ipv4_address: 172.20.0.11
  environment:
    - DATABASE_URL=postgres://app_owner:${DB_PASSWORD}@pgsql:5432/app_db
    - AUTH_USER=authenticator
    - AUTH_PASSWORD=${AUTHENTICATOR_PASSWORD}
    - AUTH_TYPE=scram-sha-256
    - POOL_MODE=session
    - MAX_CLIENT_CONN=100
    - DEFAULT_POOL_SIZE=20
    - ADMIN_USERS=app_owner
    - LISTEN_PORT=6432
  depends_on:
    pgsql:
      condition: service_healthy
```

`gateway/postgrest/postgrest.conf` 同步改为（或直接弃用该文件、统一用 compose 环境变量）：

```ini
db-uri = "postgres://authenticator:$(AUTHENTICATOR_PASSWORD)@pgbouncer:6432/app_db?sslmode=disable"
```

> 注意：compose 的 `pgsql` 容器密码 `POSTGRES_PASSWORD` 与宿主 Pigsty `pg_users` 中 app_owner 的密码应保持一致（都是 `dev_password_change_me`），避免两套库密码漂移。

### 4.4 验证命令

```bash

# 2) Schema 检查
```
