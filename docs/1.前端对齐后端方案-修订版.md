#### 1.1 修订要点（v1.1 新增）

1. **`user_role` → `user_tenants` 更名**：原 `api_v1_public.user_role` 视图（T7 起即 user_tenants 投影）与 `public.user_role` 表（024 用户↔角色分配镜像）同名不同物，API 消费者极易混淆。034 将视图更名 `user_tenants`（列 = 表列：user_id / organization_id / joined_at）。**前端注意**：查询"用户属于哪些租户/组织"用 `user_tenants` 或 `v_user_list.organizations`；查询"用户被分配了哪些 Logto 角色"用 `v_user_roles` / `v_role_users`（仅超管）或 claims（`get_current_user`）。
2. **两套 role_id 语义**：`user_tenants.organization_id`（= 租户 id）与 `iam_role_api/iam_role_menu/v_role_api_detail.role_id`（= Logto 角色 id）**不是同一 id 空间，禁止互 join**；`role` 视图 `id` 同样是角色 id。角色-API 绑定的关联键是 `role_code`（字符串）。
3. **权限前提速查**：`authenticated` 可读 = 全部表名视图 + v_user_list/v_role_list/v_dept_list/v_system_stats/v_system_stats_realtime/v_user_role_detail/v_role_api_detail/v_role_menu_detail/v_audit_log_detail/v_audit_log_timeline/v_dict_list/v_login_log + dict_type/dict_data（034 补齐）；**仅超管** = v_user_roles/v_role_users/login_log 直查（登录日志页走 RPC）。所有视图受 RLS 行级过滤（租户隔离 + 超管豁免）。
4. **`audit_log` 视图是精简投影**（8 列），019 扩展列（log_type/module/action/target_type/target_id/result/ip/user_agent/region/duration_ms）仅经 `search_audit_log` RPC / `v_audit_log_detail` 可得。

### 1.2 RPC（POST /rpc/{name}）

**Logto Console 前置配置清单**（用户落实）：
1. SPA 应用 + redirect URI（`/auth/callback`）+ post sign-out redirect URI（`/`）
2. Sign-up and sign-in：启用 **Password** 登录方式 + 注册标识（用户名/邮箱）+ **Forgot password** 验证方式（email/phone 验证码）
3. Email/SMS connector（自部署 OSS 需接入邮件服务）
4. **Password policy**（Console > Security > Password policy，按 NIST 最佳实践）：

| 配置项 | 建议值 | 依据 |
|:--|:--|:--|
| 最小密码长度 | 8（允许更长） | NIST ≥8；长度比复杂度更有效 |
| 最小字符类型 | 1/4（不强制组合） | Facebook/Discord/Stripe 实践 |
| 泄露密码检查 | 开启（HIBP） | 防目录攻击 |
| 重复字符检查 | 开启（拒绝 11111111/password123） | 低安全短语拦截 |
| 用户信息检查 | 开启（拒绝含用户名/邮箱/手机） | 官方配置项 |
| 自定义禁用词 | 可选（产品名等） | 官方配置项 |
| 定期强制改密 | 不配置（仅泄露证据时强制） | NIST + blog |
| 登录限速/锁定 | 内置默认（连续失败锁定 + cooldown + webhook） | blog Step 3 |
| 改密后清其他设备会话 | 内置默认 | blog Step 3 |

   ⚠️ 策略对新密码生效（新注册/改密）；存量密码不受影响（可用 `check-password` API 审计，可选）。
5. **Custom JWT 核对**：`organization_id` claim（后端 `current_tenant_id()` 依赖单值；Logto 默认 organizations 为数组——05 文档 v3.4 声称已注入，实施时 Console 核对）

### 2.4 菜单与路由

- **后端菜单适配**（MenuProcessor.processBackendMenu）：
  - 扁平列表 → 树（parent_id）；⚠️ **两遍构建**：扁平列表按 order_num 全局排序，子节点 order_num 可能小于父目录（跨层级混排）——先建全量节点 Map 再统一挂载，不能假设"父先于子出现"
  - **component 直用 035 下发的值**（033 已回填 `system/user/index` 形式），**path → component 映射表降级为兜底**（component 为空时用：user→/system/user、role→/system/role、menu→/system/menu、api→/system/api、dept→/system/dept、position→/system/position、dict→/system/dict、tenant→/system/tenant、login-log→/system/login-log、audit-log→/system/audit-log、monitor→/system/monitor）
  - **menu_type=button 过滤（按钮不注册路由）——v1.3 可行：035 起 get_user_menu 返回含 menu_type/perms/is_visible**；link 类型按外链处理（path=URL 直接 window.open 或 iframe，不 addRoute）
  - **is_visible=false → 注册路由 + meta.hideInMenu**（不显示在菜单栏但 URL 可直达——详情页/隐藏入口），不整体过滤
  - 树为空时 fallback 到本地 asyncRoutes
- **本地 asyncRoutes**（router/modules/*）：
  - 更新 system.ts roles：`['R_SUPER','R_ADMIN']` → `['role_super_admin','tenant_admin']`（v1.1：与 init/02-schemas.sql 新增 PG 角色一致）
  - 新增子路由：dept、position、dict、tenant、login-log、audit-log、monitor
- **VITE_ACCESS_MODE**：本轮保持 `frontend`（本地路由全量、角色过滤），后端菜单适配逻辑实现但默认关闭（拍板 3）
  - ⚠️ **角色权限分配联动**（get_user_menu 递归 CTE 特性）：菜单树只从"绑定的顶级节点"递归——若父目录未绑定，**整个子树静默丢失**。role 权限分配穿梭框必须**父子联动**（勾选子节点自动勾选父链并提交，半选父节点也要进绑定集）
  - 🔜 **下一轮优化（backend 模式切换）**：用户登录后调用 `get_user_menu()` + `v_role_api_detail` 获取可访问资源（菜单树 + 权限码），**存入前端缓存（Pinia userStore）**，路由由缓存动态注册（addRoute）替代本地全量注册；切换时核对本地 asyncRoutes 与 iam_menu.path 一致性（011 种子 path 清单 vs router/modules/system.ts）

### 2.6 权限指令

> ✎ v1.5 定稿（用户拍板 2026-08-07）：短路收窄仅 role_super_admin、内存缓存策略、v-auth/v-perm 职责边界。

- **职责边界**：
  - `v-auth` 指令：**页面/菜单级**可见性——基于路由 meta.authList（frontend 模式本地角色过滤），保留
  - `v-perm` 指令：**按钮/操作级**权限——基于后端权限码（v_role_api_detail.api_code），新增
  - 两者数据源不同（本地 authList vs 后端权限码），**两层并存不互替**；页面级用 v-auth，按钮级用 v-perm
- **`usePermission` composable**：`hasPerm(code)` 判断当前用户是否具备权限点
  - 超管短路：**仅 `role_super_admin`**（v1.5 收窄——admin/super_admin 是 Casdoor 角色名残留，后端 is_super_admin 035 重建后也只认 role_super_admin，前端必须对齐）
  - 权限码集合：拉取 v_role_api_detail（role_code ∈ roles）的 api_code 集合（✔ 视图含 api_code 列）
  - **缓存策略（v1.5）**：首次 hasPerm 时拉取 + **模块级内存缓存**（单例 Set<string>），同一会话内不重复请求；登录/登出时清空；🔜 下一轮优化迁 Pinia userStore 持久缓存（与 §2.4 backend 模式同批）
  - **空缓存降级**：v_role_api_detail 依赖 role 镜像同步（INNER JOIN role）——若 Logto 侧角色未同步，绑定不显示 → hasPerm 返回 false → 按钮全隐藏（不阻断页面渲染）；超管短路不受影响
- 页面按钮用 `v-perm="'sys:dept:create'"` 指令控制；按钮显隐配置对齐 **tenant_admin 可见矩阵**（§2.5）
