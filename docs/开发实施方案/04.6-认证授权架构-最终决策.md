## 1. 决策摘要

**一句话**：Casdoor 只做认证（authN），授权（authZ）全部收归 PG sys 模块；应用通过自建 Go token-exchange 服务签发带 `roles / tenant_id / dept_id` 的应用 JWT（roles-in-JWT）；网关用 `jwt-auth` + 自定义 Lua 插件做路由级角色检查；PG RLS 直接消费 JWT claims，用户数彻底退出授权路径。

### 1.1 决策点总表

| # | 决策点 | 结论 |
|:---|:---|:---|
| D1 | Casdoor 定位 | **纯认证**：登录 / 注册 / 第三方登录（微信等）/ 用户状态管理，**不参与任何授权** |
| D2 | 角色/权限真相源 | **PG sys 模块**（sys_role / sys_user_role / sys_role_api / sys_menu / sys_api） |
| D3 | JWT 签发方 | **应用自建 Go auth-service**（RS256 自有密钥对 + JWKS 端点），Casdoor 不签业务 JWT |
| D4 | JWT claims | `sub`=用户 UUID、`roles`、`tenant_id`、`dept_id`、`name`、`email`（不含任何敏感字段） |
| D5 | 登录流程 | Casdoor SDK 重定向登录 → **token exchange**（Casdoor JWT → 应用 JWT） |
| D6 | 网关授权 | `jwt-auth`（验应用 JWT）+ **自定义 Lua 插件 `authz-role-check`**（路由级 required_roles） |
| D7 | 用户同步 | **webhook + JIT 保留**（Casdoor → PG 单向，秒级生效） |
| D8 | 用户镜像 | **瘦身至 ~15 字段**（删除密码哈希 / MFA 秘密 / WebAuthn 等敏感字段） |
| D9 | Database Syncer | **退役**（仅保留为一次性迁移工具能力，当前无存量用户） |
| D10 | password grant 路径 | **下线**（user_login_sso / refresh_token_rtr 删除） |
| D11 | 应用会话 | **复活 sys_user_session / sys_token_blacklist**：应用 token 生命周期自管，支持即时吊销 |
| D12 | casbin-syncer / authz-casbin | **退役**；Go 工程演进为 auth-service（复用部署模式：容器 / systemd） |
| D13 | RLS | 从 JWT claims 读取 sub / roles / tenant_id / dept_id（新增 helper 函数，替代部分 PG 查表） |
| D14 | JWT 时效 | Access Token 15 分钟；Refresh Token 7 天（沿用原设计，应用侧管理） |

## 2. 背景与需求演变

### 2.1 原始需求
用 Casdoor 解决 **OAuth 2.0 第三方登录**（微信扫码、小程序等国内平台），系统本身为"零后端代码"架构：PostgreSQL + PostgREST + APISIX + Vue3 前端，业务逻辑全在 PG（函数 / RPC / 触发器）。

### 2.2 Phase 1 现状（2026-07 ~ 08 已提交代码）
- `007_casdoor_user_mirror.sql`：69 字段全量镜像表 + 兼容视图 + 派生状态触发器 + RLS
- webhook RPC（`webhook_user_upsert` / `webhook_user_delete`）+ JIT（`ensure_user`）
- `rpc_create_user` 经 pg_net 调 Casdoor `/api/add-user`（PG → Casdoor 反向）
- `user_login_sso` / `refresh_token_rtr`：password grant 遗留路径
- casbin-syncer（Go）：PG `casbin_rule` → APISIX `authz-casbin` 插件元数据
- Database Syncer（Casdoor 侧配置）：双向对账（未最终启用）

### 2.3 讨论中暴露的问题（本决策的动因）
1. **password grant 路径**绕过 Casdoor 登录页的 MFA / 验证码 / 登录锁定 / 第三方联邦；且 007 迁移后 `sys_user.password_hash` 恒为 NULL，该路径实际已失效（死代码）。
2. **69 字段镜像**包含 `password` / `totpsecret` / `recoverycodes` / `mfaaccounts` / `webauthncredentials` 等凭据与 MFA 秘密 → 业务库被拖库 = MFA 保护同时失效，爆炸半径翻倍。
3. **授权真相源分裂**：JWT roles（Casdoor 侧）与 casbin_rule（PG 侧）两套角色数据互不同步（角色审批不写 Casdoor、webhook 不同步 roles）→ 权限不一致。
4. **g/p 网关方案规模不可行**：casbin_rule 按用户展开 g 行，千万级用户下策略体积/内存/同步频率失控（见 §8）。

### 2.4 规模诉求
千万级用户为战略目标 → **授权路径上不得出现按用户展开的数据，只允许按角色展开的数据**（roles-in-JWT 是满足该约束的标准答案）。

## 4. 候选方案回顾与决策理由

| 方案 | 描述 | 结论与理由 |
|:---|:---|:---|
| 一：Casdoor 全 IAM | 用户/角色/权限全托管 Casdoor，PG 只留投影 | ❌ **否决**：需保留 sys 模块业务资产（菜单树/权限目录/数据范围/审计/租户），Casdoor 无法表达菜单级与数据范围授权；Casdoor UI 非业务管理台 |
| 二改：PG 授权无网关 | Casdoor 认证 + 授权全在 PG，网关只 jwt-auth | ⚠️ **部分采纳**：授权在 PG 为最终形态；但决策保留网关角色检查 → 用 Lua 插件实现（D6），而非放弃 |
| g/p 网关方案 | casbin_rule 同时维护 g（用户→角色）与 p（角色→权限），syncer 推 APISIX | ❌ **否决**：千万级下 g 行数 = 用户数 × 平均角色数（2000 万+），每 worker 全量内存 ≈ 2GB+，同步频率失控；且 F3 表明 subject 机制与 roles-in-JWT 冲突 |
| A：PG→Casdoor 角色同步 | 角色变更经 pg_net 写 Casdoor，Casdoor 签含 roles 的 JWT | ❌ **否决**：角色同步管道 = 深度绑定回归（outbox/重试/对账成本），漂移风险（Casdoor 后台直改角色），应用侧无法吊销 Casdoor token，角色变更生效依赖下次签发 |
| **B：应用自签 JWT（选定）** | Casdoor 纯认证 → Go auth-service 交换签发应用 JWT（含 roles） | ✅ **决策**：零同步管道；角色变更下次登录/刷新即时生效；应用侧可即时吊销；完全恢复最初 JWT 设计（user_id/tenant/dept/roles）；Casdoor 保持可替换薄层；千万级可扩展（§8） |

### 5.2 组件清单

| 组件 | 职责 | 关键配置 |
|:---|:---|:---|
| Casdoor | 认证（登录/注册/第三方/用户状态/禁用删除） | Application（clientId/secret）、Provider（微信等）、webhook 指向 PostgREST、token 格式建议 JWT-Custom |

### 5.3 登录时序（密码 / 第三方 / 小程序统一）

```
1. 前端未持有有效应用 JWT → 重定向 Casdoor 登录页（SDK signin/silentSignin）
2. 用户在 Casdoor 完成认证（密码 / 微信扫码 / 小程序 code 等）
3. Casdoor 回调 → 前端获得 Casdoor JWT（code → token，SDK 完成）
4. 前端调 auth-service POST /api/v1/token/exchange，携带 Casdoor JWT
5. auth-service：JWKS 验签（iss/aud/exp）→ 按 sub 查 PG
   （投影表无记录则执行 JIT 建档：upsert 投影 + 默认租户档案）
6. auth-service 查角色（sys_user_role JOIN sys_role）与租户/部门（sys_user_profile）
7. 签发应用 JWT（D4 claims，15 分钟）→ 返回 access_token + refresh_token
8. auth-service 写 sys_user_session（refresh_token 哈希，沿用原设计）
9. 前端以应用 JWT 调业务 API
```

> **小程序登录说明**：小程序无浏览器重定向——`wx.login()` 获取 code 后调用 Casdoor 小程序端点换取 Casdoor JWT（Casdoor v1.41.0+ 官方支持，F5），随后与 Web 端相同走 exchange 换取应用 JWT。

### 5.4 刷新时序（角色变更 ≤15 分钟生效的保证）

```
1. 应用 JWT 过期 → 前端携带 refresh_token 调 auth-service POST /api/v1/token/refresh
2. auth-service：校验 sys_user_session（哈希比对/轮换/单设备语义）
3. 重新查询 PG 角色/租户/部门（此时角色变更已生效）
4. 签发新应用 JWT（fresh roles）
```

### 5.5 请求时序（业务 API）

```
1. 前端：Authorization 请求头携带应用 JWT（Bearer 令牌）
2. APISIX jwt-auth：验签（`store_in_ctx=true` → payload 存入 `ctx.jwt_auth_payload`，官方文档核实）→ 通过后 payload 进入上下文
3. APISIX authz-role-check：按路由 required_roles 比对 JWT roles；不满足 → 403
4. PostgREST：验签 → 注入 request.jwt.claims
5. PG RLS：current_user_id() / current_user_roles() / current_tenant_id() 读 claims → 行级过滤
6. RPC 内：has_permission(code) 读 claims roles + sys_role_api 目录（小表索引查询，与用户数无关）
```

### 5.6 网关职责边界（为什么网关没有策略表）

**网关只回答两个问题，不回答"用户可访问哪些资源"**：

| 网关能回答 | 网关不回答 |
|:---|:---|
| ① 该 JWT 是否有效（jwt-auth 验签） | 用户的完整角色→资源映射（**只在 PG**：sys_role_api / sys_role_menu / casbin_rule 视图） |
| ② 这条路由要求的角色（required_roles，**部署期静态配置**）JWT 里有没有 | 细粒度权限判定（RPC 级 has_permission、RLS 行级过滤——都在 PG） |

关键澄清：
- `required_roles` 是**静态路由配置**（init-apisix-routes.sh 定义），不是同步来的策略表；新增路由时在配置中写明角色要求。
- 运行时在 PG 给角色授予新权限点，网关不知道也不管——细粒度判定由 PG 完成（权限目录为小表索引查询，或经 perms-in-JWT 优化后零查询，见 §11 P2）。
- Casdoor JWT 默认含 roles claim，但**本方案不信任、不使用** Casdoor 的角色（PG 才是真相源）；应用 JWT 的 roles 由 auth-service 从 PG 查询后签发。
- 与旧设计（casbin_rule 视图 + syncer 推 authz-casbin）对比：目标同为"网关快速授权"，但旧设计存在两个死穴——① authz-casbin subject 取自 header 而非 JWT claims（F11），链路缺"角色注入"环节；② JWT 由 Casdoor 签发、仅携带 Casdoor 角色，与 PG 的 role_code 无法对齐（真相源分裂）。本方案以"应用自签 JWT + 自研 Lua 插件"补全同一链路并消除分裂。

### 5.7 PG 侧授权判定（RLS 与 has_permission）

**授权三层（由粗到细）**：

| 层 | 判定位置 | 回答的问题 | 成本 |
|:---|:---|:---|:---|
| 路由级 | 网关 authz-role-check | 这条路由要求的角色，JWT 里有吗 | 读 claims，O(1) |
| API 级 | PG has_permission(code) | 这个 RPC 要求的权限点，我的角色有吗 | 小表查询（sys_role_api，与用户数无关） |
| 数据级 | PG RLS | 这些行我能看/改吗 | 读 claims，零查询 |

**RLS（行级安全）读 claims 零查询**：

PostgREST 验签后把 JWT 内容注入 `request.jwt.claims`（官方文档确认），表策略函数直接读取该上下文，**不查任何表**：

```sql
-- claims helper（04.6 新增/改造，读 JWT 零查询）
CREATE FUNCTION current_tenant_id() RETURNS uuid AS $$
  SELECT NULLIF(current_setting('request.jwt.claims', true)::jsonb->>'tenant_id', '')::uuid
$$ LANGUAGE sql STABLE;

CREATE FUNCTION current_user_roles() RETURNS text[] AS $$
  SELECT ARRAY(SELECT jsonb_array_elements_text(
           current_setting('request.jwt.claims', true)::jsonb->'roles'))
$$ LANGUAGE sql STABLE;

-- 表策略示例：租户隔离 + 管理员例外（每次行访问自动生效，走索引比较）
CREATE POLICY orders_isolation ON orders
USING (tenant_id = current_tenant_id()
       OR current_user_roles() @> ARRAY['role_admin']);
```

- 流程：请求带 JWT → PostgREST 验签 → 注入 claims → 行访问时自动评估策略 → 不符合的行不可见。全程无角色/用户表查询，成本仅字符串比较（微秒级）。
- 对比旧 007 策略中的 `EXISTS (SELECT 1 FROM sys_user_profile ...)`（对每行执行一次子查询）——04.6 的方向是替换为 claims 读取。

**has_permission(code) 小表查询**：

RLS 管"行"，has_permission 管"这个 API 能不能调"——RPC 函数开头显式调用；JWT 只携带角色码，需经 sys_role_api 把角色翻译成权限点：

```sql
-- RPC 内部（如 rpc_create_user 开头）
IF NOT has_permission('system:user:add') THEN
  RAISE EXCEPTION 'Forbidden' USING ERRCODE = 'P0001';
END IF;

CREATE FUNCTION has_permission(p_code text) RETURNS boolean AS $$
  SELECT EXISTS (
    SELECT 1 FROM sys_role_api ra
    JOIN sys_role r ON r.id = ra.role_id
    WHERE r.role_code = ANY (current_user_roles())   -- 角色来自 claims（零查询）
      AND ra.api_code = p_code
      AND r.deleted_at IS NULL
  );
$$ LANGUAGE sql STABLE;
```

- **"小表"**：sys_role_api 规模 = 角色数 × API 数（100 × 500 ≈ 5 万行封顶），**不随用户数增长**，常驻 shared_buffers，查询 ~0.1ms。
- 注：上方 SQL 为概念示意，实现时按 sys_role_api / sys_api 实际表结构编写（或直接复用 casbin_rule 视图：`v0=role_code`、`v1=API 路径模式`、`v2=HTTP 方法`）。
- roles-in-JWT 下这是唯一残留的授权查询；perms-in-JWT（§8.1 方案③）用 `claims->'perms' ? 'system:user:add'` 将其归零。

### 5.8 登出时序

```
1. 前端调 auth-service POST /api/v1/token/revoke（携带 refresh_token）
2. auth-service：置 sys_user_session 会话失效 + access token jti 写入 sys_token_blacklist
   （refresh/exchange 校验时拒绝，实现 §9.1 吊销语义）
3. 前端清除本地应用 JWT / refresh_token
4. 可选：跳转 Casdoor 登出（/api/logout，SSO 登出），触发 sso-logout webhook
```

## 7. 新组件规格

### 7.1 Go auth-service（token exchange）

**端点**：

| 端点 | 方法 | 说明 |
|:---|:---|:---|
| `/api/v1/token/exchange` | POST | 入参 `{casdoor_token}`；验签 → JIT/查询 → 签发应用 JWT + refresh_token |
| `/api/v1/token/refresh` | POST | 入参 `{refresh_token}`；轮换 + 重新查角色 → 新应用 JWT |
| `/api/v1/token/revoke` | POST | 登出：会话失效 + jti 黑名单（D11，§5.8） |
| `/.well-known/jwks` | GET | 应用 RS256 公钥集（供 APISIX / PostgREST） |
| `/healthz` | GET | 健康检查 |

**安全要求**：
- Casdoor JWT 校验：JWKS 验签、`iss`（Casdoor URL）、`aud`（Casdoor 应用 clientId）、`exp`、`jti` 防重放（可选一次性使用）
- 应用 JWT：RS256、`exp` 15 分钟、`jti`、`iss`=auth-service、`aud`=业务应用
- Refresh token：256-bit 随机、PG 哈希存储（沿用原 `sys_user_session` 设计）、轮换 + 单设备语义
- PG 账号最小权限：只读 sys_role / sys_user_role / sys_user_profile / sys_tenant，读写 sys_user_session / 投影表 JIT 字段

**部署**：容器（Dockerfile 复用 casbin-syncer 模式）或 WSL2 systemd 服务；密钥经环境变量/挂载注入（仓库内为 *** 占位符，.env 参数化）。

**入口**：exchange / refresh / revoke 端点建议经 APISIX 暴露（统一入口 + 限流，与业务路由同级管理），JWKS 端点可直连或经网关（按部署拓扑决定）。

**实现要点**：复用 casbin-syncer 的 PG 连接代码（lib/pq）；JWT 库 `go-jose` / `golang-jwt`；JWKS 缓存 + 定期刷新。

### 7.2 APISIX Lua 插件 `authz-role-check`

**逻辑**：`jwt-auth` 之后执行——从 JWT payload 提取 `roles` 数组；路由级配置 `required_roles`（可为空=仅要求认证）；存在交集 → 放行，否则 403。O(1)，无外部依赖，可水平扩展。

**定位说明**：该插件**不是新增负担，而是旧设计（roles-in-JWT + 网关授权）缺失的那一环**（F11）——官方 `authz-casbin` 的 subject 取自请求头，无法直接消费 JWT roles 数组；官方 `jwt-auth` 提供 `store_in_ctx=true` 将 payload 存入 `ctx.jwt_auth_payload`（官方文档核实），本插件读取该上下文完成角色比对。实现 ~60-100 行。

**配置示例**：
```yaml
# 路由级（插件 metadata / 路由配置）
- name: authz-role-check
  conf:
    required_roles: ["role_admin"]        # 空数组 = 仅认证
    roles_claim: "roles"                  # JWT claims 中的角色字段名
```

**挂载**：standalone 模式经 `extra_lua_path` + `custom_plugins` 加载；如本地 Admin API 可用则走标准插件注册。插件源码入仓（`gateway/apisix/plugins/authz-role-check.lua`）。

**回退**：插件缺失/异常时仅放行"已认证"请求（fail-open 仅限认证层，行级安全仍由 RLS 兜底），避免网关故障阻断全部流量。

## 8. 规模论证（千万级用户）

| 维度 | g/p 网关方案（否决） | roles-in-JWT（选定） |
|:---|:---|:---|
| 策略数据量 | g 行 = 用户数 × 平均角色数（1000 万 × 2 = **2000 万行**） | 角色→权限目录（100 角色 × 500 权限 = **5 万行**，与用户数无关） |
| APISIX 内存 | 每 worker 全量加载 ≈ **2GB/worker**（4 worker = 8GB） | **O(1)**（仅读 JWT） |
| 变更同步 | 任意用户角色变更触发重推（千万级下高频） | **零同步**（角色信息在 token 内） |
| 授权判定 | 网关 Casbin 本地 g() 匹配 | 读 JWT claims（常量时间） |
| RLS 判定 | 需查 casbin_rule / sys_user_role | 读 claims（常量时间），权限目录为小表索引查询 |
| 吊销 | 依赖重推 + 插件更新 | 应用侧黑名单/会话失效即时生效 |

**结论**：用户数（千万级）仅影响 Casdoor 用户表与 PG 业务表规模（PG 可水平扩展），**不进入授权判定路径**。

**佐证（F12）**：Casdoor 自身的授权实现即采用同一模式——JWT 携带 roles/permissions，策略库只持久化 p 规则（角色×资源），用户→角色 g 规则在运行时内存重建，授权路径与用户数无关。

### 8.1 JWT 内容三方案递进谱系（roles / perms 决策依据）

| 维度 | ① 仅 user_id | ② roles-in-JWT（选定） | ③ perms-in-JWT（P2 可选） |
|:---|:---|:---|:---|
| JWT 内容 | sub, tenant_id, dept_id | + roles | + roles + perms（权限点清单） |
| "用户→角色"解析 | **每次请求**（RLS 角色策略、RPC 检查均需先查角色） | **exchange 时一次**，之后所有请求省略 | exchange 时一次，之后省略 |
| "角色→权限点"解析 | 每次请求 | 每次 RPC 检查仍有小表查询（sys_role_api，claims roles 过滤） | exchange 时一次，之后**零查询** |
| 网关粗门槛 | 无（只能认证） | 读 claims | 读 claims |
| 前端"可访问清单" | 登录时查库（user→roles→资源） | 登录时经 rpc_get_user_permissions 查 casbin_rule 视图**一次并缓存** | 直接读 claims，零查询 |
| 每次请求授权查询 | 1-2 次（随用户数增长） | 0 次（网关/RLS）+ 管理 RPC 1 次小表查询（**与用户数无关**） | **0 次** |
| token 体积 | 最小 | 小 | 中大（按权限点数权衡） |

**本质**：三种方案的分野不是"查几次"，而是**用户数是否进入授权查询路径**——仅 user_id 时用户数出现在每次请求的查询里；roles-in-JWT 把"用户→角色"收敛到 exchange 一次，剩余"角色→权限"小字典与用户数无关；perms-in-JWT 连小字典也装入 token，授权路径彻底零查询。

**注意**：`sub` / `tenant_id` / `dept_id` 是三种方案**都必须**放进 JWT 的正交维度（RLS 数据隔离每次请求都要用，不可能查库获取）；roles / perms 才是可选的动态层。可访问清单仅登录/刷新时由**前端**经 `rpc_get_user_permissions` 查询一次并缓存（用于菜单/按钮渲染），**网关不查清单**，只做路由级角色门槛（§5.6）。

## 9. 安全设计

### 9.1 Token 生命周期
- 应用 JWT 15 分钟短时效；refresh_token 7 天（sys_user_session 哈希存储、轮换、单设备语义）
- **吊销语义（关键澄清）**：refresh_token **即时失效**（删除/标记 sys_user_session → auth-service 在 refresh/exchange 时校验拒绝）；**access token 残留至多 15 分钟**（有效期内请求不经过 auth-service，属短时效 JWT 的标准语义）。如需秒级吊销 access token，需网关侧查黑名单（引入每请求查询，与零查询原则冲突）——P2 按需评估，默认接受 15 分钟窗口

### 9.2 Token Exchange 防护
- Casdoor JWT 严格校验（iss / aud / exp / 签名）；拒绝空 sub
- exchange/refresh 限流（Redis/内存令牌桶），防暴力与重放

### 9.3 授权一致性
- 角色唯一真相源 = PG；JWT roles 每次 exchange/refresh 时从 PG 新鲜查询
- 网关插件与 RLS 均消费同一 JWT claims，无第二数据源
- **无角色用户**：roles 为空数组时网关 required_roles 判定为 403；如需游客默认权限，在 exchange 时对无角色用户兜底授予 `role_guest`（沿用原 user_login_sso 设计），是否启用由业务决定

### 9.4 镜像表瘦身（D8，迁移 008；casdoor_user_mirror = 投影表/镜像表，同一张表）
**删除**：`password`、`passwordsalt`、`totpsecret`、`recoverycodes`、`mfaaccounts`、`mfaitems`、`mfaphoneenabled`、`mfaemailenabled`、`mfapushenabled`、`mfaradius*`、`webauthncredentials`、`faceids`、`managedaccounts`、`ldap`、`ipwhitelist`、`invitation*` 等
**保留（~15）**：`id`、`name`、`displayname`、`email`、`phone`、`avatar`、`isforbidden`、`isdeleted`、`isadmin`（仅存档，业务超管判定一律以 PG 角色 role_admin 为准）、`signupapplication`、`createdtime`、`updatedtime`、派生 `is_active`/`deleted_at`、审计列

### 9.5 最小权限
- auth-service PG 账号只读授权数据 + 仅可写会话/投影必要字段
- Casdoor 管理凭据仅存在于部署配置，不落业务库

### 9.6 千万级备注
- Casdoor 自身可多副本 + 共享 PG/Redis 横向扩展（登录 QPS 瓶颈，非本决策范围，记录在案）

## 10. 风险与缓解

| 风险 | 影响 | 缓解 |
|:---|:---|:---|
| Casdoor 单点（登录依赖） | 登录/注册不可用 | 多副本 + 健康检查；登录页降级提示（离线期不影响已签发应用 JWT 的业务访问） |
| 双 token 概念复杂度 | 前端实现成本 | 前端 SDK 封装（axios 拦截器统一 exchange/refresh），对业务组件透明 |
| Lua 插件维护 | 网关逻辑自维护 | 插件 ~60-100 行、入仓版本控制、fail-open 策略（RLS 兜底） |
| auth-service 成为新组件 | 运维面 +1 | 复用 casbin-syncer 部署模式（容器/systemd）；极简代码面 |
| 未来开放平台场景（第三方直接调 API） | 需要 Casdoor token 直通 | 预留：auth-service 增加"Casdoor token → 应用 JWT"直通模式（同一 exchange 逻辑，可加） |
| 角色并发变更 | 极端下 roles 短暂不一致 | exchange/refresh 时新鲜查询天然收敛；变更走事务，无异步管道 |
| 团队惯性倾向复用官方 authz 插件（authz-casdoor / authz-casbin） | 重新引入旧设计的链路缺环与真相源分裂 | 决策依据见 F10/F11；网关快速授权由 jwt-auth + authz-role-check 达成，不再引入同步策略表 |
