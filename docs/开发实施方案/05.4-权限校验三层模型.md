# 05.4 — 权限校验三层模型（has_permission vs RLS vs 前端缓存）

> **状态**：✅ 定稿（2026-08-05 用户拍板后沉淀；**2026-08-14 核对更新**——055/035 演进后与代码对齐，见 §七）
> **用途**：授权校验设计参考与检查清单——回答"这个校验该放哪层、用哪个机制"。
> **一句话**：**前端缓存管"看不看得到"（UX），has_permission 管"有没有资格做"（操作级），RLS 管"能看到哪些行"（数据级）**——三层正交，缺一不可，互不重复。

---

## 一、三层模型总览

```
┌─────────────────────────────────────────────────────────┐
│ ① 前端权限缓存（UX 层）                                    │
│    登录时 rpc_get_user_permissions 拉权限码集合 →           │
│    控制按钮显隐 / 路由守卫 / 菜单渲染                       │
│    ⚠️ 可被 DevTools/curl 篡改 —— 只负责"看不看得到"         │
├─────────────────────────────────────────────────────────┤
│ ② 网关层（APISIX，前置防御）                               │
│    jwt-auth 验签（Logto JWKS）+ authz-role-check           │
│    （路由级 required_roles 粗粒度）→ 401/403 前置           │
│    ⚠️ 静态路由配置，不覆盖 RPC 内细粒度                     │
├─────────────────────────────────────────────────────────┤
│ ③ has_permission(code)（操作级，PG 内）                    │
│    超管短路 + claims roles ∩ (iam_role_api → iam_api.api_code) │
│    用于：写/管理操作、敏感数据源、SECURITY DEFINER 函数     │
├─────────────────────────────────────────────────────────┤
│ ④ RLS（数据级，PG 内，最后防线）                           │
│    PostgREST 注入 request.jwt.claims → 策略按              │
│    租户/用户/角色强制行过滤 —— 引擎自动附加，不可绕过        │
│    ⚠️ SECURITY DEFINER 函数绕过 RLS（以 owner 身份执行）    │
└─────────────────────────────────────────────────────────┘
```

---

## 二、概念辨析（回答三个高频问题）

### 2.1 RLS 是什么 / 机制
- **行级数据隔离**：每个查询（无论来源）按策略强制过滤行
- 机制：PostgREST 把 JWT claims 注入 `request.jwt.claims`（GUC）→ 策略经 `current_setting('request.jwt.claims')` 读取租户/用户/角色 → **引擎自动附加行过滤**（声明式 USING 表达式，非手动 WHERE）
- 前提：表 `ENABLE ROW LEVEL SECURITY`（项目全部系统表已启用）+ 角色有表权限（028 已补齐 GRANT）
- 无法被应用层绕过（表 owner / BYPASSRLS 除外）

### 2.2 has_permission 是什么
- **功能级授权判定**：当前用户（claims roles）是否有权执行某操作（权限点 code）
- 典型用法：RPC 入口门槛 `IF NOT has_permission('public:xxx') THEN RAISE 42501`；统一入口 `require_permission(code)`（035 三档模型，不通过即 RAISE 42501）
- 判定零查询（claims）+ 小表索引——**单通道（055 D3 收敛）**：权限点 = `iam_menu` button 行 `api_code`，经 `iam_role_menu` 绑定角色（040 双通道 iam_role_api→iam_api 已废弃收敛；iam_api/iam_role_api 表 055 已删）

### 2.3 前端权限缓存与后端校验冲突吗？
**不冲突——分层**：
- 前端缓存 = 体验层（隐藏按钮/守卫路由）；后端校验 = 安全层（API 强制）
- 前端可篡改 → **安全边界永远在后端**；"按钮藏了但 API 仍校验"才是完整设计
- 两者叠加：看不到（UX）+ 做不到（安全）

## 三、选择矩阵（业界标准模式）

> 参考：RuoYi `@PreAuthorize("@ss.hasPermi(...)")`（操作级）+ DataScope 数据权限（部门范围）；Admin.NET 权限校验 + 租户过滤器；Supabase/PostgREST 生态 RLS（数据级唯一控制）。

| 场景 | 用谁 | 原因 |
|:---|:---|:---|
| **普通查询**（列表/详情/树） | **RLS 即可** | 行级隔离天然保证"只看本租户数据"，逐 RPC 校验是重复劳动 |
| **写/管理操作**（增删改/导出/配置/定时任务） | **必须 has_permission** | RLS 管"删哪些行"，管不了"是否有删除资格" |
| **敏感数据源**（audit_log 全量/跨租户统计/登录日志/配置） | **必须 has_permission** | 超管门槛 + 权限点；RLS 租户维度覆盖不了 |
| **SECURITY DEFINER 函数** | **必须函数内自校验** | ⚠️ DEFINER 绕过 RLS——has_permission 门槛或函数内显式租户过滤，二选一 |
| **纯展示接口**（health_check 等） | 无需 | 无数据暴露 |
| **自查接口**（get_current_user/get_user_menu） | 无需 | 只返回当前用户自身数据（claims 消费） |

**决策口诀**：*能不能做 → has_permission；能看哪些行 → RLS；看不看得到 → 前端缓存。DEFINER 函数永远要自校验。*
