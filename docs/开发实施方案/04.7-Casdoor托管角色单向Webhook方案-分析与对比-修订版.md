## 1. 缘起（为什么会有这个方案）

04.6 方案 B（应用自签 JWT）的复杂性根源是：**PG 想当角色分配真相源，而 JWT 又要带角色 → 只能自签 JWT（Go auth-service）**。

本方案的洞察：**Casdoor 能像同步用户一样同步角色（webhook），则 Casdoor JWT 原生携带的 roles 就是可信的**——auth-service 可以消失，roles-in-JWT 变成零成本。

核实结论（2026-08-03 源码终审，2026-08-04 复核）：**Casdoor v3.133.0 已经支持 role 的 CRUD webhook**（`add-role` / `update-role` / `delete-role`），"如果 Casdoor 能像处理 user 一样处理 role"这个前提**大部分已经成立**——但存在若干必须补齐的设计项（见 §5.6–§5.10 与 §8）。

## 3. 目标架构

```
Casdoor（用户 + 角色目录 + 角色分配 = 唯一真相源）
  ├─ webhook: user 事件  → PostgREST rpc_webhook_user_upsert/delete   （现有，按 C7 重写为整包接收）
  ├─ webhook: role 事件  → PostgREST rpc_webhook_role_upsert/delete   （新增，整包接收）
  │     add-role / update-role / delete-role
  │     update-role 携带 role.Users → diff 同步 sys_user_role 分配（带顺序守卫，§5.5）
  └─ JWT（原生: sub / name / roles / email …）—— 直接作为应用 JWT（tokenFormat=JWT-Custom，§5.7）
        │
        ▼
APISIX: jwt-auth（Casdoor JWKS，RS256）+ authz-role-check（Lua 插件，读 roles 并过滤 isEnabled）
        │
        ▼
PostgREST（jwt-secret = Casdoor JWKS；role claim key 稳定化，§5.6）→ PG
  RLS 判定:
    sub   → 用户身份（claims，零查询）
    roles → 角色判定（claims，零查询；current_user_roles() 过滤 isEnabled）
    tenant_id / dept_id → PG 侧 current_tenant_id() / current_dept_id()
                          （STABLE SECURITY DEFINER，每语句 1 次索引查询，C6）
PG 侧数据:
    casdoor_user_mirror  （用户镜像，现有 webhook + JIT 维护）
    sys_role / sys_user_role（角色与分配镜像，新增 role webhook 维护；**只读派生**，§15）
    sys_role_api / sys_role_menu / sys_menu / sys_api（业务授权绑定，PG 真相源，不变）
```

**前端流程（大幅简化）**：Casdoor SDK 登录 → 拿到 Casdoor JWT → 直接作为 Bearer 使用（axios 拦截器附加 + 401 时 silentSignin 重登）。无 exchange、无双 token。

## 4. 组件与职责划分

| 域 | 真相源 | 管理面 | 同步方式 |
|:---|:---|:---|:---|
| 用户身份 | Casdoor | Casdoor UI / 自助注册 | 单向 webhook（现有，RPC 需按 C7 重写） |
| 角色目录（role_code） | Casdoor | Casdoor UI，或应用前端调 Roles API（**服务账号会话认证，§5.6**） | 单向 webhook（新增） |
| 角色分配（user→role） | **Casdoor（role.Users，§15）** | Casdoor UI，或应用前端调 Roles API（update-role 写 Users，服务账号会话认证） | 单向 webhook update-role diff（新增，带顺序守卫） |
| 角色→业务权限绑定 | PG（sys_role_api / sys_role_menu） | 应用管理端 | 无（PG 原生） |
| 数据隔离（租户/部门） | PG（sys_user_profile） | 应用管理端 | 无（PG 原生） |

**核心约束**（【修订】补全）：
- `role_code` 是 Casdoor 与 PG 之间的**唯一 join key**——Casdoor 角色名 = PG role_code（沿用 04.5 §5.2 约定）；
- **单业务 org**：角色名须在全局唯一（Casdoor PK=(owner,name)，多 org 可重名 → join 冲突）；
- 角色名建议 `[A-Za-z0-9_]+`（若采用 §5.6 方案①的 PG 角色镜像，则强制为合法 PG 标识符）；
- **不使用** Casdoor 角色继承（role.roles）与组挂角色（role.groups）——二者会使 JWT roles 与 users 镜像不一致（H6，§5.10 约束）。

## 5. 关键设计点

### 5.1 角色 webhook 同步（新增 2 个 RPC）【修订：签名与守卫】

```sql
-- 推荐签名：单 jsonb 参数接收整包 payload（PostgREST 对单 json/jsonb 参数整包传入；
--            PGRST202 报错文本已证实该能力），RPC 内自行解析——
--   payload->>'action'     事件类型（add-role/update-role/delete-role）
--   payload->>'object'     原始请求体 JSON 字符串 → (object #>> '{}')::jsonb 二次解析
--   payload->>'response'   {status:"ok"|"error",...}（非标准 JSON，字符串匹配 status:"ok"）
--   payload->>'requestUri' 含 ?id=owner/name（角色改名时含旧名，H7）
--   payload->>'createdTime' 事件时间（顺序守卫用，H5）
-- 备选签名：(action text, object jsonb, response text) 三参（body 键名匹配，多余键忽略——需实测确认）
CREATE FUNCTION api_v1_sys.webhook_role_upsert(payload jsonb) RETURNS uuid ...;
CREATE FUNCTION api_v1_sys.webhook_role_delete(payload jsonb) RETURNS boolean ...;
```

RPC 内**四道守卫**（缺一不可）：
1. **鉴权**：`X-Webhook-Secret` 校验（沿用现有模式，sys_secret 存储）；
2. **成败守卫（H4）**：`payload->>'response'` 必须含 `status:"ok"` 才落库——否则 Casdoor 端失败/越权的操作会被镜像；
3. **顺序守卫（H5）**：按 role_code 记录 last_applied（事件 id/createdTime），忽略更旧事件（防重试/Replay 乱序陈旧覆盖）；
4. **改名处理（H7）**：object.name ≠ 库内 role_code 时，从 `requestUri` 解析旧名（`id=owner%2Foldname`）→ 按"软删旧 + 新建新"处理，或直接拒绝改名（约束策略二选一）。

落库逻辑：
- `webhook_role_upsert`：upsert `sys_role`（role_code=object.name，软删标记按 isEnabled）+ 依据 `object.users` **diff 同步 `sys_user_role`**；
- `webhook_role_delete`：软删 `sys_role` + 清理 `sys_user_role` 分配 + **级联清理 `sys_role_api`/`sys_role_menu` 绑定（M5）**。

### 5.2 业务 claims 取舍（决策人已确认）

- JWT 仅含 `sub` / `roles`（+ name/email 等 Casdoor 身份字段）；**不含 tenant_id / dept_id**；
- PG 侧 helper（【修订】示例补齐 SECURITY DEFINER，防 RLS 递归——仓库 current_tenant_id.sql 已是此形态）：

```sql
-- 零参 STABLE：每条语句评估一次（C6），索引查询 ~0.1ms
CREATE FUNCTION current_tenant_id() RETURNS uuid AS $$
  SELECT p.tenant_id FROM sys_user_profile p
  WHERE p.user_id = current_user_id() AND p.deleted_at IS NULL
$$ LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public, pg_temp;
```

- RLS 租户隔离策略用该 helper；角色判定读 claims（新增 `current_user_roles()`：取 `request.jwt.claims->'roles'` 数组元素 name，**过滤 `isEnabled=true`，H9**——零查询）。

### 5.3 吊销语义（回归 Casdoor 生命周期）

- Access Token 短时效（15 分钟，application.ExpireInHours=0.25）；刷新由 Casdoor/SDK 处理（silentSignin / refresh token）；
- 应用侧强制下线 = 调 Casdoor 登出/吊销 API（`/api/delete-token` 存在，controllers/token.go:149；低频管理操作），或接受 ≤15 分钟残留（与 04.6 v1.2 的吊销语义一致）；
- `sys_user_session` / `sys_token_blacklist` **不再承担应用会话职责**（Casdoor 管 token 生命周期）；【修订】注意 `PGRST_DB_PRE_REQUEST=check_token_blacklist`（docker-compose.yml:89）需一并处置：移除，或反向利用——订阅 **delete-token** webhook 事件把 jti 写入黑名单实现近即时吊销（增强项，M8）。

### 5.4 角色申请审批流（若保留）【修订：认证路径补全】

- 审批通过 → 应用侧调 **Casdoor Roles API**（`update-role` 写 Users）——**单次低频调用**；
- **认证方式（H2）**：专用服务账号（业务 org、isAdmin=true）经 APISIX `/casdoor/*` 代理调 `POST /api/login` 获取会话 cookie → 携带 cookie 调 update-role（record.Organization=业务 org → webhook 正常触发）。**禁止** clientId/clientSecret 路径（app 主体不触发 webhook，静默失步）；**禁止** DB 直写 Casdoor role 表（绕过事件）；
- 或直接砍掉审批流，角色分配全在 Casdoor UI。

### 5.5 JIT 建档

- 沿用现有 `ensure_user`（前端登录后调用）+ 用户 webhook 镜像（现有代码，RPC 按 C7 重写）。

### 5.6 网关（【修订】两处变化，非"仅一处"）

- `jwt-auth` + `authz-role-check`（Lua 插件，读取 roles 数组并**过滤 isEnabled**）；
- 变化 ①：**修复 jwt-auth 插件元数据为 RS256 + cert 公钥**——scripts/setup_apisix.sh:52-58 目前按 HS256 从 `keys[0]['k']` 提取（RS256 JWKS 无 k → 空密钥），需核查部署实况（M7）；
- 变化 ②：JWKS 保持指向 **Casdoor**（相对 04.6 方案 B 的 auth-service 而言；方案 C 下无切换动作）；
- 【修订·可选安全项】应用使用**专用 cert**（勿共用 cert-built-in，M9），并按需校验 `aud=clientId`。

### 5.7 tokenFormat：JWT-Custom 强制（【修订·新增】H3）

- 默认 `JWT` 格式泄漏 passwordSalt/preHash/totpSecret 等凭据字段进每个 Bearer（C12）——方案 C 下该 token 直达业务网关与 PG，**必须** `tokenFormat=JWT-Custom`；
- tokenFields 白名单（Go 结构体字段名）：`Id, Name, DisplayName, Email, Phone, Avatar, Roles, Groups`（+ 需要时 `Properties.xxx` 自定义 claims，供未来 tenant/dept 升级）；
- 注意 tokenFields 同时白名单化 `/userinfo`——前端用户信息继续走 `get_current_user` RPC，不依赖 userinfo；
- JWT-Custom 下 roles 仍为**对象数组**，`.roles[0].name` 兼容（C12）。

### 5.8 PG 角色切换语义（【修订·新增】H1）

- 现状 `PGRST_JWT_ROLE_CLAIM_KEY=".roles[0].name"`：多角色用户下 roles[0] 按 created_time 倒序**不稳定**（C11）→ 新建角色可能改变既有用户的 PG 角色切换目标，未映射则全请求 42501；
- **推荐**：JWT-Custom `tokenAttributes` 注入静态 claim `db_role=authenticated`（Category=Static Value, Type=String），`PGRST_JWT_ROLE_CLAIM_KEY=".db_role"` → 所有用户恒定切换至 PG `authenticated` 角色，业务角色判定全部走 claims（RLS current_user_roles / 网关插件），与用户数无关；
- 备选：为每个 Casdoor 角色创建同名 PG 角色并 `GRANT … TO authenticator`（要求角色名合法 PG 标识符 + 每次角色创建/删除同步 PG 角色生命周期——成本高）；
- **保留"全员默认 authenticated 角色"约定**（signup 挂载，Phase 1 已有）：roles=[] 时 PostgREST 回落 anon → 42501（M6）。

### 5.9 顺序守卫与对账（【修订·新增】H5/H8）

- **顺序守卫**：RPC 按 role_code 记录 last_applied record.id/createdTime，忽略更旧事件（重试/Replay 安全）；
- **初始导入**：上线时一次性 `GET /api/get-roles?owner=<org>`（分页）灌入 sys_role + sys_user_role；
- **周期对账**：cron（如每日）拉取全量角色（get-roles 分页）与 PG 镜像 diff 修正（事件丢失自愈）；角色镜像**没有** Syncer/JIT 兜底（C13），此作业为必备项；
- **运维可观测**：监控 Casdoor "Webhook Events" 页（Pending/Failed/Retrying 状态 + Replay 按钮）。

### 5.10 角色模型约束（【修订·新增】H6/H9）

- **禁用角色继承**（role.roles）与**组挂角色**（role.groups）——JWT 会展开祖先角色、组员不在 role.Users，导致 claims 与镜像不一致；如确有需求，须扩展同步（同步 role.roles 建层级、user 事件重算分配）；
- **isEnabled 语义**：禁用角色仍进 JWT（C11）→ `current_user_roles()` 与网关插件必须过滤 `isEnabled=true`；
- **改名约束**：禁止通过 API 改名（或按 §5.1 守卫 4 处理 rename=delete+add）。

## 6. 方案 B vs 方案 C 对比总表

| 维度 | 04.6 方案 B（应用自签 JWT，现行） | 方案 C（Casdoor JWT 直用，候选） |
|:---|:---|:---|
| 新增组件 | Go auth-service（exchange/refresh/JWKS） | **无**（少一个服务） |

| 同步管道 | 零同步 | **单向 webhook**（user 现有 + role 新增；user/role RPC 均需按整包 payload 重写），复用已有心智模型 |

| 角色管理面 | 应用前端自由实现 | Casdoor UI，或前端以**服务账号会话**调 Roles API（H2 认证路径） |

| 实现增量（相对 04.6 现状） | 开发 auth-service + 前端改造 | 停用 auth-service 计划；重写 2 个 user RPC + 新增 2 个 role RPC + tokenFormat/claim 配置 + 对账作业 + 前端简化 |
| JWT 信任 | 自签（claims 完全可控） | Casdoor 签（claims 受其结构限制，已接受；roles[0] 不稳定 → §5.8 稳定化） |

**本质**：方案 C = 04.6 否决的"方案一（Casdoor 全 IAM）"的**改良版**——Casdoor 管 用户 + 角色目录 + 角色分配；PG 管 业务授权绑定（菜单/API/数据范围）+ 数据隔离。之前否决方案一的理由（业务授权资产在 PG）依然成立，本方案恰好把这些资产留在 PG，只把"分配"让给 Casdoor。

## 7. 为什么这个方案成立（逻辑链）

1. Casdoor JWT 原生带 roles（C4）→ roles-in-JWT 免费获得；
2. Casdoor 有 role webhook（C1/C2）→ 角色目录与分配可单向同步到 PG 镜像，PG 侧授权数据与 JWT 一致；
3. 业务授权绑定（sys_role_api/menu）本就在 PG 且 Casdoor 不需要知道 → 双系统以 role_code 为 join key；
4. tenant/dept 不进 JWT（决策人已接受）→ 消除 Casdoor JWT 结构限制的最大障碍；
5. 于是 auth-service（方案 B 的核心成本）失去存在理由 → 架构回到"Casdoor + APISIX + PG"三个组件；
6. 【修订】上述链条成立的前提 = §5.6–§5.10 的认证路径 / claim 稳定化 / 顺序守卫 / 对账 / 约束全部落实，且 §10 实测通过 update-role 稳定性验证（H4 硬前提）。

| Casdoor UI 管理体验（英文/通用风格） | 管理员体验 | 应用前端封装 Roles API 自建页面（服务账号会话认证，工作量中等，可选） |

## 14. 分析结论：现有 role webhook 是否够用（2026-08-03 源码终审 + 2026-08-04 复核）

### 14.1 机制确认（object/record.go `NewRecord` 源码）

```go
// 关键实现（NewRecord）：
action := strings.Replace(ctx.Request.URL.Path, "/api/", "", -1)  // action = URL 路径去掉 /api/
// → add-role / update-role / delete-role 与官方事件清单一致
object := string(ctx.Input.RequestBody)                            // object = 原始请求体 JSON
object = maskPassword(object)                                      // 仅掩码密码字段
// → 不经过 GetMaskedRoles，users 数组完整保留
```

- 所有 `/api/*` 请求统一经过 AfterRecordMessage 过滤器 → AddRecord → SendWebhooks（异步入队，worker 30s 轮询投递）→ **role 端点天然在覆盖范围内，事件必然触发**；
- webhook payload = Record 结构（`action` / `object` / `user`(操作者用户名) / `organization` / `requestUri` / `response` …），无 `event` 字段（C7）。

### 14.2 够用性判定【修订：按审查报告重写】

| 需求 | 判定 | 依据 |
|:---|:---|:---|
| 角色目录同步（增/改/删） | ✅ **够用** | add-role / update-role / delete-role 必然触发，object 含角色 JSON |
| 分配同步（user↔role） | ✅ **够用（有前提）** | 分配 = 修改 role.Users → update-role 事件；object 含变更后 users 列表 → 应用 diff 可行。**前提①**：写操作提交完整角色对象（含 users）——Casdoor UI 满足；程序化调用需自行保证或事件后调 get-role 保底。**前提②**：update-role API 在部署环境稳定可用（扩展 §10 必测，技能库有 500 记录） |
| payload 完整性 | ✅ **够用** | object = 请求体原文（仅 maskPassword），无掩码、无裁剪（除非 webhook 配置了 ObjectFields 过滤） |
| **现有 user webhook RPC 兼容** | ❌ **需重写** | 真实 payload 无 `event` 字段、`user` 是操作者用户名（字符串）；现有 rpc_webhook_user_upsert/delete 的 `{"event","user"}` 参数假设**与真实 payload 不匹配**（Phase 1 代码为未实测的假设）——user 与 role 的接收 RPC 均需按**单 jsonb 整包**重写（§5.1），并加 response 成败守卫 |
| 删除事件 | ✅ **够用** | delete-role 的 object 含角色标识（UI 提交整对象），软删只需标识；需级联清理绑定（M5） |
| 失败/越权事件 | ⚠️ **需守卫** | 失败/越权请求同样投递（C9）→ RPC 必须校验 response 含 status:"ok" 才落库（§5.1 守卫 2） |
| 投递可靠性 | ✅ **够用（优于 v1 认知）** | 持久化事件队列 + 自动重试（默认 3 次）+ UI 手动 Replay + Webhook Events 监控页；但投递延迟 0~30s（worker 轮询），且重试/Replay 会乱序 → 需顺序守卫 + 周期对账（§5.9） |

### 14.3 结论

**现有 role webhook 机制够用，方案 C 的"像管理用户一样管理角色"设想成立**，落地前提 5 条（【修订：v1 为 3 条，按审查报告扩为 5 条）：

1. **接收 RPC 按真实 payload 重写**：`webhook_user_upsert/delete` 与新增的 `webhook_role_upsert/delete` 统一改为**单 jsonb 整包接收**（§5.1），RPC 内解析 action/object/response/requestUri/createdTime（修正 Phase 1 的字段假设）；
2. **成败守卫**：`response` 含 `status:"ok"` 才落库（防失败/越权事件写脏数据）；
3. **写操作提交完整角色对象**（含 users 数组）：Casdoor UI 天然满足；应用前端调 Roles API 时按整对象提交（服务账号会话认证），或 update-role 事件后调 `/api/get-role` 保底拉取再 diff；
4. **顺序守卫 + 周期对账**：last_applied 防乱序/重放；初始导入 + 周期 get-roles 全量对账（角色无 Syncer/JIT 兜底）；
5. **分配 diff 以 object.users 为基准**，删除以角色标识（owner/name）为准；声明禁用继承/组挂角色（或扩展同步）。

> 注：扩展 §10 的实测验证**必须执行**（确认当前部署版本的 payload 与 update-role 稳定性），源码终审已无阻塞性风险，但 update-role 500 复测是决策的硬前提。

## 15. 【新增】角色-用户关系表的同步与主数据源结论

> 待决策问题：**既然应用和 Casdoor 都同步用户和角色，且 Casdoor 颁发带 roles 的 JWT——应用与 Casdoor 之间的"角色-用户关系表"如何同步？关系表在哪里主动维护、作为主数据源最好？**

### 15.1 结论一句话

**角色-用户关系表（user↔role assignment）以 Casdoor 的 `role.Users` 为主数据源，应用侧 `sys_user_role` 是"webhook 维护的只读派生镜像"；主动维护动作（增/删/改分配）一律发生在 Casdoor 侧**（Casdoor UI 直接操作，或应用前端以服务账号会话经管理 API 写 Casdoor）。**不存在双主数据源**——应用侧任何写路径都通过"调 Casdoor 管理 API"间接完成，禁止直接写 PG 镜像，禁止 clientId/secret 直调。

### 15.2 数据所有权矩阵（四类数据的真相源归属）

| 数据 | 主数据源（主动维护） | 派生/镜像（被动同步） | 同步机制 |
|:---|:---|:---|:---|
| 用户目录 | **Casdoor**（UI/自助注册/管理 API） | `casdoor_user_mirror` | 单向 webhook（整包重写后）+ JIT ensure_user + （可选）Database Syncer 对账 |
| 角色目录（role_code） | **Casdoor**（UI / Roles API） | `sys_role` | 单向 webhook（add/update/delete-role）+ 初始导入 + 周期对账 |
| **角色-用户分配** | **Casdoor（role.Users）** | **`sys_user_role`（只读镜像）** | **update-role 事件全量 users diff（顺序守卫）+ 周期 get-roles 对账 + JWT 运行时事实** |
| 角色→业务权限绑定 | **PG**（sys_role_api/menu） | 无（Casdoor 不需要知道） | 无（PG 原生） |
| 租户/部门归属 | **PG**（sys_user_profile） | 无 | 无（PG 原生） |

### 15.3 为什么主数据源必须是 Casdoor（而不是 PG）

1. **方案 C 的立论基础**：Casdoor JWT 的 roles 直接取自 Casdoor 的角色数据。若 PG 是分配真相源，则必须把 PG 的分配同步回 Casdoor 才能影响 JWT——这就是 04.6 **已否决的方案 A**（PG→Casdoor 同步管道：outbox/重试/对账成本 + 漂移风险）和方案 B（自签 JWT）的由来；
2. **单一写面**：分配只在 Casdoor 一侧被修改，PG 镜像只读 → 无冲突、无对账风暴；webhook 事件是"变更通知 + 全量快照"，天然幂等可重放；
3. **JWT 一致性**：Casdoor 签发 token 时读自己的 role.Users（getRolesByUser），分配与 claims 同源，杜绝"JWT 说 A、镜像说 B"；
4. **PG 镜像的用途是查询/报表/管理展示**（"哪些用户有角色 X"、"角色 Y 有哪些人"），不参与授权判定（授权判定走 claims，零查询）——镜像短暂滞后（≤30s 事件 + ≤15min token）可接受；
5. **例外情形**：若扩展 §10 实测确认 update-role API 在部署环境不稳定（技能库 500 记录），则"应用侧主动维护分配"降级为 **Casdoor UI 直管**（管理面体验下降但方案 C 仍成立）；若连 UI 保存都不稳定，则方案 C 的分配托管分支**否决**，退回方案 B。

### 15.4 同步机制的完整链路（"如何同步"的答案）

```
① 主动维护（Casdoor 侧，二选一）：
   a. Casdoor UI 角色页编辑 users（推荐，零开发）
   b. 应用前端封装（服务账号会话认证）→ POST /api/update-role?id=org/role
      body = 整角色对象（含 users: ["org/user1", ...]）——必须是整对象
② 事件生成（Casdoor 内部，源码确认）：
   /api/update-role → AfterExec AfterRecordMessage → Record{action:update-role,
   object:整对象JSON} → SendWebhooks 入队（30s 轮询投递，失败自动重试 3 次）
③ 镜像落库（PG，RPC 四道守卫）：
   webhook_role_upsert(payload jsonb)：
     鉴权(X-Webhook-Secret) → response 含 status:"ok" → 顺序守卫(last_applied)
     → upsert sys_role → object.users 全量 diff 同步 sys_user_role
④ 运行时事实（JWT）：
   Casdoor 下次签发 token 时按 role.Users 生成 roles claims（≤15min 生效）
⑤ 自愈（对账）：
   周期任务拉 GET /api/get-roles?owner=<org>（分页）→ 与 sys_role/sys_user_role
   diff 修正（覆盖事件丢失/重试耗尽/人工 Replay 遗漏）
```

### 15.5 表结构建议（镜像侧）

- `sys_user_role`：`user_id uuid`（= JWT sub）、`role_code text`（= Casdoor 角色名）、`created_at`、审计列（_by/deleted_at）；PK=(user_id, role_code)；
- diff 语义：以事件 object.users 为全量基准——`DELETE FROM sys_user_role WHERE role_code=…` + 重插（或按集合差增量）；**必须与 webhook_role_upsert 同事务**；
- `sys_role` 增加 `last_event_id` / `last_event_time` 列（顺序守卫用）；
- 管理端查询（角色成员/用户角色）只读镜像，不写。

### 15.6 一致性声明（写进验收标准）

| 场景 | 一致窗口 | 说明 |
|:---|:---|:---|
| 分配变更 → PG 镜像 | **≤30 秒**（worker 轮询上限）+ 重试时间 | 通常 0~30s；失败自动重试 3 次 |
| 分配变更 → JWT roles 生效 | **≤15 分钟**（token 有效期） | 与 04.6 相同语义 |
| 事件永久丢失（重试耗尽） | 周期对账窗口（建议每日）内自愈 | 无 Syncer/JIT 兜底（C13），对账作业为必备 |
| 授权判定（RLS/网关） | **0 查询、无依赖** | 全部读 claims（current_user_roles 过滤 isEnabled），与镜像滞后无关 |
