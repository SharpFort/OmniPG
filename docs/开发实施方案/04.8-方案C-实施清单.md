### 2.1 D3 补充：静态 db_role claim（2026-08-04 已确认采纳）

**两层"角色"概念（先厘清，避免混淆）**：

| 含义 | 是什么 | 解决什么问题 | 例子 |
|:---|:---|:---|:---|
| **数据库角色**（database role） | `CREATE ROLE` 创建的对象 | PostgREST 收到请求后 `SET ROLE` 到哪个角色执行 SQL | `web_anon` / `authenticated` |
| **业务角色** | `sys_role` 表的行（role_code） | 权限判定、菜单/API 绑定、管理查询 | `editor` / `creator` |

- **镜像同步的是"业务角色"**（`sys_role` / `sys_user_role` 表）——本方案照做不误，它是**授权绑定锚点**：授权判定 = claims 角色 → `sys_role.id` → `sys_role_api` → 权限点，没有镜像同步绑定 join 就断了；同时也是角色成员查询/报表的数据源；
- **静态 db_role claim 动的是"数据库角色"层**：所有登录用户执行 SQL 统一切到 PG `authenticated`，业务角色判定完全由 claims + 数据表承担；
- 两者是**配套分工，不是二选一**：镜像表管"角色是什么、绑定什么权限"，静态 claim 管"用什么数据库身份执行"。

**为什么"每角色建 PG 角色"不采用（角色 ≤50、低频变化场景下的完整论证）**：

| # | 理由 | 说明 |
|:---|:---|:---|
| 1 | 双权限系统平行维护 | 业务权限走 `sys_role_api`（数据层），PG 角色方案还要再维护一套 GRANT 权限；授权判定实际全走 claims + 数据表，GRANT 是**空转的第二套权限**——维护点不同必然漂移，GRANT 少 → 42501，GRANT 多 → 越权 |
| 2 | 特权 DDL 管道 | 角色变更需在 webhook 链路执行 `CREATE ROLE`（superuser 权限）→ 要么给函数提权（风险），要么外部脚本轮询（又一条对账管道） |
| 3 | roles[0] 漂移 | Casdoor 不强制单角色，多角色时 `roles[0]` 按 created_time 倒序不稳定；静态 claim 免疫（判定 = roles 数组"任一命中"） |
| 4 | 角色名被 PG 绑架 | `CREATE ROLE` 要求合法 PG 标识符（且不能 `pg_` 开头、不能撞保留字）；静态 claim 下 role_code 仅遵循业务命名规范 `[A-Za-z0-9_]+`（04.5 §5.2），PG 不参与角色命名 |

**权限模型映射（分级授权，2026-08-04 用户描述）**：

```
未登录用户   → PG web_anon（PostgREST 匿名角色）：仅公开页面路由
注册用户     → PG authenticated（静态 claim）+ 默认业务角色 role_user：编辑/提交/个人页
创作者       → 叠加业务角色 role_creator：积分查询/兑换/广告分成
              ├─ 多角色：Casdoor 挂多个角色 → JWT roles 数组 → "任一命中"判定（零额外成本）
              └─ 或独立授权：sys_role_api 直接绑 API 权限点
```

**单角色约束（D3）的定位**：静态 claim 下系统天然支持多角色（claims 数组判定），D3"默认一个用户一个角色"降级为 **Casdoor 侧管理约定**（技术不设限）——将来要开权限组合，零代码改动。

### 5.2 重写：user webhook 接收 RPC（整包 + response 守卫）【P0】

文件：`db/api_v1/sys/rpc/rpc_webhook_user_upsert.sql`、`rpc_webhook_user_delete.sql`（**原地重写，保留文件名**）

现状问题（已核实）：现签名 `(event text, "user" jsonb)` 与真实 payload 不匹配——真实 payload 无 `event` 字段、`user` 是操作者用户名（字符串）、用户对象在 `object`（JSON 字符串，需二次解析）。Phase 1 的镜像一致性实际靠 Database Syncer + JIT 兜底，重写后 webhook 才真正生效。

```sql
-- 统一签名：单 jsonb 整包（PostgREST 对单 json/jsonb 参数整包传入，PGRST202 已证实）
CREATE OR REPLACE FUNCTION api_v1_sys.webhook_user_upsert(payload jsonb) RETURNS uuid
-- RPC 内四步：
-- 1. 鉴权：current_setting('request.headers', true)->>'x-webhook-secret' = sys_secret.casdoor_webhook_secret
-- 2. 成败守卫：payload->>'response' 须含 status:"ok"（字符串匹配，非标准 JSON）
-- 3. 解析：v_obj := (payload->>'object')::jsonb   -- 二次解析
--    action ∈ {new-user, add-user, update-user}（delete-user 走 delete RPC）
-- 4. 落库：现有 upsert 逻辑不变（casdoor_user_mirror 核心字段 + sys_user_profile 默认租户）
```

**验收**：Casdoor UI 改用户资料 → 事件到达 → 镜像更新且不依赖 Syncer/JIT；失败请求（如越权改他人）不落库。

CREATE OR REPLACE FUNCTION api_v1_sys.webhook_role_upsert(payload jsonb) RETURNS uuid
-- 四道守卫（缺一不可）：
-- ① 鉴权：X-Webhook-Secret 比对（同 5.2）

### 5.5 新增：current_user_roles()（claims 角色解析，过滤 isEnabled）【P0】

文件：`db/src/sys/functions/current_user_roles.sql`

```sql
CREATE OR REPLACE FUNCTION current_user_roles() RETURNS text[]
LANGUAGE sql STABLE
AS $$
  SELECT ARRAY(
    SELECT e->>'name'
    FROM jsonb_array_elements(COALESCE(
      current_setting('request.jwt.claims', true)::jsonb -> 'roles', '[]'::jsonb)) e
    WHERE (e->>'isEnabled')::boolean = TRUE
  );
$$;
COMMENT ON FUNCTION current_user_roles() IS '当前用户有效角色 code 列表（JWT claims，过滤 isEnabled=false，零查询）';
```

**配套**：核查 `current_tenant_id()` / `current_user_dept_id()` 已是 `STABLE SECURITY DEFINER`（仓库现状：是）；确认 `rpc_get_user_permissions` / `rpc_get_user_menu` 是否读 claims（现状核查：读 JWT roles——确认过滤 isEnabled 后兼容）。

**验收**：多角色/禁用角色场景下，`current_user_roles()` 只返回 isEnabled=true 的角色。

| 周期对账 | 同一脚本全量拉取 → 与镜像 diff 修正（事件丢失自愈）→ 输出对账报告（新增/修正/异常用户） | cron 每日 03:00（建议）+ 手动可触发 |
| 监控 | Casdoor "Webhook Events" 页 Pending/Failed/Retrying 状态 + Replay 按钮 | 运维例行 |

**验收**：模拟事件丢失（删一行分配）→ 次日对账恢复；报告输出可读。

## 9. 验收标准（端到端）

### 9.1 正向场景

| 场景 | 操作（Casdoor UI） | 预期 |
|:---|:---|:---|
| S1 建角色 | 新建角色 `editor` | ≤30s `sys_role` 出现 role_code=editor，is_active=true |
| S2 挂用户 | editor 挂 alice | ≤30s `sys_user_role` 出现 (alice, editor)；≤15min alice 新 token 带 roles |
| S3 摘用户 | editor 摘 alice | ≤30s 镜像删除；≤15min alice 新 token 无 editor；**旧 token 期间权限不变化**（可接受语义） |
| S4 禁角色 | 禁用 editor | ≤30s sys_role.is_active=false；**已签发 token 内 editor 立即失效**（current_user_roles 过滤） |
| S5 删角色 | 删除 editor | ≤30s 软删 + 分配清理 + sys_role_api/menu 绑定级联清理 |
| S6 登出/强踢 | 用户登出 / 管理端删 token | 旧 access token 立即 401（黑名单命中，V14 通过后） |
| S7 角色权限绑定 | 管理端给 editor 绑 API/菜单 | 即时生效（PG 原生，不依赖同步） |
| S8 无角色用户 | 新注册未挂角色 | 登录不 42501（静态 db_role claim → authenticated + roles=[] 兜底） |

### 9.2 一致性声明（引用 04.7 §15.6）

| 场景 | 一致窗口 |
|:---|:---|
| 分配变更 → PG 镜像 | ≤30 秒（worker 轮询）+ 重试时间 |
| 分配变更 → JWT roles 生效 | ≤15 分钟（token 有效期） |
| 事件永久丢失（重试耗尽） | 周期对账（每日）内自愈 |
| 授权判定（RLS/网关） | 0 查询、无依赖（全读 claims） |

### 9.3 安全验收

- [ ] Bearer 令牌内无 passwordSalt / totpSecret / recoveryCodes 等凭据字段（V10 对照确认）
- [ ] webhook 端点无密钥请求被拒（P0098）
- [ ] 失败/越权 Casdoor 操作不产生镜像变更（response 守卫）
- [ ] 重试/Replay 旧事件不覆盖新状态（顺序守卫）
- [ ] 应用侧无任何直接写 `sys_role` / `sys_user_role` 的存活路径（grep 验证：`INSERT INTO sys_user_role` 仅存在于 webhook RPC 与导入/对账脚本）
