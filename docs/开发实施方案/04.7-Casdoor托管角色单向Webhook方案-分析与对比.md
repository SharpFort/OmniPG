# 04.7 — 方案 C：Casdoor 托管角色 + 单向 Webhook + Casdoor JWT 直用（分析与对比）

> **状态**：🚧 候选方案（分析对比完成，待验证后决策；**未取代 04.6**）
> **日期**：2026-08-03
> **决策人输入**：业务 JWT claims **可接受仅包含 用户 + 角色**（`sub` / `roles`；tenant_id / dept_id 在 PG 侧解析，不进 JWT）
> **关联文档**：04.6-认证授权架构-最终决策（现行方案 B，本文档的对比基线）、04.5-Casdoor集成（历史）
> **一句话**：把"用户 + 角色目录 + 角色分配"的真相源全部放回 Casdoor，用**单向 webhook**（user + role）同步到 PG 镜像；Casdoor JWT 原生携带 roles，直接作为应用 JWT 使用——**Go auth-service 整体消失**。

---

## 1. 缘起（为什么会有这个方案）

04.6 方案 B（应用自签 JWT）的复杂性根源是：**PG 想当角色分配真相源，而 JWT 又要带角色 → 只能自签 JWT（Go auth-service）**。

本方案的洞察：**Casdoor 能像同步用户一样同步角色（webhook），则 Casdoor JWT 原生携带的 roles 就是可信的**——auth-service 可以消失，roles-in-JWT 变成零成本。

核实结论（2026-08-03）：**Casdoor 已经支持 role 的 CRUD webhook**（`add-role` / `update-role` / `delete-role`），"如果 Casdoor 能像处理 user 一样处理 role"这个前提**大部分已经成立**。

## 3. 目标架构

```
Casdoor（用户 + 角色目录 + 角色分配 = 唯一真相源）
  ├─ webhook: user 事件  → PostgREST rpc_webhook_user_upsert/delete   （现有，复用）
  ├─ webhook: role 事件  → PostgREST rpc_webhook_role_upsert/delete   （新增）
  │     add-role / update-role / delete-role
  │     update-role 携带 role.Users → diff 同步 sys_user_role 分配
  └─ JWT（原生: sub / name / roles / email …）—— 直接作为应用 JWT
        │
        ▼
APISIX: jwt-auth（Casdoor JWKS）+ authz-role-check（Lua 插件，读 roles）
        │
        ▼
PostgREST（jwt-secret = Casdoor JWKS）→ PG
  RLS 判定:
    sub   → 用户身份（claims，零查询）
    roles → 角色判定（claims，零查询）
    tenant_id / dept_id → PG 侧 current_tenant_id() / current_dept_id()
                          （STABLE，每语句 1 次索引查询，C6）
PG 侧数据:
    casdoor_user_mirror  （用户镜像，现有 webhook + JIT 维护）
    sys_role / sys_user_role（角色镜像，新增 role webhook 维护）
    sys_role_api / sys_role_menu / sys_menu / sys_api（业务授权绑定，PG 真相源，不变）
```

**前端流程（大幅简化）**：Casdoor SDK 登录 → 拿到 Casdoor JWT → 直接作为 Bearer 使用（axios 拦截器附加 + 401 时 silentSignin 重登）。无 exchange、无双 token。

## 4. 组件与职责划分

| 域 | 真相源 | 管理面 | 同步方式 |
|:---|:---|:---|:---|
| 用户身份 | Casdoor | Casdoor UI / 自助注册 | 单向 webhook（现有） |
| 角色目录（role_code） | Casdoor | Casdoor UI，或应用前端调 Roles API | 单向 webhook（新增） |
| 角色分配（user→role） | Casdoor | Casdoor UI，或应用前端调 Roles API（update-role 写 Users） | 单向 webhook update-role diff（新增） |
| 角色→业务权限绑定 | PG（sys_role_api / sys_role_menu） | 应用管理端 | 无（PG 原生） |
| 数据隔离（租户/部门） | PG（sys_user_profile） | 应用管理端 | 无（PG 原生） |

**核心约束**：`role_code` 是 Casdoor 与 PG 之间的**唯一 join key**——Casdoor 角色名 = PG role_code（沿用 04.5 §5.2 约定）。

## 5. 关键设计点

### 5.1 角色 webhook 同步（新增 2 个 RPC）
- `webhook_role_upsert(event, role jsonb)`：upsert `sys_role`（role_code = role.name，软删标记按 isEnabled）+ 依据 `role.Users` **diff 同步 `sys_user_role`**（增/删分配）
- `webhook_role_delete(event, role jsonb)`：软删 `sys_role` + 清理其分配
- 鉴权沿用现有模式（`X-Webhook-Secret` 校验，sys_secret 存储）
- payload 具体字段以 §10 实测为准（C3 风险点）

### 5.2 业务 claims 取舍（决策人已确认）
- JWT 仅含 `sub` / `roles`（+ name/email 等 Casdoor 身份字段）；**不含 tenant_id / dept_id**
- PG 侧新增 helper：
  ```sql
  -- 零参 STABLE：每条语句评估一次（C6），索引查询 ~0.1ms
  CREATE FUNCTION current_tenant_id() RETURNS uuid AS $$
    SELECT p.tenant_id FROM sys_user_profile p
    WHERE p.user_id = current_user_id() AND p.deleted_at IS NULL
  $$ LANGUAGE sql STABLE;
  ```
- RLS 租户隔离策略用该 helper；角色判定仍读 claims（零查询）

### 5.3 吊销语义（回归 Casdoor 生命周期）
- Access Token 短时效（15 分钟）；刷新由 Casdoor/SDK 处理（silentSignin / refresh token）
- 应用侧强制下线 = 调 Casdoor 登出/吊销 API（低频管理操作），或接受 ≤15 分钟残留（与 04.6 v1.2 的吊销语义一致）
- `sys_user_session` / `sys_token_blacklist` **不再承担应用会话职责**（Casdoor 管 token 生命周期）

### 5.4 角色申请审批流（若保留）
- 审批通过 → 应用侧调 **Casdoor Roles API**（`update-role` 写 Users）——**单次低频调用**，非同步管道、无 outbox/对账（与 04.6 否决的方案 A 有本质区别：A 是全量角色同步管道，C 只是管理操作直写）
- 或直接砍掉审批流，角色分配全在 Casdoor UI

### 5.5 JIT 建档
- 沿用现有 `ensure_user`（前端登录后调用）+ 用户 webhook 镜像（现有代码，零改动）

### 5.6 网关
- 与 04.6 相同：`jwt-auth` + `authz-role-check`（Lua 插件）
- 仅一处变化：JWKS 指向 **Casdoor**（而非 auth-service）

## 6. 方案 B vs 方案 C 对比总表

| 维度 | 04.6 方案 B（应用自签 JWT，现行） | 方案 C（Casdoor JWT 直用，候选） |
|:---|:---|:---|
| 新增组件 | Go auth-service（exchange/refresh/JWKS） | **无**（少一个服务） |
| 角色分配真相源 | PG（sys 模块全权） | **Casdoor** |
| 同步管道 | 零同步 | **单向 webhook**（user 现有 + role 新增），复用已有心智模型 |
| 角色→业务权限绑定 | PG | PG（不变） |
| JWT claims | sub/roles/tenant_id/dept_id（自签可控） | sub/roles（+Casdoor 身份字段）；**tenant/dept 走 PG helper** |
| 租户/部门 RLS | 读 claims（零查询） | STABLE helper（每请求 1 次索引查询，C6） |
| 会话/吊销 | 应用自管（sys_user_session/黑名单） | Casdoor 管（强制下线调 Casdoor API 或 ≤15min 残留） |
| 角色管理面 | 应用前端自由实现 | Casdoor UI，或前端调 Roles API（PG→Casdoor 低频管理操作回归） |
| 角色申请审批流 | PG 内自由实现 | 审批通过调 Casdoor API（单次调用）或砍掉 |
| 前端流程 | SDK → exchange → 应用 JWT（双 token） | SDK → **直接用 Casdoor JWT**（单 token） |
| 实现增量（相对 04.6 现状） | 开发 auth-service + 前端改造 | 停用 auth-service；新增 2 个 role webhook RPC + tenant/dept helper；前端简化 |
| JWT 信任 | 自签（claims 完全可控） | Casdoor 签（claims 受其结构限制，已接受） |
| 对 Casdoor 依赖 | 认证层（可替换薄层） | 认证 + 角色分配（依赖加深，但管理面单一） |

**本质**：方案 C = 04.6 否决的"方案一（Casdoor 全 IAM）"的**改良版**——Casdoor 管 用户 + 角色目录 + 角色分配；PG 管 业务授权绑定（菜单/API/数据范围）+ 数据隔离。之前否决方案一的理由（业务授权资产在 PG）依然成立，本方案恰好把这些资产留在 PG，只把"分配"让给 Casdoor。

## 7. 为什么这个方案成立（逻辑链）

1. Casdoor JWT 原生带 roles（C4）→ roles-in-JWT 免费获得；
2. Casdoor 有 role webhook（C1/C2）→ 角色目录与分配可单向同步到 PG 镜像，PG 侧授权数据与 JWT 一致；
3. 业务授权绑定（sys_role_api/menu）本就在 PG 且 Casdoor 不需要知道 → 双系统以 role_code 为 join key；
4. tenant/dept 不进 JWT（决策人已接受）→ 消除 Casdoor JWT 结构限制的最大障碍；
5. 于是 auth-service（方案 B 的核心成本）失去存在理由 → 架构回到"Casdoor + APISIX + PG"三个组件。

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
|:---|:---|:---|
| role webhook payload 完整性（update-role 是否携带完整 Users 列表） | 分配同步依赖 diff，payload 不全则无法同步 | **§10 验证步骤先行**；若不全，改由应用前端在分配操作后主动刷新（调 Casdoor get-role 拉全量 Users） |
| 双管理面（Casdoor 管分配 / PG 管绑定） | 管理员需要两处操作 | role_code 命名规范（04.5 §5.2）；应用前端可将 Casdoor 角色管理页嵌入/封装 |
| 角色分配变更时效 | webhook 秒级（Casdoor→PG）；JWT roles 生效 ≤15min（token 刷新） | 与 04.6 相同的短时效语义，可接受 |
| 应用侧吊销能力弱于方案 B | 强制下线需调 Casdoor API | 15min 短 token + Casdoor 登出/吊销 API（低频管理操作） |
| 对 Casdoor 依赖加深（角色分配） | Casdoor 不可用时角色管理不可用 | 角色管理为低频管理面，不影响已签发 token 的业务访问（同 04.6 §10） |
| Casdoor UI 管理体验（英文/通用风格） | 管理员体验 | 应用前端封装 Roles API 自建页面（工作量中等，可选） |
| 租户/部门解析每请求 1 次查询 | 相比 claims 读取略增开销 | 索引支撑 ~0.1ms；仅租户隔离策略涉及；可未来用 JWT-Custom + user properties 升级为 claims（不阻塞） |

## 14. 分析结论：现有 role webhook 是否够用（2026-08-03 源码终审）

### 14.1 机制确认（object/record.go `NewRecord` 源码）

```go
// 关键实现（NewRecord）：
action := strings.Replace(ctx.Request.URL.Path, "/api/", "", -1)  // action = URL 路径去掉 /api/
// → add-role / update-role / delete-role 与官方事件清单一致
object := string(ctx.Input.RequestBody)                            // object = 原始请求体 JSON
object = maskPassword(object)                                      // 仅掩码密码字段
// → 不经过 GetMaskedRoles，users 数组完整保留
```

- 所有 `/api/*` 请求统一经过 AfterRecordMessage 过滤器 → AddRecord → SendWebhooks（异步）→ **role 端点天然在覆盖范围内**，事件必然触发；
- webhook payload = Record 结构（`action` / `object` / `user`(操作者用户名) / `organization` / `requestUri` …），无 `event` 字段。

### 14.2 够用性判定

| 需求 | 判定 | 依据 |
|:---|:---|:---|
| 角色目录同步（增/改/删） | ✅ **够用** | add-role / update-role / delete-role 必然触发，object 含角色 JSON |
| 分配同步（user↔role） | ✅ **够用（有前提）** | 分配 = 修改 role.Users → update-role 事件；object 含变更后 users 列表 → 应用 diff 可行。**前提：写操作提交完整角色对象（含 users）**——Casdoor UI 满足；程序化调用需自行保证或事件后调 get-role 保底 |
| payload 完整性 | ✅ **够用** | object = 请求体原文（仅 maskPassword），无掩码、无裁剪（除非 webhook 配置了 ObjectFields 过滤） |
| **现有 user webhook RPC 兼容** | ❌ **需适配** | 真实 payload 无 `event` 字段、`user` 是操作者用户名（字符串）；现有 rpc_webhook_user_upsert/delete 的 `{"event","user"}` 参数假设**与真实 payload 不匹配**——user 与 role 的接收 RPC 均需按 `{action, object}` 重写（Phase 1 代码为未实测的假设，需一并修正） |
| 删除事件 | ✅ **够用** | delete-role 的 object 含角色标识（UI 提交整对象），软删只需标识 |
| 投递可靠性 | ⚠️ **基本够用** | 异步发送 + Record.isTriggered 标记；投递失败依赖应用侧兜底（JIT / 对账），与用户同步一致 |

### 14.3 结论

**现有 role webhook 机制够用，方案 C 的"像管理用户一样管理角色"设想成立**，落地前提 3 条：

1. **接收 RPC 按真实 payload 重写**：`webhook_user_upsert/delete` 与新增的 `webhook_role_upsert/delete` 统一改为 `(action text, object jsonb)` 解析（修正 Phase 1 的字段假设）；
2. **写操作提交完整角色对象**（含 users 数组）：Casdoor UI 天然满足；应用前端调 Roles API 时按整对象提交，或 update-role 事件后调 `/api/get-role` 保底拉取再 diff；
3. **分配 diff 以 object.users 为基准**，删除以角色标识（owner/name）为准。
