## 三、问题 1：app_config / audit_log / cron_job_log / department / user_profile 是否加 iam_ 前缀？

**结论：❌ 不要加 `iam_`。但当前"无前缀"命名规则存在歧义，需要三档命名修正。**

### 3.1 为什么不加 iam_

`iam_` 前缀在 v2.2 定稿中的语义是**授权域（角色/权限绑定，PG 可写）**——`iam_api` / `iam_menu` / `iam_role_api` / `iam_role_menu` 都是授权判定的数据源。而：

| 表 | 实际归属域 | 判断 |
|:---|:---|:---|
| `app_config` | 系统参数配置（通用系统域） | 非授权域 → 不加 |
| `audit_log` | 审计日志（安全/审计域） | 非授权域 → 不加 |
| `cron_job_log` | 任务调度日志（任务域） | 非授权域 → 不加 |
| `department` | 组织架构（组织域，业务也会 JOIN） | 非授权域 → 不加 |
| `user_profile` | 用户扩展资料（用户域） | 非授权域 → 不加 |

给它们加 `iam_` 会让"授权域"语义被稀释（别人看到 `iam_app_config` 会以为它与授权相关）。

### 3.2 但 v2.2 命名规则有漏洞（必须修）

v2.2 规则："**无前缀 = Logto 镜像（只读）** / `iam_` = 业务自主（可写）"。而这 5 张表也是**无前缀但可写**——规则被打破，"无前缀"现在既指只读镜像又指可写系统表，**无法从表名判断权威方**。

### 3.3 推荐方案：三档命名（需您拍板）

| 档位 | 前缀 | 语义 | 表 |
|:---|:---|:---|:---|
| ① | **无前缀** | Logto 镜像（只读，权威在 Logto） | `users` / `tenants` / `user_tenants` / `role` / `user_role` |
| ② | **`sys_`** | 系统管理域（可写，通用系统功能） | `sys_config` / `sys_audit_log` / `sys_cron_log` / `sys_department` / `sys_user_profile`（+新增字典/公告等） |
| ③ | **`iam_`** | 授权域（可写，授权判定数据） | `iam_api` / `iam_menu` / `iam_role_api` / `iam_role_menu` |

**理由**：
1. 命名三档各司其职，表名一眼可知"只读镜像 / 系统管理 / 授权域"
2. `sys_` 前缀已**空出**——Casdoor 时代授权表（sys_role 等）已全部删除/迁移为 iam_，现在 `sys_` 可重新定义为"系统管理域"，与 RuoYi/Admin.NET 业界惯例一致（它们都用 sys_ 表示系统管理表），未来团队读开源代码心智零转换
3. 您此前想摆脱 `sys_` 的动机是它与 Casdoor 授权表混淆——该混淆源已不存在（授权表全部 iam_）
4. 代价：014 刚把这 5 张表从 sys_ 改成无前缀，现在改回 sys_ 是**第 2 次改名**——好在项目从 0 开发未上线，此刻是成本最低的时点（上线后改名才痛苦）

**备选方案 B**：保持无前缀，把命名规则改为"无前缀 = 平台基础域（镜像只读 + 系统管理可写），iam_ = 授权域"——简单但丢失"只读/可写"的辨识度。

**备选方案 C**：用 `core_` 代替 `sys_`（避免与 db/src/sys 目录、api_v1_sys schema 混淆）——如果您仍介意 sys_ 与 api_v1_sys 的混淆，core_ 是次优选择。

> ⚠️ `schema_migrations` 属迁移工具表，不参与命名（保持原样）。

| 代码生成 | gen_table | — | ❌ | ✅ 不需要（零后端） |
| 用户实体/会话/密钥 | sys_user/sys_token 等 | — | 已清理 | ✅ 不需要（Logto 权威） |

### 4.2 缺口分级结论

| 级别 | 建议 | 说明 |
|:---|:---|:---|
| **P1 建议新增** | ① **字典**：`dict_type` + `dict_data`（或单表 `sys_dict`） | 业界 admin 标配，业务枚举/下拉/状态码的权威管理，避免硬编码。**与约束的分工**：字典管"展示/可配置"（文案、样式、可动态调整），约束管"合法性"——**约束形式按场景选用**：复用型/少变枚举（如 audit_log.log_type）用 PG ENUM 或 TEXT+CHECK；频繁变化（业务状态码）用 TEXT + CHECK + 字典（PG ENUM 的 ALTER TYPE ADD VALUE 有事务限制，频繁加值不便） |
| | ② **登录日志**：`login_log`（或 audit_log 增加 event_type 维度） | 安全审计刚需（谁在何时从哪 IP 登录/失败）——与 04.6/05 的登录审计诉求对应 |
| **P2 可选** | ③ 通知公告 `sys_notice`(+已读) | 业务需要站内公告时 |
| | ④ 文件元数据表 | 业务需要文件上传时（零后端下元数据入 PG + 对象存储） |
| | ⑤ 岗位 `sys_post` | 业务有职级/岗位体系时 |
| **明确不需要** | 在线用户、数据权限表、用户实体表、代码生成、会话/密钥表 | 见 4.1 理由（Logto/RLS 原生覆盖） |

### 4.3 "强大 admin 模块"还需要考虑的三件事（表之外的工程面）

1. **操作审计链路**：audit_log 需要与 PostgREST 请求打通——建议用 RLS 旁路或触发器自动记录（current_user_id()/current_tenant_id() 已有），管理端可查"谁在哪个租户做了什么"
2. **字典/参数的 RLS**：dict_data 等系统表是否按租户隔离？建议：全局字典（无 tenant_id）公共读 + 租户字典（tenant_id）按组织隔离——与 department 的隔离策略一致
3. **菜单与前端路由**：iam_menu 的字段需覆盖前端渲染需求（路由 path/component/icon/排序/类型[目录|菜单|按钮]/权限码），建议对照 RuoYi sys_menu 字段（见附录 DDL 参考）

### 附录：新增表 DDL 建议（字典 + 登录日志）

```sql
-- 字典类型
CREATE TABLE dict_type (
    id          BIGSERIAL PRIMARY KEY,
    tenant_id   TEXT,                -- NULL = 全局字典；非 NULL = 租户字典（RLS 按 claims 过滤）
    dict_name   TEXT NOT NULL,       -- 业务名（如 "user_status"）
    dict_label  TEXT NOT NULL,       -- 展示名（如 "用户状态"）
    status      BOOLEAN NOT NULL DEFAULT TRUE,
    sort_no     INT NOT NULL DEFAULT 0,
    remark      TEXT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, dict_name)
);
ALTER TABLE dict_type ENABLE ROW LEVEL SECURITY;

-- 字典数据
CREATE TABLE dict_data (
    id          BIGSERIAL PRIMARY KEY,
    dict_name   TEXT NOT NULL REFERENCES dict_type(dict_name) ON DELETE CASCADE,
    item_label  TEXT NOT NULL,       -- 显示文本（如 "启用"）
    item_value  TEXT NOT NULL,       -- 存储值（如 "1"）
    item_type   TEXT NOT NULL DEFAULT 'default',  -- default/success/warning/danger（前端样式）
    is_default  BOOLEAN NOT NULL DEFAULT FALSE,
    sort_no     INT NOT NULL DEFAULT 0,
    status      BOOLEAN NOT NULL DEFAULT TRUE,
    remark      TEXT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
ALTER TABLE dict_data ENABLE ROW LEVEL SECURITY;
-- 注：dict_name 同时充当 join key 与租户隔离键（租户字典的 dict_name 全局唯一含 tenant）

-- 登录日志（如选择独立表）
CREATE TABLE login_log (
    id          BIGSERIAL PRIMARY KEY,
    tenant_id   TEXT,
    user_id     TEXT,                -- Logto user id（镜像 users.id）
    username    TEXT,
    login_type  TEXT NOT NULL,       -- password/sms/wechat/...
    result      TEXT NOT NULL,       -- success / fail / locked / mfa_required
    fail_reason TEXT,
    ip          INET,
    user_agent  TEXT,
    logto_event TEXT,                -- PostSignIn 等（若经 webhook 补充）
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_login_log_user ON login_log (user_id, created_at DESC);
ALTER TABLE login_log ENABLE ROW LEVEL SECURITY;
-- 数据来源：APISIX 网关日志旁路 or Logto webhook（PostSignIn）+ Identifier.Lockout 事件；P1 实施时定
```
