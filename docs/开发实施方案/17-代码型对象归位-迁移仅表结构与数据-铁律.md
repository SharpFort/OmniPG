## 1. 决策结论（铁律正文）

**铁律：`db/migrations/public/` 只允许承载「表结构变更」与「一次性数据变更」；函数（RPC/底层）、视图、触发器、类型等「代码型对象」一律以幂等源文件形式归位于 `db/src/` 或 `db/api_v1/`，禁止在迁移文件中创建或修改代码型对象。**

三条硬性约束：

1. **判定先行**：任何建/改 SQL 对象的任务，先按 §4 判定表归类，再决定创建/修改的文件位置——不允许"顺手写进迁移"。
2. **禁止双份定义**：同一对象全库只允许一处定义。若目标对象在迁移中有历史定义，迁移删定义与源文件建文件**必须同一提交同步完成**，不允许过渡期双份。
3. **迁移内 GRANT 随对象收编**：`db/api_v1/public/privileges/grant_all.sql` 为 GRANT 唯一集中地（现有 35 条），迁移内散落 GRANT 随搬迁删除。

## 2. 背景与问题实锤（2026-08-14）

| 证据 | 事实 |
|---|---|
| 用户提问起点 | `rpc_create_department` 的定义在 `024_admin_crud_rpc.sql`（`api_v1_sys.` 前缀，027 改名 `api_v1_public`），`db/api_v1/public/rpc/` 无对应文件——RPC 作为 API 端点却埋在迁移史里，不可发现 |
| 现状统计 | 62 个迁移文件，38 个含 `FUNCTION`、25 个含 `VIEW`；同时 `db/src/public/functions/` 16 个、`db/api_v1/public/rpc/` 13 个、`db/api_v1/public/views/` 15 个——**双轨并存**（新对象进源码、历史对象留迁移） |
| 双份定义实锤 | `v_user_list` 同时定义于 `058` 迁移与 `db/api_v1/public/views/v_user_list.sql`；058 注释自称"v_user_list 仅源文件定义"，自己却在迁移里重建视图——注释与行为自相矛盾 |
| 前序建议未落地 | 14-v6 §4 早有"函数/视图迁到 src"的建议，但从未形成约束；且其"步骤 3：迁移中保留 CREATE 首次定义"与铁律相悖（=双份模式），**本节作废**，以本文档 §4 判定表为准 |

**根因**：项目脱胎于 C# ABP 迁移史，早期一切变更"追加式写迁移"；引入 src/api_v1 幂等层后没有回头清理历史包袱，也没有立规则阻止新代码型对象继续进迁移。

## 3. 关键技术点：执行顺序陷阱（铁律成立的前提，必须理解）

`apply-src.sh` 重放顺序：**src → api_v1 → init → migrations（迁移最后执行）**。

由此推导：

1. 若迁移中残留同名函数/视图定义，全量重放后**迁移版本覆盖源文件版本**（后执行者胜）。
2. 推论：源文件改了但迁移里还有旧定义时，**源文件的修改永远不生效**——静默回归，且 PGlite 单测源文件时全绿、部署后行为却是旧的。
3. 058 被迫把新视图写进迁移、注释却声称"仅源文件定义"——正是此陷阱的症状（不写进迁移，新版本会被 024/035 历史定义覆盖）。
4. **铁律推论**：搬迁 = 迁移删定义 + 源文件建文件，一步到位；任何"先建源文件、迁移以后再说"的做法都会触发陷阱。

## 4. 对象归属判定表（创建/修改前必查）

| 对象类型 | 判定特征 | 归属目录 |
|---|---|---|
| 表/列/约束/索引结构变更 | DDL，需版本演进 | `db/migrations/public/`（新编号文件） |
| 枚举类型创建 / ALTER TYPE | 一次性结构变更 | `db/migrations/public/` |
| seed / 权限点映射等数据 | 非幂等 INSERT（无 ON CONFLICT 全量保护） | `db/migrations/public/` |
| **PostgREST RPC** | `api_v1_public.*` 前缀（如 rpc_create_department） | `db/api_v1/public/rpc/<name>.sql` |
| 对外视图（PostgREST 暴露） | `api_v1_public.*`（如 v_user_list、v_dept_list） | `db/api_v1/public/views/<name>.sql` |
| 底层函数（被 RPC 调用） | public schema 无前缀（如 current_tenant_id、has_permission） | `db/src/public/functions/<name>.sql` |
| 触发器 / 审计模板 / 类型 | public.* | `db/src/public/triggers/`、`templates/`、`types/` |
| GRANT | — | `db/api_v1/public/privileges/grant_all.sql`（集中管理） |

> `db/src/` 与 `db/api_v1/` 下按 **schema 名** 分目录（public / inventory / sales / _shared），不是按业务模块；新模块须在 `apply-src.sh` 的 `MODULES`/`API_MODULES` 声明位置。

## 5. 例外清单（数据类必须留迁移，不算违反铁律）

- 003/011 seed 数据、040/041/055 权限点映射 INSERT、016 角色改名数据、047/048 镜像同步数据等

## 8. 铁律检查清单（agent 每次建/改 SQL 文件前逐条执行）

1. **判类型**：这个对象是结构/数据（→ 迁移新编号）还是代码型（→ 源文件）？查 §4 表。
2. **定归属**：代码型 → 按前缀定目录（`api_v1_public.*` → api_v1；public 无前缀 → src）。
3. **查双份**：`grep` 迁移目录确认无同名定义；有 → 本提交同步删迁移定义，禁止过渡期双份。
4. **幂等写法**：源文件必须 CREATE OR REPLACE / IF NOT EXISTS / DO 块保护，重放两遍不炸。
5. **GRANT 归位**：权限授予写 grant_all.sql，不散落。
6. **验证**：PGlite 验证链通过 + 确认迁移中无残留定义（防执行顺序陷阱）。
