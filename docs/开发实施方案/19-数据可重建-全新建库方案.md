# 19-数据可重建·全新建库方案（40 号方案 D20 路径 B）

> **状态**：方案定稿（2026-08-21），配合分支 `refactor/schema-platform-logto-public` 执行
> **适用前提**：业务数据可重建（开发 / 测试 / 预生产环境，或存量数据允许放弃的库）
> **与 40 号文档的关系**：D20 路径 B——**跳过 live `SET SCHEMA` 搬迁**，直接按新代码全新建库，再以种子文件回灌业务主数据
> **一句话**：清环境 → 新代码拉起 → 业务主数据种子回灌 → Logto 重放 → 验收
> 对应旧库数据保留场景的路径 A（live 搬迁）见 40 号 §4.2，本文不展开。

---

## 1. 背景与适用范围

schema 更名链（`public → platform`、`api_v1_public → api_v1_platform`、`public:* → platform:*`、`/api/v1/public/* → /api/v1/platform/*`）已全部落到仓库代码/配置/文档。对**已有数据的存量库**，存在两条落地路径：

| | 路径 A：live 搬迁 | 路径 B：全新建库（本文） |
|:---|:---|:---|
| 数据 | 保留全部数据，`SET SCHEMA` 搬迁 | 放弃存量库，仅保留业务主数据种子 |
| 停机窗口 | 需要冻结窗口（低峰停写） | 不需要（全新库无并发顾虑） |
| 操作对象 | 运行中的真实 PG 实例（需超级用户） | 全新集群，无历史包袱 |
| 脚本量 | 搬迁 + 权限收敛 + 残留校验 + 回滚演练 | 冷启动链路（已固化）+ 种子回灌 |
| 风险 | 中高（对象遗漏、FK/RLS 随表、回滚复杂） | 低（拉不起来就重拉） |
| 适合环境 | 生产、数据不可丢 | 开发/测试/预生产、数据可重建 |

**本方案适用**：当前分支处于开发重构期，大变动可接受 → 采用路径 B 最经济。
**不适用**：生产存量库（请走路径 A 或先做数据全量备份再评估）。

---

## 2. 方案优势（为什么推荐）

1. **绕开 live 搬迁全部风险**：无需 `ALTER TABLE/TYPE/FUNCTION ... SET SCHEMA`、无需逐对象核对 FK/RLS/ACL 跟随、无需回滚演练——全新库天然就是代码描述的新拓扑（`platform` 业务 + `ext` 扩展 + `public` 空置给 Logto），**零残留**。
2. **冷启动链路已被代码固化**：`scripts/verify-fresh-db.sh`（建库 → 02-schemas → dbmate 064-066 → apply-src 两遍 → 结构比对 → pgTAP）就是为本路径准备的验收器；`scripts/deploy-db.sh`（bootstrap → dbmate → apply-src）即生产化入口。
3. **种子数据大部分已在仓库**：`db/migrations/platform/066_v010_seed_data.sql` 已含 `app_config(14)`、`dict_type(2)`、`dict_data(9)`、`iam_menu(55)`，只需补充**运行时产生的业务主数据**。
4. **Logto 侧全可重放**：M2M 应用 / webhook / JWT claims 由 `scripts/phase2/init-logto.py`、`reconcile-logto.py` 脚本化，全新 Logto 重跑即可。
5. **回滚即重拉**：失败无需逆向迁移，种子文件保留可重放。
6. **`db/schema.sql` 自动重生成**：`deploy-db.sh` 的 `dbmate up` 未加 `--no-dump-schema`，全新库首次迁移即刷新快照，消除「快照残留」遗留项。

## 4. 数据保留清单（按权威方分类）

### 4.1 建议导出为种子（业务 PG 权威）

| 表 | 内容 | 说明 |
|:---|:---|:---|
| `iam_role_menu` | 角色-菜单按钮绑定 | 依赖 066 菜单 UUID（固定）与 Logto 角色名，见 §5.4 |
| `iam_role_data_scope` | 角色数据范围绑定 | 同上 |
| `department` / `position` / `user_position` | 组织/岗位主数据 | 若含 `tenant_id` 需按 P3 处理 |
| `user_profile` | 用户扩展档案 | 依赖 `users.id`（Logto 用户 id），**重新拉起后用户 id 会变**，通常放弃或仅导出全局字段 |
| `dict_type` / `dict_data` / `app_config` | 066 之外的增量字典/配置 | 066 已含基线；仅导出增量行 |
| `ip_*`（GeoLite2/ip2region） | IP 归属离线数据 | **不需要导出**，重新跑 `scripts/import-geolite2.sh`、`scripts/import-ip2region.sh` |

### 4.2 不导出（Logto 权威，重新 seed / 同步）

| 表 | 理由 |
|:---|:---|
| `users` / `tenants` / `role` / `organization_role` / `user_tenants` / `user_role` | **镜像表（064）已退役（D25）**：Logto 与 platform 同库 schema 隔离，platform 只读 Logto 表（经 platform 内投影视图），无 webhook/对账同步链路；**旧库导出无用（id 与重新 seed 的 Logto 对不上）** |

> **镜像退役影响（D25 代码改造）**：065 业务表 FK（如 `user_profile.user_id`、`department.tenant_id`）与 api_v1 视图/RLS 将改指 Logto 的 public 表（users/organizations/roles/users_roles…），投影视图承担「只读安全视图 + 敏感列不过界」（43 号 §6）。改造清单见 §8-T4。

### 4.3 可重建不导出

| 表 | 理由 |
|:---|:---|
| `audit_log` / `login_log` / `cron_job_log` / `webhook_event_log` | 审计/日志类，历史可放弃 |
| `schema_migrations` | dbmate 自行管理 |

## 5. 种子导出与规范化（关键步骤）

### 5.1 导出方式

推荐 **CSV 导出再生成 INSERT**（可控、可重写限定名），或 `pg_dump --data-only` 后统一重写；产物按 066 惯例命名为 **`067_v010_seed_data_business.sql`**（走 dbmate 迁移链，幂等 + 拓扑序可编排）：

```bash
# 方式一：CSV（推荐，便于处理 tenant_id 与权限码）
psql "$OLD_DB_URI" -c "\\copy iam_role_menu TO 'seed_iam_role_menu.csv' WITH CSV HEADER"

# 方式二：pg_dump 数据段（注意限定名是 public.xxx，需重写为 platform.xxx）
pg_dump --data-only --no-owner --no-privileges -t iam_role_menu -t iam_role_data_scope "$OLD_DB" > seed.sql
sed -i 's/COPY public\./COPY platform./g' seed.sql
```

### 5.2 schema 限定名重写（必做）

- `COPY public.xxx` / `INSERT INTO public.xxx` → **`platform.xxx`**（新库表在 platform）
- 表内引用的 `'public.xxx'::regclass` / `public.func(...)` 字符串 → `platform.xxx`

### 5.3 tenant_id（Logto 组织 id）映射（重点坑 ⚠️）

Logto 组织 id 是**服务端生成的 21 位 nanoid，不可控**；重新拉起 Logto 后组织 id 全变。凡导出的行含非空 `tenant_id`：

- **选项 1（推荐，测试环境）**：放弃租户级数据，仅保留 `tenant_id IS NULL` 的全局行（066 的 dict/app_config 即全局行）。
- **选项 2（必须保留租户数据）**：导出后建立映射表 `旧org_id → 新org_id`（先从新 Logto Management API 拉组织清单），对种子做替换；并同步重写该租户下 `department/user_position/user_profile` 等行。

### 5.4 FK 拓扑序与幂等（必做）

| 顺序 | 对象 | 注意 |
|:---|:---|:---|
| 1 | `dict_type` → `dict_data` | FK 依赖 |
| 2 | `iam_menu` | **parent_id 自引用，按拓扑序**（066 已有先例，直接复用其顺序与 UUID） |
| 3 | `iam_role_menu` / `iam_role_data_scope` | 依赖 066 菜单 UUID（**固定值，直接可用**）+ Logto 角色名（`role_code`，如 `admin`）——**先重放 Logto 同名角色再入库** |
| 4 | `department` / `position` / `user_position` | FK 依赖 user_position 等，按 065 定义 |
| 5 | `app_config` 增量 | 无 FK，可任意序 |

- 全部种子行加 `ON CONFLICT (id) DO NOTHING`（幂等，可重放）。
- **权限码注意**：`iam_menu.api_code` 已随 066 种子为 `platform:*`；旧库若导出过含 `public:*` 的菜单/绑定，必须映射为 `platform:*`（前端 v-permission 同步改）。

## 6. 全新建库操作流程

```
[0] 准备 ──→ [1] Pigsty 全新集群 ──→ [2] deploy-db.sh ──→ [3] 扩展落位 ext
     └──→ [4] deploy-gateway.sh + 路由 ──→ [5] 种子回灌 ──→ [6] Logto 初始化
          └──→ [7] 前端同步 ──→ [8] 验收（verify-fresh-db / e2e / OIDC）
```

### 0. 准备
- [ ] 确认 P1-P4 决策（§3），冻结种子导出清单（§4）
- [ ] 导出业务主数据并按 §5 规范化（schema 限定 / 拓扑序 / 幂等 / tenant 映射）
- [ ] 记录旧环境关键参数（镜像表角色名、组织清单，供 Logto 重放后对账）

### 1. Pigsty 全新集群
- [ ] 清除旧集群/旧库（`pgsql-rm` 或按 Pigsty SOP 卸载）
- [ ] 按 `infra/pigsty.yml` 拉起全新单机集群（pg_omnipg）
- [ ] **logto 角色补 `CREATEROLE`**（40 号 §3①：`pg_users.logto.privileges: [CREATEROLE]`，官方 compose 的 `POSTGRES_USER=logto` 是 superuser，本项仍比官方收敛）

### 2. 数据库部署
```bash
bash scripts/deploy-db.sh development
# 内部 = apply-src --bootstrap（init 建 platform/ext/api_v1_platform + src types）
#      → dbmate up（064/065/066 落 platform；schema.sql 自动重生成）
#      → apply-src 全量（函数/视图/RLS/权限）→ dbmate status
```

### 3. 扩展落位 ext（超级用户，一次性）
> ⚠️ `deploy-db.sh` 目前**未内置**该步（app_owner 无法 ALTER EXTENSION），见 §7-R1。
```sql
-- 以超级用户（postgres）执行
CREATE SCHEMA IF NOT EXISTS ext;                       -- 02-schemas 已幂等建，可跳过
ALTER EXTENSION pgcrypto SET SCHEMA ext;
ALTER EXTENSION pgtap    SET SCHEMA ext;
-- 验证：\dx 中 pgcrypto/pgtap 的 Schema 列为 ext
```

### 4. 网关与路由
```bash
bash scripts/deploy-gateway.sh development
bash scripts/init-apisix-routes.sh     # 路由已为 /api/v1/platform/*
```
- 核对 `PGRST_DB_SCHEMAS=api_v1_platform`、`PGRST_DB_EXTRA_SEARCH_PATH=api_v1_platform,platform,ext`

### 5. 业务种子回灌
- 按 §5.4 拓扑序执行种子文件（psql 或并入 067 迁移；测试期建议独立文件便于重放）
- 校验：`SELECT count(*) FROM platform.iam_role_menu;` 等与导出清单一致

### 6. Logto 初始化（public 交给 Logto）
- [ ] 超级用户执行：`ALTER SCHEMA public OWNER TO logto;`（40 号 D18；public 现为空置，业务零对象）
- [ ] compose `DB_URL` 改 `postgres://logto:***@host.docker.internal:5432/app_db?sslmode=disable`（端口 5433→5432）
- [ ] 容器启动自动 `db seed --swe`，Logto 71 张表原生落 public
- [ ] `python3 scripts/phase2/init-logto.py ...`（保留：M2M 应用 / 全局与组织角色 / **JWT claims 脚本（pg_role 注入，PostgREST 必需）**；**webhook 段已退役**）
- [ ] 按需创建组织（租户）与角色——**无需 webhook / reconcile 同步**：platform 直读 Logto（D25 同库只读）

### 7. 前端同步（仓库外）
- [ ] baseURL：`/api/v1/public` → `/api/v1/platform`
- [ ] `v-permission`：`public:*` → `platform:*`
- [ ] 与后端同版本发布

### 8. 验收
- [ ] `bash scripts/verify-fresh-db.sh`：结构比对 + pgTAP 全绿（112/115 或 Result: PASS）
- [ ] `bash scripts/e2e-test.sh`：业务 API 回归全绿（/api/v1/platform/*）
- [ ] Logto Console 登录、OIDC discovery（/oidc/.well-known/openid-configuration）正常
- [ ] 权限抽查：`has_permission('platform:menu:create')` 生效、`public` 内无 app_owner 对象
- [ ] `dbmate status` = Applied 4 / Pending 0（064/065/066/067）

## 7. 注意事项与风险

| # | 风险/注意 | 缓解 |
|:---|:---|:---|
| R1 | **扩展落位缺口**：全新库扩展由 Pigsty 默认装进 public，`deploy-db.sh` 未内置迁 ext | 步骤 3 手动执行一次；或后续把 `ALTER EXTENSION` 补进部署链（待办 T1） |
| R2 | **tenant_id 失联**：Logto 组织 id 重新生成，租户级数据导出后对不上 | §5.3 选项 1 放弃 / 选项 2 建立 id 映射表 |
| R3 | **镜像表 id 失联**：`users/tenants/...` 导出无用（id 变） | 4.2 不导出，Logto 重放 + 对账 |
| R4 | **绑定表时序**：`iam_role_menu` 依赖 066 菜单 UUID 与 Logto 角色名 | 先 066 幂等入库，再重放 Logto 同名角色，最后回灌绑定 |
| R5 | **权限码断裂**：旧绑定若含 `public:*` 码 | 统一映射 `platform:*`（§5.4），前端同步 |
| R6 | **种子限定名**：`COPY public.xxx` 不重写会在新库炸 | §5.2 必做 |
| R7 | **回滚**：全新建库无降级路径 | 种子文件保留可重放；重拉即回滚 |
| R8 | **Logto 升级漂移**：public 是 Logto 官方拓扑，升级走官方 runbook（`db alteration deploy latest`）；同库只读下投影视图与 Logto 表结构耦合 | 视图层为隔离点，升级后按 43 号 §6 回归（列漂移 → 调整投影视图） |
| R9 | **claims 脚本误删**：`init-logto.py` 的 JWT customizer（pg_role 注入）是 PostgREST 角色切换必需，不能整体退役 | 仅退役 webhook 段（step5）；claims（step6）/ 角色（step2/3）/ M2M（step1）保留 |
