## 3. 关键发现：本项目的独特有利条件

大多数项目"合并迁移"的最大障碍是**已执行记录**（schema_migrations 表记录旧文件名 → 新文件无记录 → 存量库重放 → 非幂等 DDL 炸）。

本项目**无此障碍**：
- 部署走 `apply-src.sh` **全量重放**，每个迁移文件都必须是幂等的（项目惯例：DO 块 + IF NOT EXISTS + CREATE OR REPLACE）
- `schema_migrations` 机制实际未使用（`db/schema.sql` 仅 16 行，dbmate 早已不是主路径）

**→ 合并后的文件只要保持幂等，存量库重放安全。** 合并无技术障碍，决策纯属工程权衡。

## 4. 方案对比

| 方案 | 做法 | 适合时机 | 风险/代价 |
|---|---|---|---|
| **A. 合并为 1 个文件** | 001-053 → 单文件 | 正式发布 v1.0 冻结后 | 大文件协作痛（10.5K 行）；验证链全废需重构；git blame 退化 |
| **B. 按域合并 6-8 个** ⭐ | identity / iam / logto镜像 / admin模块 / 清理类 / 审计配置 等按域归并 | **联调收敛后** | 中等；每个域文件 1,500-2,500 行，仍可读、可 blame、可并行 |
| **C. 发布前 squash**（业界标准） | 冻结后 001-053 → 1 个 baseline，054+ 继续编号 | v1.0 前 | 低（一次做透），但文件仍多 |
| **D. 保持现状 + 轻量整理** ✅ | 不动迁移，清理过时配置 | **现在** | 零 |

**方案 B 优于 A 的核心理由**：按域合并保留"命名即文档"的可读性，域内 diff 范围可控，且后续新迁移可落在对应域文件继续追加。

## 5. 业界实践依据

迁移合并（squash / baseline）是**发布前动作，不是开发中动作**：
- **Ecto**：`mix ecto.squash` — 发布前压缩历史迁移
- **Flyway**：`baselineOnMigrate` — 基线标记后新迁移继续编号
- **Rails**：发布前合并历史 migration 为 schema 基线

共同逻辑：开发期迁移是**活的**（随时被新需求推翻），合并后马上又要改 = 白做；且合并是一次性大工程（需重新验证全部 DDL 行为），应放在"最后一次变"之后。本项目 34-53 号连续产出正是联调期未冻结的证据。
