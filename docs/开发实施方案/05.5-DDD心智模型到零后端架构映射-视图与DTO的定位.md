# 05.5 — DDD 心智模型到零后端架构的映射：视图与 DTO 的定位

> **状态**：✅ 定稿（2026-08-06，用户讨论后沉淀）
> **用途**：回答"单表视图是否类似 DDD 里的 DTO"——并延伸到完整的 DDD → 零后端（OmniPG）概念映射，作为团队从 ABP DDD 转向零后端时的心智模型参考。
> **一句话**：**单表视图 ≈ DTO 形状 + RLS 权限边界（超集）；多表视图 ≈ CQRS Read Model（DTO + 装配逻辑）；DDD 里写 DTO 与装配代码的地方，在零后端就是 CREATE VIEW。**

---

## 一、结论先行

用 DDD 术语精确归类：

| 零后端对象 | DDD 对应物 | 说明 |
|:---|:---|:---|
| **单表视图**（纯字段投影） | **DTO（弱化版）+ 权限边界** | 指定暴露字段、隐藏敏感字段（如 password）、定义 API 输出形状；且免费获得 RLS 行级过滤 |
| **多表视图**（join/聚合/子查询） | **Read Model / Projection（读模型）** | 形状 + 数据来源 + 装配逻辑，替代 Application Service 手动拼 DTO 的代码 |
| **物化视图** | **快照型 Read Model** | 需要缓存/快照语义时的选择 |

**为什么说不完全等于 DTO**：DTO 是纯数据传输对象（零行为、无权限、无查询能力）；视图是数据库对象——它同时具备**输出形状**（DTO 职责）、**数据来源声明**（Repository 职责）、**权限边界**（RLS，DTO 完全没有）、**可继续下推的查询能力**（PostgREST 可再过滤/排序/分页）。差异是"超集 vs 子集"的关系。

---

## 二、职责拆解：视图到底干了 DTO 的哪些活

### 2.1 单表视图 = 纯 DTO 形状

以 `db/api_v1/public/views/users.sql` 为例：

```sql
CREATE VIEW api_v1_public.users AS
SELECT id, username, primary_email, ... FROM public.users;
```

这确实等价于 DDD 里的 DTO：**指定了暴露哪些字段、隐藏哪些字段（password 不暴露）、定义 API 输出形状**。在 ABP 中对应的写法：

```csharp
public class UserDto  // ABP 里定义输出形状
{
    public string Id { get; set; }
    public string UserName { get; set; }
    public string Email { get; set; }
    // ... 不包含 PasswordHash
}
```

### 2.2 多表视图 = Read Model（DTO 扛不住的部分）

以 `db/api_v1/public/views/v_user_list.sql` 为例：

```sql
CREATE OR REPLACE VIEW api_v1_public.v_user_list AS
SELECT
    u.id,
    u.username,
    u.primary_email AS email,
    u.primary_phone AS phone,
    p.tenant_id,
    p.dept_id,
    t.name AS tenant_name,
    d.dept_name,
    (NOT u.is_suspended) AS is_active,
    u.created_at,
    u.updated_at,
    u.deleted_at,
    COALESCE(
        (SELECT json_agg(ut.organization_id ORDER BY ut.organization_id)
         FROM public.user_tenants ut
         WHERE ut.user_id = u.id),
        '[]'::json
    ) AS organizations
FROM public.users u
LEFT JOIN public.user_profile p ON p.user_id = u.id
LEFT JOIN public.tenants t ON p.tenant_id = t.id
LEFT JOIN public.department d ON p.dept_id = d.id;
```

这在 DDD 里对应的是 **Application Service 层用多个 Repository 组装 DTO** 的代码：

```csharp
// DDD 里的等价物（ABP 风格）
public async Task<List<UserListDto>> GetUserListAsync()
{
    var users = await _userRepo.GetListAsync();
    var dtos = new List<UserListDto>();
    foreach (var user in users)
    {
        dtos.Add(new UserListDto
        {
            Id = user.Id,
            Username = user.UserName,
            TenantName = (await _tenantRepo.GetAsync(user.TenantId))?.Name,  // ← join
            DeptName = (await _deptRepo.GetAsync(user.DeptId))?.Name,         // ← join
            Organizations = await _userTenantRepo.GetListAsync(user.Id)       // ← 子查询聚合
        });
    }
    return dtos;
}
```

**结论**：单表视图确实类似 DTO（形状层）；多表视图 = DTO + 组装逻辑 + 数据源封装，更接近 CQRS 的 Read Model。

## 三、差异：视图比 DTO 多做什么、少做什么

| 维度 | DTO | PG 视图 |
|:---|:---|:---|
| **职责** | 纯数据传输，零行为 | 形状 + 数据来源 + **权限边界（RLS 自动附加）** |
| **权限** | 无（由 Service 层控制谁能拿到） | **有**——RLS 策略在视图查询时自动行过滤，这是 DTO 完全没有的能力 |
| **可查询性** | 拿到的就是最终结果 | 是**可继续下推的查询对象**：`?select=username&order=created_at.desc` PostgREST 可再过滤/排序/分页 |
| **数据来源** | Service 代码里拼 | SQL 声明式 join/子查询，优化器可下推（性能在 DB 侧） |
| **生命周期** | 每请求创建，无状态 | 元数据对象，**随底层表实时变化**（非快照） |
| **版本管理** | 代码仓库 | 迁移文件（CREATE OR REPLACE VIEW） |
| **行为** | 无 | **无**——视图不含行为；涉及业务规则的输出形状必须放 RPC + has_permission |
| **序列化协议** | DTO 自带（JsonSerializer 特性等） | 由 PostgREST / OpenAPI 承担（视图定义列，OpenAPI 自动生成 schema） |

### 3.1 视图 ≠ DTO 的三个坑（使用时注意）

1. **视图没有行为**——涉及业务规则的输出形状（如"有权限才显示某字段"）必须放 RPC + has_permission，不能指望视图；
2. **视图实时跟随底层表**——需要快照语义（如统计报表）时用物化视图或 RPC 缓存；
3. **过度 join 的视图会让 PostgREST 查询下推失效**——聚合/多层子查询视图（如 `v_system_stats_realtime`）要确认性能，必要时改 RPC 封装。

## 四、完整 DDD → 零后端映射表

| DDD 概念 | 零后端（OmniPG）对应物 | 项目实例 |
|:---|:---|:---|
| Entity / Aggregate Root | **表**（+ RLS 定义聚合边界） | `users`、`iam_menu`、`department` |
| Value Object | PG 类型 / CHECK 约束 / jsonb 子结构 | `audit_operation` 枚举、`app_config.config_type` |
| **DTO** | **单表视图（投影）** / RPC 返回的 json 形状 | `api_v1_public.users`、`get_current_user()` 的 json |
| **Read Model（CQRS 读模型）** | **多表视图 / 物化视图** | `v_user_list`、`v_audit_log_detail` |
| Repository | **视图 + 查询 RPC** | `v_dept_list` + `get_dept_tree()` |
| Application Service | **RPC（api_v1_public.\*）** | `search_users`、`update_config` |
| Domain Service | **src 层函数（无 schema 前缀）** | `has_permission()`、`write_audit_log()` |
| Domain Event | **触发器 + audit_log + webhook** | `trg_audit_*`、`rpc_webhook_logto` |
| 工厂/装配 | 视图的 join + RPC 内 json_build_object | `v_role_api_detail` |
| 应用服务校验（FluentValidation） | **CHECK 约束 + RPC 内校验 + pg_jsonschema** | 029 权限门槛、update_config 校验 |
| 数据权限（DataScope） | **RLS 策略（租户/行级）** | 017/019/023/024 全表策略 |
| 仓储事务边界（UoW） | **PG 事务 + RPC 原子性** | SECURITY DEFINER RPC 单事务 |

## 五、实用结论：怎么用这个认知

### 5.1 写 DTO 时想"要不要建视图"

- 如果只是**单表字段裁剪**（不 join、不聚合）→ 视图 = DTO 形状，**值得建**——同时免费获得 RLS 权限边界和 PostgREST 可查询性，比 DDD 里建 DTO 类更省。
- 需要**组装**时（join/聚合）→ 视图 = Read Model，**替代了 Application Service 里手动拼 DTO 的代码**——`v_user_list` 那段 json_agg 子查询，在 ABP 里就是一段 C# 装配逻辑，现在声明式完成。

### 5.2 视图/接口隔离策略

DDD 用多个 DTO 服务不同客户端（管理端/用户端），零后端用**多个视图**实现同样的字段隔离：

| 客户端 | DDD 做法 | 零后端做法 |
|:---|:---|:---|
| 管理端（Admin） | `UserListDto`（含 tenant_name/dept_name） | `api_v1_public.v_user_list`（join 后的管理视图） |
| 用户端（C端） | `UserProfileDto`（仅自身字段） | `api_v1_public.users`（投影视图）+ RLS |
| 敏感字段 | DTO 不映射 PasswordHash | 视图不 SELECT password 列 |

且视图天然带 RLS——同一个视图对不同租户/角色返回不同行，这是 DTO 方案需要额外写 DataScope 过滤器才能实现的。

### 5.3 行为与形状的分层原则

```
形状（数据长什么样）     → 视图（CREATE VIEW） / RPC 返回 json
行为（谁能做什么）       → has_permission（05.4 三层模型）
行为（数据怎么变）       → RPC + src 层函数（业务规则）
行为（数据变后怎么办）   → 触发器 + audit_log + webhook
能看哪些行              → RLS（05.4 三层模型）
```

**决策口诀**：*形状用视图、资格用 has_permission、行级用 RLS、快照用物化视图、带行为的输出用 RPC。*

## 六、边界与反模式（避免过度类比）

| 反模式 | 说明 |
|:---|:---|
| ❌ 视图里塞业务规则 | 视图无法做权限门槛（has_permission）——"有权限才显示字段"必须 RPC |
| ❌ 把所有查询都做成视图 | 一次性/低频/参数复杂的查询应直接 RPC + SQL，视图是**可复用形状**时才建 |
| ❌ 深层嵌套视图链 | 视图套视图（view-of-view）降低可读性与优化器下推能力，最多一层 |
| ❌ 视图承载写入 | 视图只读（除非 INSTEAD OF 触发器，但本项目统一走 RPC 写路径） |
| ❌ 把 DTO 的"传输协议"职责强加给视图 | 序列化格式/Content-Type/CORS 由 PostgREST/APISIX 网关层负责 |
