## 4. 重大缺陷（H1–H9）

### 🔴 H1【架构级·文档空白】多角色 JWT 下 PostgREST 角色切换语义

现状：`PGRST_JWT_ROLE_CLAIM_KEY=".roles[0].name"`（gateway/docker-compose.yml:88）。Phase 1 每人仅 1 个角色（authenticated），无问题；方案 C 下用户持有**多个角色**时：

- JWT roles 数组顺序 = `GetAncestorRoles` 按 `GetRoles(owner)`（created_time **DESC**）遍历（object/role.go:47-55, 355-392）→ **roles[0] = "最近创建的角色"，不是稳定值**；
- 后果：新建/挂载任一角色后，该用户 roles[0] 漂移 → PostgREST `SET ROLE` 目标随机变化；若该角色名不是 PG 角色或未 `GRANT … TO authenticator` → 用户**全部请求 42501**；
- 与 04.6 方案 B（auth-service 控制 role claim）的本质区别：方案 C 无法控制该 claim；
- 另：roles=[]（无角色）→ PostgREST 回落 anon → 42501（技能库 pitfall 14 同源）。

**需要（三选一，文档必须写明）**：① 为每个 Casdoor 角色创建同名 PG 角色 + GRANT authenticator（角色名须为合法 PG 标识符）；② **推荐**：JWT-Custom `tokenAttributes` 注入静态 claim `db_role=authenticated`，claim key 改 `.db_role`；③ 保持"全员默认 authenticated 角色"约定 + 接受漂移（不推荐）。

### 🔴 H2【架构级·文档空白 + 静默断流陷阱】"应用前端调 Roles API"的认证机制

管理 API 鉴权链（routers/authz_filter.go `getUsername` + authz/authz.go:158-209 `IsAllowed`）：只有 **global admin / 组织 admin（isAdmin=true）/ app 主体（clientId/clientSecret）/ 被显式授权（Casdoor permission 对象）** 能调 update-role——普通业务用户**不能**。

致命陷阱：**clientId/clientSecret 认证（含 Basic Auth 形式）的主体是 `app/xxx`，而 `AddRecord` 对 `organization=="app"` 的记录直接 return false（object/record.go:162-164）→ 不产生审计记录 → 不触发 webhook**。即应用用客户端凭据调 Roles API 做分配变更 → **PG 镜像静默永久失步**。

另外：**Basic Auth 在 v3.133 被解析为 OAuth client credentials（routers/base.go:113-152），不是用户名/密码**——技能库 "curl -u admin:pass 可调管理 API" 的结论在 v3.133 源码不成立（静默变 anonymous → 403）。且管理 API **不接受 Bearer token**（authz 过滤器只认 session / clientId+secret）。

**需要**：文档明确管理路径 = 专用服务账号（业务 org、isAdmin=true）经 APISIX `/casdoor/*` 代理调 `/api/login` 建会话 cookie → 带 cookie 调 update-role（record.Organization=业务 org → webhook 正常触发）；**禁止** clientId/secret 路径写角色。

### 🔴 H3【安全·文档空白】tokenFormat 未决策 = 凭据泄漏进每个 Bearer

默认 JWT 格式（token_jwt.go:583-589 + ClaimsWithoutThirdIdp）：`refineUser` 只清空 `password`，**passwordSalt / passwordType / preHash / hash / totpSecret / recoveryCodes / ldap / managedAccounts 全部进 token**（token_jwt.go:486-506, 218-306）。方案 C 中该 token 直接成为应用 Bearer（过 APISIX、PostgREST、进 RLS claims）→ 业务链路全链泄漏凭据材料。

**需要**：`tokenFormat=JWT-Custom` + `tokenFields` 白名单（Go 字段名：`Id, Name, DisplayName, Email, Phone, Avatar, Roles, Groups, Properties.*`）。JWT-Custom 下 `Roles` 仍为**对象数组**（reflect `FieldByName("Roles")` → `[]*Role`），`.roles[0].name` 兼容 ✓。注意 tokenFields 同时白名单化 `/userinfo`（前端不要依赖它取用户信息——沿用现有 `get_current_user` RPC 模式）。04.6 P2#11 已计划 JWT-Custom，方案 C 必须把它从"P2 优化"提为"P0 强制"。

### 🔴 H4【正确性·文档空白 + 硬前提】失败/被拒请求同样触发 webhook

`AfterRecordMessage` 对**所有** `/api/*` 请求（含 authz 拒绝路径 authz_filter.go:392-401 的 AddRecord、控制器错误路径）都生成记录并投递；记录 `statusCode` 恒为 200（NewRecord 硬编码），成败信息只在 **`response` 字段**（`{status:"ok"|"error", msg:...}`，键无引号、非标准 JSON）。

**后果**：Casdoor 端 update-role **失败（500/越权拒绝）时 webhook 照样投递 object** → diff 同步把**失败的操作写进 PG**。叠加技能库实测记录"**v3 的 update-role 曾返回 HTTP 500**"——若在你的部署环境复现，则"分配=改 role.Users→update-role 事件"整条前提崩溃（DB 直写不触发 webhook；UI 保存失败但事件照发 → PG 与 Casdoor 反向失步）。

**需要**：① 扩展 §10 必须复测 update-role（UI 保存 + API 直调）；② 接收 RPC 必须校验 `response` 含 `status:"ok"` 才落库（要求 RPC 接收完整 payload，见 M2 签名建议）。

### 🔴 H5【正确性·文档空白】diff 同步的乱序/重试/重放陈旧覆盖

事件队列 worker 按 created_time 升序投递（webhook_event.go:154-169），但**失败重试**（默认 3 次、60s 间隔，webhook_worker.go:184-199）和**手动 Replay**（ReplayWebhookEvent）会把旧事件插到新事件之后送达；diff 以 object.users 为全量基准 → **后到的旧事件用旧 users 覆盖新状态**。

**需要**：每 role 记录 last_applied（record.id/createdTime），忽略更旧事件；或事件到达后调 `/api/get-role` 拉权威全量再 diff（get-roles 支持分页 ✓）。

### 🟠 H6【范围·文档空白】角色继承与组挂角色

Role 模型有 `Roles []string`（子角色/继承）与 `Groups []string`（组挂角色）字段（object/role.go:35-37）：JWT roles = **直接角色 + 祖先角色**（GetAncestorRoles 展开），组员**不在 role.Users 里**（getRolesByUserInternal:238-255 按 `role.groups ∩ user.groups` 命中）。"object.users diff"只覆盖直接挂载 → **一旦使用继承或组挂角色，JWT roles ≠ sys_user_role 镜像**（授权读 claims 不受影响，但管理端镜像失真）。

**需要**：文档显式声明约束（禁继承/禁组挂角色）或扩展同步（同步 role.roles 建层级 + user 事件时重算）。

### 🟠 H7【Join key】角色重命名

Casdoor 支持改名（UI 可编辑 name，UpdateRole 有 renameRole 路径 role.go:106-146）→ role_code 变更；update-role 事件 object **只含新名**，旧名仅在 `requestUri`（`/api/update-role?id=owner%2Foldname`）。按 role_code 主键 upsert 无法配对。

**需要**：从 requestUri 解析旧名做 rename=delete+add，或声明禁止改名。

### 🟠 H8【运维·文档空白】角色镜像无对账机制

官方 Syncer 文档明确 **Syncer 只同步用户**（"Casdoor stores users in its user table… keep user data in sync"），角色不在任何 syncer 范围；角色也没有 JIT。事件 3 次重试后 Failed 且无人 Replay → **sys_role/sys_user_role 永久漂移，无自愈手段**。文档 §14.2"投递失败依赖应用侧兜底（JIT / 对账），与用户同步一致"——**该类比不成立**：用户有 Syncer+JIT 兜底，角色一个都没有。

**需要**：一次性初始导入（get-roles 分页）+ 周期全量对账（cron 调 get-roles）+ 监控 Casdoor "Webhook Events" 页（有 Replay 能力）。

### 🟠 H9【权限正确性】isEnabled=false 的角色仍进 JWT

`getRolesByUserInternal` 无 isEnabled 过滤 → 禁用角色照进 claims（对象含 `isEnabled:false`）。RLS 的 `current_user_roles()` 和网关 `authz-role-check` **必须过滤 isEnabled**，否则禁用角色在 token 有效期内继续生效。

## 6. 判定与前提条件

**方案 C 可行性判定：✅ 有条件可行（机制真实存在），但当前文档状态 ⚠️ 不足以决策。**

决策前必须满足：

1. **扩展 §10 实测**（新增 6 项）：
   - ① update-role **UI 保存 + API 直调**是否稳定 200（技能库有 500 记录——最大硬前提）；
   - ② 失败/越权请求是否触发事件（验证 response 守卫必要性）；
   - ③ 多角色 JWT 的 roles 顺序实测（H1）；
   - ④ SingleOrgOnly 行为实测（M1）；
   - ⑤ tokenFormat 实测（默认格式含凭据字段确认 + JWT-Custom 后 roles 仍为对象数组）；
   - ⑥ 角色改名事件的 requestUri 与 object 内容（H7）。
2. **补齐设计**：H1（claim 稳定化方案）、H2（管理认证路径）、H3（tokenFields 清单）、H5（顺序守卫）、H8（对账作业）、H6/H9（约束或扩展）。
3. **修正文档内部矛盾**：§5.1 签名、§8 时效、§13.3 #5、§14.2 可靠性表述。

**硬性否决点**：若 §10-① 复现 update-role 500 → 方案 C 的"分配同步"分支不可行（UI 保存失败照发事件写脏数据、DB 直写不触发事件），需退回"角色目录 webhook + 分配由 PG 侧管理"的混合方案。其余缺陷均可设计修复。
