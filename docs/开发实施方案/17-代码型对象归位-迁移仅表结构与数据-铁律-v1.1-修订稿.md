## 1. 决策结论（铁律正文 v1.1）

**铁律主文：`db/migrations/` 只允许承载「表结构变更」与「数据变更」；函数（RPC/底层）、视图、触发器、类型（含枚举）等「代码型对象」一律以幂等源文件形式归位于 `db/src/` 或 `db/api_v1/`，禁止在迁移文件中创建或修改代码型对象。**

六条硬性约束：

1. **判定先行**：任何建/改 SQL 对象的任务，先按 §4 判定表归类，再决定文件位置——不允许"顺手写进迁移"。
2. **禁止双份定义**：同一对象全库只允许一处定义。若目标对象在迁移中有历史定义，迁移删定义与源文件建文件**必须同一提交同步完成**；双轨冲突按 §6 仲裁（人工裁决强制）。
3. **GRANT 集中**：`db/api_v1/public/privileges/grant_all.sql` 为 GRANT 唯一集中地；迁移内散落 GRANT 随搬迁清理。
4. **Bootstrap 前置（B' 方案）**：部署链固定为 **bootstrap（init + `src/*/types/`）→ dbmate up → apply-src.sh 全量重放**；新建库禁止裸跑 `dbmate up`（§3.4 冷启动陷阱）。
5. **删定义机制**：从迁移中移除对象定义 = **编辑既有迁移文件删除该对象 DDL 段**；禁止新增 DROP 迁移来归位（§3.5）；迁移文件编辑边界见 §7.4。
6. **一文件一对象**：迁移出的每个代码型对象（函数/RPC/视图/触发器/枚举/类型等）**独立一个文件**（`<name>.sql` 一一对应），禁止多个对象混写一个文件；触发器函数归 `functions/`、`CREATE TRIGGER` 归 `triggers/`（两文件同一提交）；GRANT/RLS 策略沿用集中清单文件（grant_all.sql / rls_policies.sql）。历史迁移文件不受此限（按编号演进，可含多段落）。

## 3. 执行链与陷阱（铁律成立的前提，必须理解）

### 3.1 部署链（v1.1 定稿）

```
deploy-db.sh:
  ① bootstrap   —— init/*.sql（扩展/schema/角色）+ src/<module>/types/*.sql（枚举）
                   psql 逐语句 autocommit
  ② dbmate up   —— 迁移按编号顺序执行，每个迁移文件默认包在一个事务里
  ③ apply-src.sh—— 全量幂等重放: src → api_v1 → init → migrations（迁移最后）
```

- `apply-src.sh` 保留全量重放语义（幂等验证用途）；`--bootstrap` 子集标志为新增项。
- PGlite 验证链须镜像 bootstrap 顺序（P2 对齐项）。

### 3.2 陷阱一：迁移最后重放会覆盖源文件版本

`apply-src.sh` 重放顺序 **src → api_v1 → init → migrations（迁移最后执行）**：

1. 若迁移中残留同名函数/视图定义，全量重放后**迁移版本覆盖源文件版本**（后执行者胜）。
2. 推论：源文件改了但迁移里还有旧定义时，**源文件的修改永远不生效**——静默回归，且 PGlite 单测源文件时全绿、部署后行为却是旧的。
3. 058 被迫把新视图写进迁移、注释却声称"仅源文件定义"——正是此陷阱的症状。
4. **铁律推论**：搬迁 = 迁移删定义 + 源文件建文件，一步到位；任何"先建源文件、迁移以后再说"的做法都会触发陷阱。

### 3.3 陷阱二：dbmate 事务包裹（v1.1 新增）

- dbmate 官方行为：**每个迁移文件默认原子执行（包在一个事务里）**，`-- migrate:up transaction:false` 指令可关闭。
- PG 官方文档：`ALTER TYPE ... ADD VALUE` 在事务内执行时，**新值在该事务提交前不可使用**（提交后可用）。
- 推论：**任何"ADD VALUE 后同文件使用新值"的迁移，在 dbmate 下必炸**（`unsafe use of new value of enum type`）；psql 逐语句 autocommit 则安全。032 是活体案例（作者注释只考虑了 psql 路径）。
- 规则：含 ADD VALUE 且同文件使用新值的迁移，必须 `transaction:false` 或把"使用新值"段落拆到后续文件（B' 方案下枚举 ADD VALUE 一律在 src，此坑基本消失，规则保留兜底）。

### 3.4 陷阱三：冷启动依赖倒置（v1.1 新增）

现行 deploy-db.sh（dbmate 先行）无法冷启动空库，三处炸点见 §2。**bootstrap 前置阶段（init + types）是必须的修复，与枚举归位选择无关**；纪律要求：**新建库必须走 deploy-db.sh（或等价顺序），禁止裸跑 `dbmate up`**。

### 3.5 删定义机制（v1.1 新增）

- **"迁移删定义" = 编辑既有迁移文件、移除该对象的 DDL 段**（含随对象的 COMMENT；GRANT 按 §5 原地保留）。
- **禁止新增 DROP 迁移来归位**：apply-src 每次全量重放迁移（在 src 之后），迁移里的 DROP 会在**每次**重放后把 src 刚建的对象杀掉——等于每次部署都缺对象。
- dbmate 官方 README **无 checksum 机制**（只记版本号）→ 编辑已应用的迁移文件不会破坏 `dbmate status`；但编辑边界必须遵守 §7.4。

## 4. 对象归属判定表（创建/修改前必查）

| 对象类型 | 判定特征 | 归属目录 |
|---|---|---|
| 表/列/约束/索引结构变更 | DDL，需版本演进 | `db/migrations/<module>/`（新编号文件） |
| 数据变更（seed/权限点映射/回填/字典数据） | INSERT/UPDATE/DELETE，**无论幂等与否** | `db/migrations/<module>/` |
| **枚举类型创建 / 加值（ADD VALUE）** | 代码型对象（B' 拍板） | `db/src/<schema>/types/<name>.sql`（§8 模板） |
| **枚举 → CHECK/字典 转换** | 列结构 + 数据变更 | `db/migrations/`（新编号，§8.6 流程） |
| PostgREST RPC | `api_v1_public.*` 前缀（如 rpc_create_department） | `db/api_v1/public/rpc/<name>.sql` |
| 对外视图（PostgREST 暴露） | `api_v1_public.*`（如 v_user_list） | `db/api_v1/public/views/<name>.sql` |
| 底层函数（被 RPC 调用） | public schema 无前缀（如 current_tenant_id、has_permission） | `db/src/public/functions/<name>.sql` |
| 触发器 / 审计模板 / 其他类型（domain/复合） | public.* | `db/src/public/triggers/`、`templates/`、`types/` |
| GRANT | — | `db/api_v1/public/privileges/grant_all.sql`（集中管理） |

> **注 1**：`db/src/` 与 `db/api_v1/` 下按 **schema 名**分目录；新模块须在 `apply-src.sh` 的 `MODULES`/`API_MODULES` 声明位置。
> **注 2**：**新迁移不得引用 src 函数/视图**（dbmate 先于 apply-src，全新库上 src 对象尚不存在；引用 bootstrap 对象——schema/角色/枚举/扩展——合法）。
> **注 3**：**枚举不进入函数签名**（参数/返回值用 text + 函数体内部显式 cast，现行惯例 rpc_create_menu 升格为规范）——规避 src 内文件排序依赖，同时保持 RPC 参数对外为 JSON 友好的 text。
> **注 4**：搬迁产物一律**一文件一对象**（§1 约束 6）——函数/RPC/视图/触发器/类型每对象独立 `<name>.sql`；触发器函数归 `functions/`、`CREATE TRIGGER` 归 `triggers/`（两文件同一提交）；GRANT/RLS 策略沿用集中清单文件（grant_all.sql / rls_policies.sql）。

## 5. 例外清单（数据类必须留迁移，不算违反铁律）

- 003/011 seed 数据、040/041/055 权限点映射 INSERT、016 角色改名数据、047/048 镜像同步数据等。
- **判据（v1.1 统一）**：数据变更（INSERT/UPDATE/DELETE）**无论幂等与否**一律归迁移；"幂等写法（ON CONFLICT 保护）"是防重放炸的手段，**不是归位判据**——src 目录永不写数据。
- 迁移中"引用型"语句（GRANT、权限映射 INSERT、校验 DO 块引用函数名）**不随函数搬迁**，原地保留（函数存在即通过）。
- **COMMENT 随定义走**：迁移内 `COMMENT ON FUNCTION/VIEW/TRIGGER/TYPE` 属违规残留，清理对象时一并删除（iam_menu_type COMMENT 漂移实锤）。
- **新迁移禁引用 src 函数/视图**（§4 注 2）；引用 bootstrap 对象（schema/角色/枚举/扩展）合法。

## 6. 双份定义仲裁规则（人工裁决强制）

**原则：src 源文件 = 唯一权威版本。迁移中的定义一律视为"待清除的历史遗留"，不参与版本竞选。机器只负责发现与拦截，裁决必须人工执行——禁止任何自动删除/自动覆盖。**

### 6.1 五步规程

1. **定位**：发现同名对象双轨（新双份由 §6.3 机器扫描拦截；历史双份见 §11 P1/P2 清单）。
2. **取证**：按 §7 提取"迁移链终态" T_m，与 src 版本 T_s 做归一化 diff。
3. **人工分情形裁决**（强制人工环节）：
   - **情形 a**：T_s 与 T_m 等价或更新 → 迁移删定义，src 定稿；
   - **情形 b**：T_m 含有 T_s 缺失的逻辑（有人在迁移里改过、没同步进 src）→ 人工确认差异是**有意修复**（合并进 src）还是**过时残留**（丢弃），再迁移删定义；
   - **情形 c**：双向分叉（两边各有对方没有的内容）→ 逐段人工仲裁合并进 src，**禁止"两处都留"**。
4. **落点**：无论哪种情形 = 迁移删定义 + src 定稿**同一提交**；COMMENT 随定义迁走；GRANT 按 §5 原地保留。
5. **记录**：每次仲裁在迁移文件头注释登记，并在 §6.2 仲裁记录表追加一行（日期/对象/情形/结论/依据）。

## 7. 最新版定义与归位规程（回放终态）

### 7.1 定义

**对象的最新版 = 全部迁移按编号顺序重放后的数据库终态**（"最后生效的定义"）。不以文件修改时间、注释自称、作者意图为准。

### 7.2 提取规程（禁止肉眼串读迁移链）

1. **首选**：从已回放到最新的库导出终态——`pg_get_functiondef('schema.fn'::regproc)` / `pg_get_viewdef('schema.v'::regclass)` / `obj_description`，落为 src 文件。
2. **无可用库**：PGlite 验证链按 bootstrap → src → api_v1 → init → migrations 顺序全量回放 → 从 PGlite 实例导出终态。
3. **人工质检**：导出结果与迁移史关键节点做一次 diff 审阅（质检而非仲裁）；仅当发现"最后生效版本疑似回退/半成品"（最后一笔是把新功能改回去）时，提交用户裁决。

### 7.3 归位后的规则

- 该对象此后**唯一合法修改位置 = src 文件**；迁移链中其定义段已删除、永不恢复。
- 删除 = 编辑既有迁移文件移除该对象全部 DDL 段（§3.5），与 src 建文件**同一提交**。

### 7.4 迁移文件编辑边界（安全契约）

| 允许 | 禁止 |
|---|---|
| 删除代码型对象定义段（src 全量重放兜底收敛，老环境不分叉） | 修改/删除表结构、列、约束、索引段（老环境 dbmate 不重放已应用文件 → 新老结构分叉，无兜底） |
| 修正注释/登记仲裁记录（无执行语义） | 修改/删除数据段（同分叉风险） |

> dbmate 无 checksum（已核实官方 README），编辑已应用迁移文件不破坏 `dbmate status`——但上述边界必须遵守，否则新老环境分叉。

## 8. 枚举类型专项规则（B' 方案，2026-08-14 拍板）

### 8.1 归位与部署

- 枚举（**含被表列引用者**）统一归 `db/src/<schema>/types/<name>.sql`；bootstrap 前置阶段先于 dbmate 应用 → 表迁移可安全引用枚举（§3.4 冷启动陷阱随 bootstrap 一并消除）。
- 目录即注册表：`ls db/src/*/types/` = 全库枚举清单，一个文件一个枚举，头部注释记录语义/使用位置/演进史。

### 8.2 形态政策（用户决策，2026-08-14）

- **开发期（上线前）：所有枚举一律用原生 ENUM 创建，统一归 `db/src/public/types/`（当前全库枚举均属 public schema）。**
- **存量清零**：现有 TEXT+CHECK 形态枚举同样转为原生 ENUM 归位（盘点见 §8.7，任务 P0-8）。
- 测试阶段若出现值集合频繁变更/删值需求，再按 §8.6 转 TEXT+CHECK（优先字典表方案）。

### 8.3 源文件规范模板（规则本体，新建枚举必须遵守）

```sql
-- db/src/<schema>/types/<name>.sql
-- 语义: ...          使用位置: <表>.<列>
-- 演进史: v1 三值 → v2 加 'x'（日期，经办人）
-- 废弃值: z_deprecated_*（RENAME VALUE 标记，永不删除）

-- ① 当前态全量值（只追加、不重排、不删除）
DO $$ BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM pg_type t JOIN pg_namespace n ON n.oid = t.typnamespace
        WHERE t.typname = '<name>' AND n.nspname = '<schema>'
    ) THEN
        CREATE TYPE <schema>.<name> AS ENUM ('a', 'b', 'c');
    END IF;
END $$;

-- ② 每个"首次发布后追加"的值一个守卫块（新库跳过、存量库追平）
DO $$ BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM pg_enum e
        JOIN pg_type t ON t.oid = e.enumtypid
        JOIN pg_namespace n ON n.oid = t.typnamespace
        WHERE t.typname = '<name>' AND n.nspname = '<schema>' AND e.enumlabel = 'b'
    ) THEN
        ALTER TYPE <schema>.<name> ADD VALUE 'b';
    END IF;
END $$;

COMMENT ON TYPE <schema>.<name> IS '...';
```

### 8.4 硬性约束

1. **值只增不删**：PG 无 DROP VALUE；**不重排**（值有排序语义，重排会使新老库枚举顺序分叉）；废弃值 `RENAME VALUE` 加前缀标记（如 `z_deprecated_*`）。
2. **守卫必须 schema 限定**（typname + typnamespace 双条件；031 未限定 schema 是隐患）。
3. **ADD VALUE 事务限制**：事务内 ADD VALUE 的新值提交前不可用（PG 官方文档）。apply-src 的 psql 逐语句 autocommit 天然安全；**禁止在 src 文件内显式 BEGIN/COMMIT 包块**。
4. **COMMENT 只在源文件一处**（迁移内 COMMENT ON TYPE 属违规残留，§5）。
5. **枚举不进入函数签名**（§4 注 3）。

### 8.5 可发现性（枚举清单查询，附于文档即为标准口径）

| 途径 | 命令 | 说明 |
|---|---|---|
| psql | `\dT` | 全部类型清单 |
| psql | `\dT+ <枚举名>` | 单个枚举全部值 + 注释 |
| SQL | `SELECT enum_range(NULL::public.<name>);` | 单个枚举全部值 |
| **SQL（全库总清单）** | `SELECT n.nspname, t.typname, e.enumsortorder, e.enumlabel FROM pg_type t JOIN pg_enum e ON e.enumtypid=t.oid JOIN pg_namespace n ON n.oid=t.typnamespace WHERE t.typtype='e' ORDER BY 1,2,3;` | 所有 schema × 枚举 × 值 × 顺序 |
| CHECK 形态 | `SELECT conrelid::regclass, conname, pg_get_constraintdef(oid) FROM pg_constraint WHERE contype='c' ORDER BY 1,2;` | 值藏在约束定义字符串里 |

> 注意：`information_schema` **查不到枚举值**（仅笼统归类 user_defined_types），必须走 `pg_catalog`。CHECK 形态的"枚举"不是类型（无 typtype='e' 入口），可发现性弱于原生 ENUM——这也是"开发期一律原生 ENUM"政策的附带好处。

### 8.6 ENUM → CHECK/字典 转换流程（测试期触发）

1. **触发判断**：值集合需要频繁变更，或出现删值需求。
2. **优先字典表**：值多或需中文语义/权限点时，用 TEXT + 字典表 + CHECK/FK；值少则 TEXT + CHECK。
3. **迁移步骤**（新编号迁移文件）：
   - **数据清理段前置**（CHECK 建约束会校验存量行——违例数据先清，否则迁移失败）；
   - `ALTER TABLE ... ALTER COLUMN ... TYPE text USING col::text`；
   - `ADD CONSTRAINT ... CHECK (col IN (...))`；
   - `DROP TYPE IF EXISTS <schema>.<name>;`（幂等：apply-src 重放时类型已不存在，IF EXISTS 跳过）。
4. **同提交**：删除 `src/types/<name>.sql`；引用该枚举的函数/视图源文件同步修改（§9 模板）；更新函数体 cast 与注释。
5. 在 §6.2 登记转换记录。

## 9. 幂等写法模板（各对象，源文件必须遵守）

| 对象 | 常规变更 | 结构变更（签名/列集变化） |
|---|---|---|
| 函数 | `CREATE OR REPLACE FUNCTION` | 同文件 `DROP FUNCTION IF EXISTS <schema>.<name>;`（无参名形式）+ 重建；**禁止重载（一名一签名）** |
| 触发器函数 | `CREATE OR REPLACE FUNCTION` | 被触发器依赖、直接 DROP 会报依赖错误 → 函数文件（functions/）`DROP FUNCTION IF EXISTS` + 重建、触发器文件（triggers/）`DROP TRIGGER IF EXISTS` + 重建，**两文件同一提交** |
| 视图 | `CREATE OR REPLACE VIEW`（仅支持末尾加列） | 删列/改名 → 同文件 `DROP VIEW IF EXISTS` + `CREATE VIEW`；依赖视图同批修改 |
| 触发器 | PG18 可用 `CREATE OR REPLACE TRIGGER`（PG14+） | 或 `DROP TRIGGER IF EXISTS` + `CREATE TRIGGER` |
| RLS 策略 | — | `DROP POLICY IF EXISTS` + `CREATE POLICY` |
| 枚举/类型 | — | §8.3 模板 |

**全对象禁令**：禁止 CASCADE（除迁移结构清理外）；禁止源文件内显式 BEGIN/COMMIT；禁止 GRANT 散落（归 grant_all.sql）；禁止同名重载；禁止一文件多对象（§1 约束 6）。

## 12. 铁律检查清单（agent 每次建/改 SQL 文件前逐条执行）

1. **判类型**：结构/数据 → 迁移新编号；代码型 → 源文件。查 §4 表。
2. **定归属**：代码型 → 按前缀定目录（`api_v1_public.*` → api_v1；public 无前缀 → src；枚举 → `src/<schema>/types/`）。
3. **查双份**：`grep` 迁移目录确认无同名定义；有 → 按 §6 仲裁（人工裁决），本提交同步删迁移定义，禁止过渡期双份。
4. **幂等写法**：按 §9 模板（CREATE OR REPLACE / IF NOT EXISTS / DO 块守卫 / DROP IF EXISTS + CREATE），重放两遍不炸；枚举按 §8.3/§8.4。
5. **GRANT 归位**：权限授予写 grant_all.sql，不散落。
6. **新迁移依赖**：新迁移只允许引用更早迁移 + bootstrap 对象（schema/角色/枚举/扩展），禁止引用 src 函数/视图。
7. **验证**：PGlite 验证链通过 + 迁移扫描无违禁定义（防执行顺序陷阱）+ 空库冷启动冒烟（结构性变更时）。
